## 做法

1. 天气：`texts[6]` → `texts[7]`，“更新”用 `texts[6]`。
2. 待整理备忘：`navigate` 里带 id 且备忘待整理时，`memo.edit`、`memo.open` 都转到 PENDING 页（要求带 id，因为新建时临时内存没清零）；填转写文字时正文不空就换行接在后面，超过 4 KB 回 INVALID、原有的字不动。
3. 转写重试：本次开机记最多 8 条失败过的备忘，第 n 次失败后等 2^(n-1) 分钟（1、2、4…32，之后每次 60），记满替换最早到期的；写库失败、联网时转写失败、调不起 `memo.voice` 记为失败，没联网的失败不记；空文字当作完成；补漏跳过没到期的。**另修**：同一执行器上调能力，回复可能在调用里就回来，原来 `T.busy = ink_cap_call(...) == 0` 会在回复清掉它之后又设回 true，转写完最后一条后本次开机就不再转写；改成调用前设 busy、失败时再清。
4. 后台不同步打开：`mutate`、`play` 改用 `ink_db_open_cached_member`，集合不在内存里时回 FAILED“备忘还没读出来，请先打开备忘再试”（AI 可以先 `app.open` 备忘）；录音结束时 `memo.voice` 没存成就撤下录音页，录音留给补漏；补漏先过一遍记录收集已有录音编号，再和文件比对（整数比较）。没用 `ink_app_db_open_async`（只能在界面任务、要一个页面）；也没在没读出来时顺手发 `data.list`（实验证实那一刻无论谁在后台读这个集合，文件列表都读不完）。
5. `audio.transcribe`：发送循环里加“调用已过期限”（`ink_cap_time_left_ms == 0`）就结束本次转写、清掉占用。
6. `REC.why`：新增 `rec_why()` 在锁里写、已是 cancelled 不覆盖；`rec_finish` 在锁里先拷一份。
7. `via`：在能力表写明不能撤销，不补登记（AI 打开飞行模式时设置在回执之后才写，登记时不知道新版本号；断网后 AI 也没法说撤销；直接调专门能力本来就不能撤销）；`expected_revision` 在转调前核对，不一致回 STALE。
8. `memo.voice`：先判断有没有 `/`。
9. 备份：`mark_failed` 先 `ink_task_end` 再改阶段；存好那条路要在日志写成之后（写不成要退回上传），所以挪到日志写成之后、`acknowledge_manifest` 之前。
10. S31 串口：`S31_LINE_CAP` 512；超长行返回 -2、计数、探针 `uart.overlong_lines`；`hal_uart.h` 说明补 -2。
11. `RECORD` 宏改 `ID_ARGS`。

## 没做到的

低 6、低 9 没有自动测试；正文接近 4 KB 时转写文字永远填不进去（录音和手写的字都在）；从没打开过备忘时，AI 直接调备忘的改动类能力或 `memo.play` 会回“请先打开备忘”，比原来退了一步，是有意的取舍。

## 顺手发现

1. 开机约 2.8 秒（联网触发补漏那一刻）在后台第一次把备忘集合读进内存要 1.27 秒，之后 FileList 一直读不完；在 2.1 秒读就没事（2.4 毫秒）。像是数据存储和文件索引在开机那段时间有冲突，值得单独查。
2. `audit12-m1` 原有的 “then airplane mode is on” 有竞争：等飞行模式变 1 就立刻读 Wi-Fi，这时 Wi-Fi 可能还没关；新增检查因此放在测试末尾，原检查没动。
3. 同一执行器上调能力、回复在调用里就回来，和“先赋值、后调用”的写法冲突；别的服务里可能也有，没有逐个查。
