# voice-stream-1：语音回答在 4G 上不再断续——中枢提前多发、预取下一句，模拟器的随机数按模型分开

总规则先读 `docs/tasks/codex-rules.md`（第 9、10、11 节优先）。

## 为什么

`perf-latency-2`（ai_ask，种子 42）在 20.38 s 断音 45 ms。tap-loss-1 的调查（`docs/tasks/tap-loss-1/REPORT.md`、PLAN.md）查清了：

- 设备的语音抖动缓冲只有约 0.24 s 真余量，加 0.18 s 丢包补偿和约 0.06 s DMA 环，合计不到 0.5 s；中枢按 1 倍速匀速发（`hub/ink_hub/voice/flow.py` 开头先发 5 帧，之后 1 倍速），缓冲永远涨不上去。回答中途下行卡住 0.5 s 以上（这次是一次 TCP 重传，晚了 0.6 s）就一定断。按现在的 LTE 模型，每段回答约一成概率断一次【估算】；真机上机制一样。
- 余量是照几个种子调出来的（3→5→6 帧），不是从“要扛住多长的卡顿”算出来的。
- 看起来像阅读合并带来的回归，其实是模拟器所有模型共用一个随机数生成器（`simulator/runtime/sim_main.c`）：闪存操作次数一变，网络的丢包和延迟整体错开。
- 模拟中枢的发法和真中枢不一样：模拟中枢从第一帧起 1 倍速、各句连着发；真中枢开头多发 5 帧、一句一句依次要 TTS，句子交界有 TTS 首包延迟带来的空档，模拟器测不到。

## 要做的

1. **模拟器的随机数按模型分开**：网络、闪存、触摸、语音前端、电源各用从种子派生的独立随机数流，改一个模型的调用次数不再打乱别的模型。所有依赖种子的结果会整体变一次，全量重跑核对；以前靠某个种子刚好通过的余量重新暴露的，按根因修，不换种子。
2. **中枢提前多发**：发 TTS 时保持约 1～1.5 s 的提前量（开头先多发，之后 1 倍速），设备仍按现在的帧数开播，第一声不变慢，缓冲自己涨到提前量那么深。打断时“用户听到了哪里”改用设备报回的已播放帧数（heard_frames），不再用“已发帧数减 5”估算。
3. **中枢预取下一句**：播当前这句时就去要下一句的 TTS，句子交界不留空档；打断和取消要把预取一起停掉。
4. **模拟中枢照真中枢的节拍发**：同样的提前量和逐句节奏，并给每句加一个可配的 TTS 首包延迟，模拟器才测得到句子交界的断法。
5. **设备端只加指标**：丢包补偿连续 2 帧以上记一次“听得出的补帧”，进预算；抖动缓冲的开播帧数不改（第一声的延迟预算 SR-UX-06b 不能变差）。
6. **测试改成确定的**：脚本加一条“下行卡住 N 毫秒”（或指定第 k 帧重传）的指令；ai_ask 在回答中段注入一次 600 ms 卡顿，断言不断音；随机丢包另做一组 20 个种子的统计，断音次数 0。`perf-latency-2` 不改预算、不换种子就通过。

## 范围和预算

- 只改：`hub/ink_hub/voice/flow.py`、`stream.py` 和中枢测试；`simulator/runtime/` 的随机数、`simulator/environment/sim_hub.c`、`ports/sim/hal/hal_net_sim.c`（卡顿指令）、脚本解析；`system/services/audio/audio_service.c`（只加指标）；`tests/scenarios/`、`tests/perf_latency_2/`；`docs/tasks/voice-stream-1/`。
- 不改：设备的开播帧数、音频驱动和 DMA、屏幕、4G 模组。
- 产品代码（中枢加设备）不超过 150 行，模拟器和测试另计；超了先停下写清原因。
- 中枢在这台 Mac 上跑着（`hub/deploy/start-mac.sh`），改完由主会话重启，代理不要动正在跑的中枢进程。

## 验收

1. `perf-latency-2`、`scenario-ai_ask` 各 profile 通过；注入 600 ms 卡顿不断音（反向对照：去掉提前量，这条要失败）；20 个种子 0 次断音；第一声延迟不比现在差（报告写前后数字）。
2. 中枢测试（`hub/tests`）通过，新加：提前量、预取、打断时停掉预取、heard_frames 的“听到哪里”。
3. 主工程全量 ctest 过；S31 宿主机测试过；`ports/esp32s31/build.sh` 编译通过、无新警告；gcccheck 过。
4. 报告写清：每段回答在 LTE 模型下的断音概率前后对比、真中枢上要核对的事（TTS 出音是不是比实时快）。
