【实测，模拟器】已有索引的一小时里追加 25 次、压缩 0 次；首次建索引的一小时追加 26 次、压缩 1 次。首次追加耗时 4.614 秒，压缩耗时 4.427 秒，两种大写盘都不能被后来到达的等待者打断。单独的竞争实验中，压缩使另一个集合的同步写盘多排队约 4.428 秒。

## 计量

### 方法与一小时脚本

【实现】观察基线完整系统，而非自行重写数据库模型。`tests/index_cost/run.py` 复用 `sim-storage-order` 的编译/链接参数，只在构建目录的存储服务副本插入开始、结束计时，并导出既有 NOR 计数；用测试包装层观察 `ink_db_wait`。产品文件、压缩条件、队列调度、模型参数均未改。计时使用 `osal_now_us`，日志及宿主文件操作走 `vtk_host_call`。每项存储操作均核对成功，每次能力调用均核对回执。

【估算：使用频率假设】这是声明过的代表性脚本，不是用户行为采样。设备保持唤醒，每次操作收尾后再进行下一次；首次操作在第 60 秒，初始化与日常使用分开计量。计时窗口是启动至虚拟时间 3600 秒，种子 1，默认 `metalio-plus`、`tail` 擦写分布，关闭随机断电。

| 时刻（秒） | 实际操作 |
| --- | --- |
| 0～60 | 1000 个 5 B 合成文本文件；冷启动首次建索引，或读取预先建好的同一组索引 |
| 60、120、180、240、300、360 | 各调用一次真实 `camera.photo`，保存 PNG 并取得文件编号 |
| 480、540、600、660、720、780 | 各新建一条备忘并编辑一次；走 `memo.edit`、`text.insert`、`text.submit`，等待草稿及备忘落盘 |
| 1020～1130，每 10 秒 | 各删除一个原有合成文件，共 12 个 |
| 1500、1510 | 模拟拔卡、插回同一张未修改的卡 |
| 2100～2220 | 真实 U 盘借卡接口；模拟电脑覆盖 50 个文件、删 6 个、增 6 个、改名 4 个，再归还 |
| 2700、2760、2820、2880、2940、3000 | 再拍 6 张照片；余时空闲，结束时卡上仍有 1000 个实际文件 |

【实现】当前备忘存于成员集合 `memo.notes`，草稿存于内部数据区，不是卡上的文件；所以保存笔记的索引写入数是 0。没有用“写一个假文件”代替备忘录操作。

【实现＋实测，模拟器】一条 payload 为 216 B，但日志还有 32 B 帧头和 4 B CRC；1000 条首批日志是 252000 B，快照加 32 B 文件头后是 **252032 B（246.125 KiB）**。1024 条上限对应 258080 B，而不是只算 payload 的约 220 KB。未有快照时，252000 B 已超过 8192 B 的压缩下限，首次追加落盘后立刻产生一次同量级重写；已有快照后，阈值为 126016 B，本小时的 18576 B 增量尚未达到它。

### 等待者因此多等了多久

【实测，模拟器】两种一小时脚本各记录 25 次其他集合的持久化等待（`memo.notes`、`confirm.results`），等待区间与索引写盘的重叠均为 **0 ms**；实际存储队列里的其他追加/替换任务也为 0 ms。这个结果依赖上述稀疏、逐项收尾的使用安排，不能推成“压缩不会阻塞用户”。

另做一对独立的受控实验：预先打开合成集合；在索引快照已经被存储任务取走时发出 5 B payload、41 B 帧的同步写盘。没有卡住线程或修改调度器。空卡对照提交相同内容，确认没有索引阻塞。

| 观察项 | 压缩中提交 | 无索引大写盘对照 |
| --- | ---: | ---: |
| 索引压缩时长 | 4428.007 | 0 |
| 同步写盘排队时间 | 4428.110 | 0.161 |
| 其中直接与索引写盘重叠 | **4427.878** | **0** |
| 同步任务自身写盘 | 3.437 | 2.784 |
| `ink_db_wait` 总耗时 | 4442.595 | 16.742 |

同步等待与索引写盘重叠 4427.902 ms；以实际队列重叠 4427.878 ms 归因“多等”，避免把自身写盘及 10 ms 完成轮询计进去。两个环境的 Flash 分配和随机抽样序列不同，总耗时之差 4425.853 ms 只是辅助对照，不能当成严格同状态反事实。存储服务的等待者优先只作用于**下一项**任务；正在执行的快照和首批大追加都不可中断。

### 真机估算及边界

下表前两列是【实测，模拟器】的模型敏感性试验，最后一列才是【估算】；没有访问设备。分别把 Flash 抽样切成 `typ`、`max`，其他产品实现不变。

| 操作 | 模型 `typ` | 模型 `max` | 真机条件估算 |
| --- | ---: | ---: | --- |
| 首次追加 252000 B | 3826.615 ms | 17483.927 ms | 约 3.8～17.5 s |
| 压缩快照 252032 B | 3832.016 ms | 17490.249 ms | 约 3.8～17.5 s |
| 两次合计 | 7658.631 ms | 34974.176 ms | 约 7.7～35.0 s |

依据：本次单个快照实测 62 次扇区擦除、252928 B 编程；按已有 [硬件资料](../../hardware/2026-11-03-phase0.md) §3 的 Puya PY25Q128HA 数据手册 Ver0.3（原查阅 2026-11-03，本次复核 2026-11-10），4 KiB 擦除典型/最大 50/240 ms，256 B 编程 0.5/2.4 ms。纯擦写约 `62×50ms + 252928/256×0.5ms = 3.594s` 至 `62×240ms + 252928/256×2.4ms = 17.251s`，再加模型中的读取、命令及 CPU 开销约 0.24 s，得到上述量级。

成立条件：目标仍用同款 Flash、LittleFS 相同分配及参数、无自动挂起、写盘顺序类似。`tail` 是模拟器自定义抽样，**不是设备实测分布**；`max` 也不是系统时延上界或置信区间。真实占用、碎片、驱动和电压温度都可能改变结果；[S31 端口](../../../ports/esp32s31/README.md)的存储 HAL 尚未接入，不能承诺真机会落在这个区间。若请求刚好遇到正在开始的完整重写，可因此等待同量级时间。

## 方案对比

以下改动量、收益均为【估算】，不是已实现或跑分结果；行数指产品 C/H 的变动量，不含测试、文档。

| 方案 | 预计改动量 | 收益 | 风险、限制 |
| --- | --- | --- | --- |
| A：索引与完成记录移到卡上 | 约 350～600 行；文件、数据、存储服务及接口/路径定义 | 索引不再占内部 Flash，不再制造这些 NOR 停顿；可让同卡携带索引 | FAT 的断电提交不能直接照搬 LittleFS 假设；共享存储任务仍会被 SD 写入占用。各卡独立从编号 1 开始会破坏换卡后旧编号语义，须一起解决编号、成员映射和迁移，不能只换路径 |
| **B：按实际字节长度保存路径（推荐）** | **约 120～180 行，集中在 `file_service.c`** | 本例每条帧可由 252 B 缩至约 92 B，1000 条快照约 92032 B，减少约 63.5%；快照缓冲和记录占用也下降 | 需 schema 3 编解码及旧记录兼容；最长路径收益小，仍不能保证同步等待低于 250 ms；小追加的 LittleFS 尾块重写仍在 |
| C：只提高该集合压缩下限/比例 | 约 5～15 行，集中在数据层压缩条件 | 可减少或推迟快照次数，改动最小 | 不缩短已经开始的一次重写；增大日志、重启回放与空间压力。256 KiB 下限只比初始日志多约 10 KB，可能把本次启动的压缩挪到电脑归还时；全局改阈值还会影响其他集合 |
| D：将日志追加及快照都分段写入，段间让同步写盘插队 | 约 180～300 行，数据/存储服务 | 若每段 8～16 KiB，可将整次独占约 4.4 s 降成一段量级 | 要保持临时文件、代际、借用缓冲及最终原子替换的断电一致性；只切快照仍留着首批 252 KB 追加的 4.6 s 阻塞。多次提交可能增加尾块擦写，需重做故障注入验证 |

推荐 B 的理由：本小时热路径没有压缩，主问题是冷建索引有“整批追加＋整批快照”两次固定大写盘。变长记录同时缩短两者，保留现有两代日志、存储队列、文件编号及成员鉴权，不引入卡级数据域或分段提交状态。方案 C 主要挪动发生时间；A、D 的一致性及接口风险明显更大。如果目标是完全避免索引触发内部 Flash 停顿，须另选 A；B 无法满足这个更强目标。

- 【实测，模拟器＋实现】两次小时脚本最后均为卡上 1000 个文件、数据库 **1010 条**。电脑删除 6 个、改名 4 个后，扫描未清除消失记录；原文件元数据相同，改名匹配又有歧义。这会消耗 1024 条上限，本报告未清掉记录来美化写入量。证据是 `summary.json` 的 `physical_files` / `final_index_records`；代码在 `index_walk_load`、`index_renamed`、`index_walk_step`，本任务不修。

- 首轮全量 283 项通过、3 项因缺中枢 Python 依赖而明确跳过；随后用既有依赖环境重跑，最终 286 项全过、无跳过，没有安装或升级依赖。
