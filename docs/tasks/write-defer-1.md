# write-defer-1：打字时不再丢键——擦闪存的写入避开正在打字的那几秒

总规则先读 `docs/tasks/codex-rules.md`（第 9、10、11 节优先）。

## 为什么

voice-stream-1 把模拟器的随机数按模型分开以后，`autotest-cap` 的备忘打字一段每次都丢键：按每秒一下的节奏退格 5 次，第 1、2 次丢了（`docs/tasks/voice-stream-1/REPORT.md` 复核修复的“没修的”）。

- 19.000 s 手指按下；19.010 s 一次前台写入（备忘草稿日志，从 12.14 s 排到现在）开始，写了 297 ms，其中一次闪存擦除让两个核都停住 236 ms。触摸芯片 19.020 s 拉中断，驱动 19.236 s 才醒来读，手指 19.080 s 已经抬起，这一下丢了。
- 丢了一下以后，系统以为没人在操作，19.97～20.29 s 又跑了一次后台写，20.0 s 那下也丢了。
- 现在的规则（tap-loss-1）：前台写只躲“手指正按着”，后台写只躲点按后 300 ms 和上次操作后 500 ms。按正常速度打字时，两下之间的空档里仍会开始一次可能擦除的写入，下一下就落进擦除里。tap-loss-1 已经查清：擦除时两个核都停、I2C 锁也被拿着，整下落进去的点按救不回来（`docs/tasks/tap-loss-1/REPORT.md`）。

打字丢键很伤体验，用户按正常速度写备忘、发短信、输入搜索词时都会碰上。

## 要做的

1. 先量清楚：哪些写入会擦闪存（LittleFS 换新块、整理等），各自多久；打字时这些写入是从哪里来的（草稿、日志、索引、成员表……）。
2. 按根因修，一处修一类：有输入以后的一小段时间（按打字节奏定，比如 2～3 秒，写清依据）内，不开始可能擦除的写入，等过了才写；等太久（写清上限和理由）才放行，保证数据不会一直不落盘。能区分“只编程、不擦除”的快写入就别拦它。如果在空闲时预先擦好空块更简单、更彻底（之后的写入只编程、不停核），也可以，比较两种做法后选一种，写清理由。
3. 写清数据安全：推迟期间断电，最多丢几秒的草稿；不能丢已经确认保存的东西。
4. 测试：`autotest-cap` 不改时间就通过；新场景按每秒 1 下和 3 下各打 20 个键，写草稿和日志照常发生，每个键都送到、只送一次；断电场景证明最多丢规定秒数的草稿。反向对照：去掉推迟，打字场景要丢键。

## 范围和预算

- 只改：存储写入的调度（存储服务、它的 HAL 和模拟器模型里和调度有关的部分）、相关测试、`docs/tasks/write-defer-1/`。
- 不改：闪存驱动的挂起支持（要真机证据）、分区、屏幕、4G。
- 产品代码不超过 150 行；超了先停下写清原因。
