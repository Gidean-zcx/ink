# 输入法：先分清引擎、词库和键盘

**结论【估算】：按已核实功能，libime 与 librime 属于第一档；优先把 Google/AOSP 拼音完整解码核心作为设备端验证对象，键盘行为以 fcitx5-android 为底、补 Trime 的分类符号和 Mogo 的九键交互。** 这个设备端推荐有条件：整句质量、九键解码、成员词库、S31 内存和剩余程序空间都要过验证。不能把它写成“已能移植”。Mogo/kiikoread 是现成的嵌入式组词来源，成熟度仍受静态小词表限制；口袋不适合作为完整中文输入法的引擎底子。

本次没有输入正确率、候选命中率或真屏体验对比。以下排名是根据功能覆盖和工作流作出的建议，不是性能跑分；“未找到”仅指 [SOURCES](SOURCES.md) 所列固定版本和路径。默认离线引擎与可选中枢辅助分开，不能用远端结果冒充设备端整句能力。

## 引擎排名

“接续”指已经选出汉字之后的下一词预测；“组句”指仍在输入拼音时组合多个词。只在词库里收了一条长词，不能算自动组句。

| 暂定序 | 引擎与证据 | 组句、词组与接续【实现】 | 九键与简拼【实现】 | 学习与中英输入【实现】 |
| --- | --- | --- | --- | --- |
| 1 | **libime**，[I08](SOURCES.md#i08-libimefcitx-拼音核心)；fcitx5-android 默认拼音的核心，[I07](SOURCES.md#i07-fcitx5-android-前端和引擎归属) | 句子候选、词组、上下文预测都有独立接口；词典与语言模型分开 | 有不完整音节配置；所查核心和官方 Android 前端没有找到可交付的中文九键工作流，不能从 `keyboard_t9_ids.xml` 推定已有 | `PinyinContext::learn` 学词和历史；英文需前端及 spell 等附加模块，不能把整个框架的功能算成单个库的功能 |
| 2 | **librime + 明月拼音/简体拼音数据**，[I03](SOURCES.md#i03-librime)、[I04](SOURCES.md#i04-rime-明月拼音数据和方案)、[I12](SOURCES.md#i12-固件口袋-plus-源码包) | 词图组句、用户词典；默认明月方案的流水线没有独立下一词预测器，若要接续需核对扩展方案/插件 | 明月有简拼补丁；默认字母表不接数字，九键要配解码方案，换九个按钮不够 | 提交学习；有 ASCII 分段/切换，但默认方案不等于自动英文词预测。词库、规则、插件会改变体验 |
| 3 | **libpinyin**，[I05](SOURCES.md#i05-libpinyin) | `guess_sentence`、按前文预测及训练 API 齐全 | 支持 `PINYIN_INCOMPLETE`；所查代码未找到完整九键前端/解码合同 | 有训练和保存用户学习信息；中英混输还要输入法前端，不是库本身已提供完整手机键盘 |
| 4 | **SunPinyin**，[I06](SOURCES.md#i06-sunpinyin) | 二元/三元统计模型、整句候选、用户历史；未核实选字后的下一词接续 | 有声母/不完整音节处理；九键未核实 | SQLite 用户词库及历史权重；未核实中文组合串中的英文候选混排 |
| 5 | **Google/AOSP PinyinIME C++ 核心**，[I01](SOURCES.md#i01-aosp-拼音lineage-保留分支)、[I02](SOURCES.md#i02-qt-virtual-keyboard-的-google-拼音派生版本) | 首项整句、分步选词、预测、用户词典更新；明显胜过只查固定词条 | 有声母/首字母开关；API 输入是拼音字母，没有已核实的数字九键解码器 | 有词频及用户词学习；英文由 AOSP 前端另管，是模式切换，不能声称与现代商业 Google 拼音/Gboard 等价 |
| 6 并列 | **Mogo、kiikoread**，[I10](SOURCES.md#i10-mogo-e4p-输入法)、[I11](SOURCES.md#i11-kiikoread-输入法) | 有界动态规划组词、词组候选、按已提交文本后缀接短语；固定词表各 **487 条**，不是统计语言模型 | 九键数字映射、拼音读音选择；未发现独立首字母简拼索引 | 未发现持久用户学习；中文/英文模式切换。两份短语表字节相同、核心高度同源，不算两种独立技术路线 |
| 7 | **ink 当前**，[I13](SOURCES.md#i13-ink-基线现状) | 最长前缀查词，有词组；没有跨词自动切分组句。AI 接话是另一条需联网的路径 | 全键/九键都有；词库生成器也生成每个词的首字母键，**已有简拼** | 已有按成员、按“消耗拼音+词”学习的重排；并非新词组句学习。英文显式切换，非自动混输 |
| 8 | **固件口袋 Plus**，[I12](SOURCES.md#i12-固件口袋-plus-源码包) | 精确单音节查表，逐个单字候选；输入最多 6 字母。**使用 Rime 数据不等于运行 librime** | 未发现拼音九键或首字母词组简拼 | 未发现用户词频学习；中文/英文、大小写、数字符号模式齐全，适合短输入框 |

libime 排在前面，依据是本次确认了组句、接续、学习和移动前端的成套接口；Rime 的可配置性更强，默认方案的接续覆盖却不能一概而论。两者的真实中文质量要用同一语料再比较，不能凭仓库名断言谁更准确。

## 词库、内存与 ESP32 证据

| 对象 | 本次拿到的量或边界 | 对目标设备的含义 |
| --- | --- | --- |
| Google | 【实测】随包 `dict_pinyin.dat` **1,068,442 B**，Qt 与 AOSP 的该文件 Git blob 相同；SHA-256 见 [复核记录](EVIDENCE.md)。原始词源文件 3,570,346 B；名称含 65105，不把文件名当本次词条计数 | 词库本身已大于约 400 KB 程序余量，应放数据资源/卡；解码器仍会分配词典、搜索和用户词缓冲。**文件大小不是运行 RAM**。无本次 S31 验证 |
| librime / 明月 | 【实测】明月 `.dict.yaml` **889,896 B**；【实现】还用预设词汇，运行时另有编译后的字典、用户库和依赖，见 I03/I04 | 不能用这一个文本文件估算整个 Rime 小于 1 MB；依赖需裁剪/适配，峰值内存、程序大小未知。未查到可核实的 ESP32 原生整套运行证据 |
| libime | 【实现】固定版下载 `dict-20260907.tar.zst` 和 `lm_sc.arpa-20260629.tar.zst`，并生成词典、语言模型及预测文件，URL/哈希在 I08 | 本次未下载大语料、未生成二进制模型，故最终大小和 RAM **不确定**；不能用源码包或压缩包大小冒充运行占用。未核实 ESP32 端移植 |
| libpinyin / SunPinyin | 【实现】前者独立生成字符/拼音索引及 bigram 数据并依赖 GLib/数据库；后者用统计模型、SQLite、mmap 相关接口，见 I05/I06 | 无本次资源实测，没有证据支持“默认就装得进 16 MB PSRAM”。也没有证据证明裁剪后一定不可行；未核实 ESP32 原生运行 |
| Mogo / kiikoread | 【实测】短语头文件均 **13,842 B、487 条**。需要借原应用的单字查找接口。见 I10/I11 | 【估算】假设 RV32、4 字节对齐，48 字母的路径工作区连同最多 512 个音节缓存约 **15.2 KB**，24 候选约 **3.7 KB**；不含字表、字体、UI、文件扫描临时内存和分配器。是资源边界推算，不是实机峰值 |
| 口袋 | 【实测】源码包内 Rime 源数据 **1,266,216 B**；生成头 **20,685 B**；【实现】生成记录为 402 音节、4,262 个不同单字、带 NUL 的字符串合计 15,348 B | 是裁剪后的单字码表，不是 1.26 MB 完整词库常驻设备。上游生成记录明确 `hardware_verification: pending`，不能写成 Plus 输入法已实测 |
| ink 当前 | 【实现】词库上限 **1 MiB**；卡上加载到 PSRAM，资源包可只读映射；60 个候选、每页 6 个；学习载荷上限 512×4 B。见 I13 | 有基线代码，不代表本任务重测过目标硬件。现有词典规模通常大于 Mogo 静态短语，但没有其组句能力；不应把升级简单等同于更换词表 |

对“有人在 ESP32 上跑过”的证据等级：Mogo、kiikoread、口袋有面向 ESP32/Plus 的实际源码和分配接口，属于【实现】；本轮没有运行它们，也没有据此声称实机成功。对 Google、Rime、libime、libpinyin、SunPinyin，公开检索未获得足以验证的 S31/ESP32 成套运行记录，记为**不确定**，不是断言从无人移植。检索词和范围见 [EVIDENCE](EVIDENCE.md)。

本次 Google 原始核心在 Mac 上编译成功但加载随包词库失败（`SIGABRT`、`std::bad_alloc`）。已核对到 32/64 位 `size_t` 词库读法差异；没有继续修改上游让探针过关，没有得到可信的运行 RAM/中文候选结果。Qt 版本仍有 `QFile`/`Qt::Core` 依赖，**不能原样带整个 Qt 到设备**。详情与复现命令见 [EVIDENCE](EVIDENCE.md)。

## 推荐的嫁接范围

1. **完整搬代码的优先对象**：Google 的解码核心、系统词典加载/搜索/选词/预测/用户词典这一组功能，保持一组来源，不自己重写半套概率解码器。先解决固定宽度数据格式、POSIX 存储/锁与 OSAL/HAL 对接，验证通过再接 UI。Mogo 的九键候选/读音过滤可作独立替代来源，但不是套在 Google 外面枚举所有字母组合就能保证整句性能。
2. **只能翻译的完整前端**：fcitx5-android 的键盘/候选/符号页，补 Trime 分类符号和 Mogo 九键交互；它们分别依赖 Android 或自有绘制层，没有一套已核实的 LVGL 完整替代品。
3. **保留 ink 的合同**：`text.*` 输入会话、`keyboard.*`、剪贴板、语音和 AI 接话、成员隔离与密码禁止学习/外发。只换解码后端，不能改成 UI 直接写服务状态。[接入表](PORTING.md)

**不确定时的保守结果**：保留当前可用实现；Google 作为首个验证候选，Mogo/kiikoread 作为有界离线组词的对照，Rime/libime 作为成熟能力标杆和可选中枢端候选。这里没有决定把输入引擎永久放服务器，也没有决定放弃九键、学习或中英混输。
