# 通知栏和控制中心

**结论【估算】：以 AOSP SystemUI 的通知和快捷控制行为作完整底子；代码复用优先取 PebbleOS 的通知动作与勿扰规则、ESP-Brookesia 旧版的壳层控件，低刷新交互以 MuditaOS 和 LilyPhone 校准。** 未找到一套已经核实、同时具备手机级分组/操作/例外且可直接链接到本项目 LVGL 9 的完整通知中心。不能因此退回只做状态图标，也不能声称已经完成完整移植。

排序看用户能否辨认通知对象、处理通知、理解勿扰例外及看到开关真实状态；不是按语言或移植工时排序。所有体验判断都是【估算】，没有本次真屏试用。

## 哪些值得整块搬

| 来源 | 建议的最小完整复用单元【估算】 | 不能一并搬的部分 |
| --- | --- | --- |
| AOSP SystemUI | 分组列表、展开详情、动作和直接回复的完整工作流，按页面和状态逐项翻译成 LVGL；把“通知内容”和“可执行动作/执行结果”分开 | Java/Kotlin、Binder、SystemServer、RemoteViews 不是 MCU 可链接的系统框架。不能只拷 `NotificationContentView` 就称获得直接回复能力 |
| PebbleOS | 通知动作菜单/回复选择、成功失败反馈这一组行为；跨日勿扰时段和允许来电规则，可提取成独立代码单元作对照验证 | Timeline 存储、手机传输、Pebble UI、cron/线程不能再建一套。需接现有通知/时间/通信服务；不能整目录复制后悄悄引入后台任务 |
| ESP-Brookesia v0.4.2 | 状态栏图标、返回/主页/最近任务导航控件各自完整一块，若确有功能提升再移 | 不带其系统 Core、应用生命周期、截图缓冲和原 LVGL 版本；当前本项目已有这些职责。只为了换外观而平行建立系统框架没有收益 |
| ZSWatch | 回复弹层从草稿到真实结果的展示逻辑；尤其区分转写失败与发送失败 | 不带手机协议、转写服务、150 ms UI 定时器和重试语义；用户要求的发送走我们同一条能力路径 |
| MuditaOS / LilyPhone / InfiniTime | 单色列表当前值、模式说明、可点的大开关与明确返回；LilyPhone/InfiniTime 的 LVGL 局部视图可拆出来适配 | 不带硬件驱动和原来的刷新时序，不拿手表/按键交互尺寸直接套目标触屏 |

这是一份可复用单元清单，**不是这些片段已经完成跨平台解耦的证明**。如果提取后仍依赖一整套上游系统服务，保留原文件作为行为参照，按整条工作流翻译，不伪造“只包一层即可运行”。

## 在墨水屏上保住体验

以下是建议，不是擅自改合同：[本项目刷新与输入规则](../../product/system-ui-spec.md)、[R-061 接入约束](PORTING.md)。

- 通知首屏先让人识别来源、对象、时间、未读与可做动作。分组展开时用稳定对象标识；新通知到达不把手指下的旧通知换成另一个对象。
- 控制区开关同时显示名称和当前值。连接中、正在关闭、受成员策略限制与失败要有不同反馈；“请求受理”不能显示成已经成功。
- 下拉进入后静态显示，提供可点的收起/分页；拖动仅更新必要区域，抬手后的精刷仍交统一显示服务，不能另做每 N 次强制全刷机制。
- 亮度指设备前光，不照抄 OLED 背景亮度或 LilyPhone 键盘背光。滑条要有可点的确定档位/数值反馈；频率与触感需要目标硬件验证，本报告不自定毫秒参数。
- 快捷回复、清除、勿扰设置都经能力与策略执行。普通用户主动动作不额外加确认；不可恢复删除、身份权限或非用户主动对外动作仍遵守既有确认规则。
