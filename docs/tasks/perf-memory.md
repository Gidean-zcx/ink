# perf-memory：内部 RAM 和 PSRAM，找最大的几项，有实测收益才改

总规则先读 docs/tasks/codex-rules.md，第 7 节优先；docs/tasks/backlog.md 的 perf-memory 一节是原始要求。报告写到 docs/tasks/perf-memory/REPORT.md。

## 要做的

预算：产品代码改动不超过 200 行（增删合计）。完成标准 R-068 里有“性能流畅、硬件充分合理应用”；内部 RAM 是真机上最紧的资源（实时路径、DMA、栈都要它）。

1. 先量：跑全部场景，列出内部 RAM 最低余量最小的 5 个场景，以及内部 RAM、PSRAM 的前 15 个占用（静态和堆分开；模拟器的标签计数 `ink_mem_budget`/`osal_mem_tag`、各任务栈）。再参照端口骨架给的 S31 静态尺寸（docs/tasks/port-skeleton/REPORT.md 若已合入，否则用 `ports/esp32s31` 的 `idf.py size` 结果）。
2. 再改：只挑前几项里有明确收益、改动小的：例如把只在后台用的大缓冲移到 PSRAM、把每次调用都在栈上开的大结构改成按需分配、去掉重复的缓存。每一项都要前后对比。
3. 栈：审计说模拟器估算里 `esp_timer`（3552/3584）、`main`（3952/4096）、`exec.media`（7552/8192）接近上限（docs/audits/batch4/report.md“待证实”一节）。对照 S31 的 `-fstack-usage` 结果判断哪些是主机估算偏大、哪些是真要加；能降的降（例如存储任务 4096），要加的说清依据。不要只靠调高预算来“通过”。

## 边界

- 行为不变：全量测试、确定性测试都过；不放宽任何预算。
- 没有收益的尝试写进报告，不留改动。
- 同时在做的有 perf-latency（时延）；两边都可能动同一个文件，只改各自那几处，报告里列清。

## 验收

1. 报告里有前后对比表：各场景内部 RAM 最低余量、PSRAM 峰值、改动的每一项各省多少【实测，模拟器】。
2. 至少把内部 RAM 最紧的场景的最低余量提高 2 KB，或者说清楚为什么做不到（附数据）。
3. 栈的结论表：任务、配置、主机估算、S31 估算、结论（降、保持、加）和依据。
4. 全量测试和内存检查通过；产品代码改动不超过 200 行。
