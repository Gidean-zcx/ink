【实现】后台批次及文件编辑的索引更新只提交既有数据库写入；扫描结束后确认索引版本已持久化，才保存完成标记。两个既有索引集合在启动阶段加载，避免 BG 在 UI 已运行时等待冷数据。没有新增落盘队列或重试机制。

【实测】原五项回归已定位到的原因及处理：

- `integration-races`：执行轨迹中的删除作业在 `index_save` 同步等待落盘 3.015 秒；取消这处同步等待。新增存储写入挂起测试，恢复后台同步等待后，其他 BG 工作超过原 500 ms 断言。
- `confirm-durable`：已换成员的确认请求先写 running、等落盘或排回 UI，状态查询时仍为 unknown。BG 入口先终止已换成员的请求，保留提交后的身份、时效校验；原容量场景的 2000 秒窗口、断言均保留。
- 中枢端到端、阅读时延及页面版本场景：创建卡身份推进了模拟硬件时序／故障的随机序列。卡身份生成移到存储 HAL，模拟端仅为此用途使用种子和虚拟时刻驱动的私有随机状态；通用随机接口沿用原实现，不读取宿主时间。新增直接检查模型随机序列未被推进的测试，恢复共用取数后失败。
- 索引作业已经结束但清理回调尚未完成时，编号查询原先仍返回 busy；只在作业实际运行时拒绝查询。原文件索引回归中的“后台删除后旧编号立即失效”断言保留。
