# boot-db-stall：开机时在后台读数据集合，文件列表就读不完

总规则先读 docs/tasks/codex-rules.md，第 7、8 节优先。报告写到 docs/tasks/boot-db-stall/REPORT.md。

## 现象

memo-record 和 audit13-fix 两次查到同一个问题（见 `docs/tasks/memo-record/REPORT.md` 顺手发现 1、`docs/tasks/audit13-fix/REPORT.md` 顺手发现 1）：开机约 2.8 秒（联网、触发备忘补漏的那一刻），在后台执行器上第一次把备忘集合读进内存要 1.27 秒，之后“文件”页的文件列表一直读不完（`files-app` 测试 `page FileList has finished reading` 失败）；同样的读在 2.1 秒做就没事（2.4 毫秒）。为了绕开它，audit13-fix 让备忘的改动类能力和 `memo.play` 在集合没读进内存时回“备忘还没读出来，请先打开备忘再试”，AI 要先打开备忘才能记，这是退步。

## 要做的

预算：产品代码改动不超过 150 行。

1. 用时间线（事件和时刻）查清根因：开机那段时间数据存储、文件索引（后台建索引、落盘、压缩）、存储服务的写盘队列之间是怎么卡住的，为什么之后文件列表永远读不完（而不只是晚一点）。可以在 `files-app` 测试里复现（audit13-fix 加的“联网触发补漏的同一时刻在后台调 `memo.play`、`memo.delete`”就能稳定触发，前提是把那两处改回同步打开）。
2. 修根因，让“在后台执行器上第一次打开一个成员的数据集合”在任何时刻都不会让别的作业永远等下去（可以慢，但要能完成）。
3. 根因修好后，去掉 audit13-fix 加的限制：备忘的改动类能力和 `memo.play` 在集合没读进内存时照常打开并完成（AI 不用先打开备忘）。
4. 如果根因是一个通用的问题（别的服务在后台第一次打开集合也会碰到），在报告里列出受影响的地方。

## 验收

1. 测试：开机那一刻在后台第一次打开备忘集合，文件列表照样读完，备忘写入成功；AI 在从没打开过备忘时直接记一条备忘，成功。撤掉修复后测试失败。
2. 原有 files-app、memo、memo-record、文件索引系列测试原样通过；全量测试和内存检查通过；S31 能编过。
3. 报告有时间线、根因、修法，以及去掉限制的说明。
