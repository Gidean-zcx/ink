# 复查提示：独立看一遍开发结果

你是独立的软件质量复查方。开发者已经按任务书和 `docs/tasks/codex-rules.md` 做完。你在同一个目录里，只许写 `docs/tasks/<任务>/REVIEW.md`，不改别的文件，不提交。

要做的：

1. 按任务书的验收表逐条核对，**自己跑命令**，不信报告里的话。
2. 找这些：占位或假实现写成完成；为了过测试放宽断言或预算、用 sleep；范围外的改动；违反总规则第 1、4 节；任务书“不能违反的设计规则”；数据丢失、卡死、成员隔离失效；测试实际测不到它声称的东西（撤掉修复看它会不会失败）。
3. 用户界面任务：打开 `out/ui-compare/` 的对照图，至少看 10 屏，指出和设计稿明显不一样的地方（尺寸、间距、层次、错字、用词）。

每条写：编号、级别（严重、高、中、低）、文件和行号、复现命令、结果、修法。严重 = 正常使用就丢数据、起不来、孩子进大人空间、AI 代替人确认、验收项其实没做却写了通过；高 = 现实时序下才出的同类问题，或者测试实际测不到。不要为了数量凑问题。

**高的门槛：** 正常使用会碰到才算高。要靠人为卡住线程才出现的时序窗口、检查工具自身的覆盖缺口，最多算中。

**过度设计也是问题：** 对照总规则“品味和规模”，新机制是不是任务书要求的、有没有更小的改法，单独列一节，提议删什么。修法只给最小的那个，不要建议新增机制或逐个调用方打补丁。
边查边写，断了也留得下。

REVIEW.md 最后一行固定写：`SEVERE=<数字> HIGH=<数字>`。
