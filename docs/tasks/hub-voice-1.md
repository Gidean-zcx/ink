# hub-voice-1：把小智服务端的语音核心整块搬进中枢——流式识别、语音检测、流式朗读、打断，做到极低延迟

总规则先读 `docs/tasks/codex-rules.md`（第 9、10 节优先）。

## 为什么

用户 2026-11-12：“中枢架构之前说是要参考移植小智哦 需要极低延时恢复和打断等操作”。之前的设计是 D-76（中枢自己写一条可取消的语音链，厂商接法借小智服务端）和 `docs/hub/hub-architecture.md` 的时延预算（第一句文字 ≤ 3 秒、第一个音 ≤ 4 秒；打断时设备本机先停播、发 `rt.close`，中枢立刻取消）。今天接上的语音（`hub-real-1`）是临时的：整句说完才用 `whisper-cli` 识别、每次重新加载模型；朗读用 `say` 一句一句合成。用户要的是小智那样的低延迟和打断。按用户的整体方向（D-129：成熟的实现整块搬，不自己重新设计），这次把小智服务端的语音流水线核心搬进来。

## 来源

- 小智服务端：`https://github.com/xinnan-tech/xiaozhi-esp32-server`（MIT，Python 部分在 `main/xiaozhi-server`）。只读克隆到本任务的 `work/`，在报告里写固定提交。重点看：连接和会话处理、`core/handle` 下接收音频、发送音频、中止（abort）的处理，`core/providers` 下的 VAD（Silero）、ASR（本地 FunASR/SenseVoice/sherpa-onnx，云端豆包和阿里的流式接口）、TTS（流式接口）的适配写法，断句和朗读队列。
- 我们的协议和中枢：`docs/hub/device-protocol.md`、`docs/hub/hub-architecture.md` 第 5.3 节、`hub/ink_hub/voice/flow.py`、`hub/ink_hub/speech/`、`hub/ink_hub/gateway/server.py`。

## 要做的

1. **搬流水线核心**：把小智的语音检测、流式识别、断句、流式朗读、中止这几块的逻辑搬进 `hub/ink_hub/voice/`（照它的结构，改成我们的协议消息 `ai.listen`、`rt.*`、`ai.delta`、朗读帧；成员、策略、额度、孩子的内容检查照现有的走）。不另起一套连接或会话管理。
2. **识别常驻、流式**：识别模型常驻内存，不再每次起进程；有中间结果就按设备的 `interim_ms` 节流发；语音检测判定说完就立刻定稿。厂商接口照小智每家一个适配文件：保留现在的 Whisper（改成常驻，例如 whisper.cpp 自带的服务端程序或进程内调用），加一个本地流式适配（SenseVoice 或 paraformer 流式，经 sherpa-onnx 或 FunASR），加豆包和阿里的流式识别适配（只用本机假服务器测）。
3. **朗读流式**：第一句按逗号就切（至少 8 个字），一句一句送朗读，首包一到就发；保留 `say`，加豆包和阿里的流式朗读适配（只用假服务器测）。
4. **打断**：设备发中止（按键或开口）后，中枢在 100 毫秒内取消识别、模型和朗读，不再发任何朗读帧；对话历史截到用户实际听到的地方（按已发帧数估算，和设计文档一致）。照小智的中止处理写。
5. **量时延**：每一段都打时间戳（说完、识别定稿、模型首个字、首句凑齐、第一帧朗读发出）；写一个本机基准：用 `say` 生成几句中文录音当设备上行，跑完整流程，给出从“说完”到“第一句文字”“第一帧朗读”的 p50/p95，分本地和假云端两组。本机已有的 Whisper 程序和模型在 `work/whisper.cpp/`（主仓库的忽略目录，用户刚装好），能用就用来量真实数字。
6. **设备端的回声消除（只调研，不改设备）**：写清小智设备固件在 ESP32 上怎么做“边播边听”的回声消除（乐鑫 AFE），原厂这台设备的固件（`$INK_DEPS/../ink-hw/upstream/` 里原厂代码，小智系）有没有、BH1098 能不能给回采信号，我们要接需要做什么。
