## SC-H1（高）：80 ms 的翻页短按被吞掉，`scenario-ai_page_version-metalio-plus` 失败

你的报告已经定位到：19.5 秒那次 80 ms 的翻页键，加了本任务的改动后，第一次读触摸芯片（I2C）晚到 19.5817 秒，而键在 19.580 秒已经松开，于是漏掉；只把 `clock.c` 换回基线就好。真实用户也会碰到这种情况（短按被吞），所以不能改场景、拉长按键、加等待或放宽预算。

要做的：

1. 查清 `clock.c` 的哪一处把输入读取推迟了（例如倒计时或闹钟页的刷新定时、页面创建时的额外工作、按秒或按分钟的唤醒），以及按键提示音是否在输入路径上占用了 I2C、音频任务或界面任务。
2. 改成不影响输入：刷新不在没有倒计时运行时进行；运行时按分钟更新，不在输入到来时抢占输入读取；提示音在输入事件处理完之后再发，输入任务不等音频。
3. `scenario-ai_page_version-metalio-plus` 按原样通过；普通和 ASan/UBSan 两套全量都过（能力表文档除外）。报告写清原因和前后计量（送达次数、首次读取时刻）。

## 主会话复核第二轮（2026-11-10，05:00）

SC-H2 已修，合入。原因：模拟器里启动控制固定在 0 号核，提高优先级后的输入任务可以跑在任一个核上，打乱了交接顺序。确认回执唤醒启动任务时，0 号核正在画确认卡，确认的写盘被排到一次刷屏之后，又等了 2.6 秒。现在把输入任务也固定到 0 号核（3 行），另一个核可以并行画界面。夹具确认回到 2.4 秒，80 ms 短按仍然不丢；hub 端到端测试加了“家人就绪早于 3 秒”的断言，以后再变慢会直接报出来。合到最新主线后全量 284 项通过。

留给真机的：输入任务现在是最高优先级、固定在 0 号核，屏幕送数据任务降了一级。真机上要确认刷新时有输入不会让屏幕出瑕疵，以及 0 号核上 Wi-Fi 等任务不受影响。
