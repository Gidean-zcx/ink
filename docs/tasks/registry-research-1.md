# registry-research-1：CloudZao 固件仓库里的固件和社区移植，能复用什么、该补什么、该参考什么

总规则先读 docs/tasks/codex-rules.md，第 7、8 节优先。报告写到 docs/tasks/registry-research-1/REPORT.md。**这是调研任务，不改产品代码、不碰设备。**

## 背景

用户 2026-11-11：“https://burner.cloudzao.com/zh/registry 找这里面设备的固件功能，已经可能某些项目就是社区移植，梳理哪些可能是我们应该可以使用和复用的，哪些功能是应该补齐的，哪些设计是应该参考的，进一步完善我们的系统。”

主会话先看过一眼（【实测】静态抓取，2026-11-11）：

- 页面标题“固件仓库 · CloudZao Burner”，是原厂网页烧录工具的固件仓库。
- 板卡条上有四块：Metalio E-Ink4 Plus（esp32s31，“官方”，就是我们的设备）、Metalio E-Ink4（esp32s3）、Metalio Claw4（esp32p4）、Metalio 1.54（esp32s3）。
- 筛选项有“精选 / 官方 / 社区 / 全部”。静态内容里 Plus 显示“官方 0 · 社区 0”“没有匹配的固件”。固件列表是页面脚本加载的，静态 HTML 里看不到。
- 导航还有：OTA 接口文档、书籍工具、串口调试日志、云造云（yun.cloudzao.com）。

我们这边已有的对照材料：

- `docs/tasks/vendor-feature-audit/REPORT.md`：原厂固件功能盘点，以及 2026-11-11 下午的逐行复查（在 `docs/tasks/backlog.md` 的“原厂对比复查”一节）。
- `docs/product/system-ui-spec.md`、`docs/system/`、`docs/tasks/backlog.md` 的“完成界限”。
- 原厂只读副本 `$INK_DEPS/../ink-hw/upstream/Metalio-E-INK4-Plus-874538e`（v2.0.77）。

## 要做的

1. **把仓库里的固件列全**：
   - 找出页面加载数据的接口：读页面的 HTML 和脚本包，找 JSON 接口。
   - 每块板、每个筛选项（尤其“全部”和“社区”）都列出来：固件名、作者、官方还是社区、版本、更新时间、说明、功能、源码链接和许可证。
   - 只读：**不下载、不运行任何固件二进制，不登录，不上传，不注册账号**。接口要是需要登录才能看，写清楚停在哪一步。
2. **看清每个固件是什么**：有源码的读源码和说明，判断它是不是哪个项目的社区移植，从哪个上游来、改了什么。只有二进制没有源码的，只记说明里写的，标明没法核实。
3. **导航里的几样也看一下**：OTA 接口文档（对照我们 `system/services/update/` 的升级流程）、书籍工具（对照阅读器支持的格式）、串口调试日志（对照我们的日志和 `tools/device/`）。云造云只记它是什么，不注册。
4. **分三类给结论**，事实和建议分开写，证据分级照 AGENTS.md：
   - **可以直接用或复用的**：代码、组件、数据、协议。每条写清许可证、和我们 C 代码怎么接、要动哪个模块，许可证不兼容的单列。
   - **我们应该补齐的功能**：对照我们现有的系统和 backlog，写缺口在哪个模块、大约多大、要不要用户定（花钱、账号、对外服务这类一律标“要用户定”）。已经在 `vendor-feature-audit` 里的不重复列，只补新发现。
   - **值得参考的设计**：交互、功耗、刷新、存储、升级、AI 接入这几方面，哪里比我们做得好，具体到哪个界面或机制。每条按我们的规矩看一遍：模块是不是拆成软总线加原子能力、AI 能不能调用、是不是够简单（用户偏好乔布斯式的简洁）。
5. 最后给一个“建议先做的三到五件事”，每件写清理由和大致工作量，不替用户拍板。

## 验收

1. 报告里有完整的固件清单表（每行有来源链接或接口出处，标【实测】或【文档】），以及上面三类结论和建议清单。
2. 每个“可复用”的条目都核对过许可证原文，引用不超过 15 个字，不大段复制别人的文档。
3. 隐私扫描：报告里不出现账号、令牌、个人信息；接口地址可以写，带签名或令牌的参数一律去掉。
4. 不改任何产品代码、测试和构建文件；只新增 `docs/tasks/registry-research-1/` 下的文件。
