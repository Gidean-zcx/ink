# perf-latency：点按到反馈、翻页、开机到主页、打开应用的时延

总规则先读 docs/tasks/codex-rules.md，第 7 节优先；docs/tasks/backlog.md 的 perf-latency 一节是原始要求。报告写到 docs/tasks/perf-latency/REPORT.md。

## 要做的

预算：产品代码改动不超过 200 行（增删合计）。只留有实测收益的改动。

1. 先量（模拟器的虚拟时间和 CPU 计量，`--cpu measured` 那套）：点按到第一帧反馈、翻一页、开机到主页可用、打开常用应用（设置、文件、相册、短信、AI）到首屏可读，各给 p50/p95。场景预算文件里已有的时延指标优先用。
2. 再改：先查合并记录里点过名的几处，量出确实拖慢的再改：
   - 长文本每打一个字就整篇写盘并落盘（text-long）；
   - 缩略图解码时一直拿着文件服务的锁（file-index-2）；
   - 主屏每次重画都同步调 `job.list` 两次（activity-card 的 `read_activity`）；
   - AiLog 每次刷新都把整个活动集合数一遍（privacy-records 的 `list_count`）；
   - 其它量出来排在前面的。
3. 每一项前后对比；改了没收益的退掉。

## 边界

- 行为不变：全量测试、确定性测试都过；不放宽任何预算。真机才能确认的标清楚。
- 不改刷新算法（D-110 已固定）。
- 同时在做的有 perf-memory；两边都可能动同一个文件，只改各自那几处，报告里列清。

## 验收

1. 报告里有前后对比表（p50/p95）【实测，模拟器】，每项改动对应的收益。
2. 点名的四处每处都有结论：改了省多少，或者量下来不值得改（附数据）。
3. 全量测试和内存检查通过；产品代码改动不超过 200 行。
