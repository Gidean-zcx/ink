## 已确认问题

### BR-R4（高，新发现）：恢复的版本检查漏掉正在进行的原子写，覆盖新资料后仍报成功

**位置**：`system/services/backup/backup_service.c:217`、`:700`、`:708`；`system/services/file/file_service.c:1300`、`:1324`。

**复现与结果【实测】**：隔离编译测试副本，链接未修改的产品归档；使用原设备档案。备份根目录文件 A；改为 B 后预览、人工确认恢复；在正文下载完成时，另一任务通过 `ink_fs_write_atomic` 写入新资料 C。新写入返回成功，但恢复把 C 覆盖成 A，最终 `backup.restored=1`。探针 25 条通过，只有“保留较新成功写入”的断言失败，`test.finished=1`。首个复现为原文件 98,304 B、新文件 8 MiB，最终文件却是 98,304 B 的 A。证据：`build/review-atomic-race-pk2cfzsp/atomic-race/metrics.json`。

**原因【实现】**：文件版本只在原子写开始前加一。`hash_file` 不持文件修改锁，在替换尚未提交时读到旧文件，却取得已加一的版本；原子改名完成后版本不再变化。随后恢复拿到修改锁时，版本仍相等，就删除较新文件并装入旧备份。已有 `api` 用例是在写入完成前后比较版本，没覆盖“写入进行中取版本及哈希”的窗口。

**修法**：让哈希采样能够识别进行中的写入，版本校验覆盖提交完成；例如提供受修改锁保护的稳定读取标记，或开始/完成双边变化的序列，并拒绝在不稳定区间采样。增加通过真实恢复能力与并发原子写交错的测试，核对较新正文及恢复结果，不能只检查两个顺序调用的版本值。

### BR-R3（高，部分未修）：慢链路上的网络等待仍占用共享后台执行器

**位置**：`system/services/backup/backup_service.c:453`、`:508`、`:533`、`:545`；共享执行器 `system/services/res/exec.c:38`。

**复现与结果【实测】**：原产品二进制、原 `large-seed` 场景，文件保持默认 98,304 B；只把模拟网络改为 0.2 Mbit/s、固定 RTT 600 ms、丢包率 0，其他配置及断言不变。备份最终成功，但两次进度查询超时，`cap.timeouts=2`，`test.fail=3`、`test.finished=1`。证据 `build/review-slow-link-levcx_zo/out/metrics.json`。这是较慢但仍可用的网络，未注入断连、损坏、扩大文件或缩短能力期限。

**原因与影响【实现】**：`upload_block` 在同一 `exec.bg` 步骤中等待 begin RPC、最多 64 KiB 的 ACK 和 end RPC；其间的 task delay 只让出 CPU，不归还后台执行器。每次等待上限 3 秒不能保证整个步骤或排队查询小于默认 3 秒。分块复制/哈希的修复有效，网络阶段仍会拖住进度、成员解锁等共用后台工作。

**修法**：将 RPC 与 ACK 等待也拆为状态机续接，发送后归还执行器，由回执或超时回调唤醒；保持持久偏移和成员绑定。增加上述慢链路下的进度/解锁测试，不提高能力期限。
