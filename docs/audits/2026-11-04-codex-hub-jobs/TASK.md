# 产品审查任务说明（2026-11-04，家庭中枢，产品负责人视角，交给 Codex）

用户要求功能、交互和界面的设计向乔布斯的理念看齐，并在审查时模拟一位这样思考的产品负责人。前几轮审查看的是设计对不对、全不全；这一轮只看**它是不是简单、专注、值得喜欢**。

你按这种方法工作：只问一个人真正要做成什么事；删到不能再删；一个屏幕一个目的、一个主要动作；用正确的默认值代替设置；用人话代替技术词；复杂留给系统，不留给人；出错时告诉人下一步做什么。**这是模拟一种方法，不要编造任何人说过的话。**

## 1. 看什么

这个产品是用户自己一家用的 AI 墨水屏设备，这里审的是它背后的服务器（家庭中枢）里**人碰得到的部分**。用户自己会装服务器，家里还有成人和孩子。

- `docs/hub/hub-architecture.md`：§0（用户读到的结论）；§4.1（安装和向导）；§4.2（命令行）；§4.5（数据放哪、恢复卡、换服务器、恢复时的核对页）；§5.2（费用上限）；§5.3.1（语音输入的失败提示）；§5.5（记忆，“忘掉”）；§5.7（远程画面，确认卡）；§6.1～§6.4（配对、换设备）；§7.5（确认卡）；§10（用户要等什么）。
- `docs/decisions/README.md` 第九轮：用户被要求做多少决定，这些决定问得对不对。
- `_design/hub-summary.html`：给用户看的摘要页（只在这个工作目录里，不在仓库中）。
- 设计稿和界面规范按需看：`docs/product/system-ui-spec.md`。

不要审协议细节、数据一致性和代码，那是别的审查的事。

## 2. 问这些问题

1. **第一次装好**：从拿到一台服务器到手机扫码连上设备，用户要做几件事、填几样东西、看到多少技术词？哪些可以默认、可以合并、可以不问？
2. **日常**：一家人日常会碰到中枢的哪些地方？有没有本来不该让人知道它存在的东西？
3. **出事的时候**：服务器坏了、额度用完、网断了、确认卡超时，人看到什么、下一步做什么？恢复卡和核对页够不够简单？
4. **选项和设置**：哪些设置其实不该存在？哪些决定应该由系统替用户做？这份设计问用户的 24 个决定，哪些本来不该问？
5. **功能**：哪些可以砍或者推迟，让第一版更专注？
6. **用词**：哪些词用户看不懂（比如“对象存储”“同代快照”“恢复卡”）？给出替换。

## 3. 规则

- **砍需求、改已定的决定，都只能写成给用户的提议**，写明好处和代价，不要写成必须。用户已选的是 D-74、D-78、D-79、D-85、D-87、D-91、D-94、D-98。
- 安全和数据的底线不要为了简单而放弃：有副作用要人确认（D-25、R-040），孩子的规则，不丢数据。可以提议更简单的做法，但要说明底线还在。
- 不改产品代码、测试、现有文档；不提交、不推送、不建分支；不接触设备；不注册、购买、调用付费接口。
- **产出只写在** `docs/audits/2026-11-04-codex-hub-jobs/`：`report.md`、`findings.json`。边做边写。
- `_design` 是临时目录，不要把它的路径写进结论。

## 4. 写法与格式

报告用中文，说人话。`report.md`：

1. **一页结论**：这个产品的服务器部分，一句话说它应该是什么；现在离那里有多远；最值得改的 3 件事。
2. **问题清单**：每条写清是什么、在哪（文件和章节）、为什么不够好、具体怎么改、改了有什么代价。分三级：**必须改**（人会卡住、搞错或放弃）、**应该改**（明显更简单）、**可以想**。
3. **给用户的提议**：要砍或者要改已定决定的，单独列出来。
4. **做得好的**：哪些已经够好，不要动。

`findings.json`：数组，每项 `{"id","level","area","title","where","why","change","cost"}`，编号 JOBS-HUB-001 起。

## 5. 完成后

最后的回复里给出：各级数量、最值得改的 3 件事、报告路径。
