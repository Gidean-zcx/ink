## 新问题

下列【复现】均为[合成状态实验](experiments/README.md)，结果见 [results.json](experiments/results.json)。没有中枢实现或实机故障证据。

### HUB5-001｜严重｜核对页要求停旧机，但安全日志在停机前已经读完，可能遗漏已上传的操作

**证据与位置：**【文档核查】`docs/hub/hub-architecture.md:398`、`:399` 先取快照、取回并重放安全日志；`:400`、`:409` 随后才让成人去服务商停旧机；`:401` 确认后直接换实例并开放。`:442`、`:443`、`:453` 则承诺已写到对象存储的吊销和“忘掉”在恢复后仍有效。这段流程没有停机后的重新读取或最终日志水位检查。

**失败路径：**【复现】`read_log_then_stop` 按这个顺序执行：

1. 新机取完快照和日志，停在核对页，尚未开放。
2. 旧机此时仍可工作；此前排队的安全操作完成上传，或者另一位成人在旧机完成一次“忘掉”。该操作已经异地成功。
3. 安装者按页面要求把旧机真正关掉，随后确认开放新机。
4. 新机只重放了先前取到的日志，旧快照中的该条记忆仍可见。实验中异地日志有 1 条，新机应用 0 条；停机后重新取回并重放的对照不再保留它。

**影响：**【推断】已承诺完成的“忘掉”可重新进入 AI 的可读数据；同样的时序用于吊销时，恢复名单也可能漏掉最新吊销。这里没有人错误确认旧机已停，也没有两台同时服务、对象存储旧读或未上传尾部的假设。人工核对可能碰巧补救，但不能替代“异地已完成的操作自动重放”的保证。因此属于数据保护问题，定为严重；不重报 §12 已接受的人为误确认风险。

**建议：**把旧机停写、停服务的确认放在选取最终恢复点之前。允许预先下载，但停机确认后必须重新取得并验证最终快照／日志水位，补齐重放，再用更新后的名单和时间核对开放。计划内 `handover` 应在持续禁止新写入的状态下排空任务、完成最终上传，并把交接标记绑定这次实例和恢复水位；新机只能据此接管。此修正不要求首版增加自动租约。

### HUB5-002｜高｜恢复令牌直接接续增量，漏掉新数据集的删除历史缺口

**证据与位置：**【文档核查】`docs/hub/hub-architecture.md:988`、`:997` 明确墓碑最多 256 条，被挤掉就须全量对账。`docs/hub/device-protocol.md:298` 只对“已认识”的数据集处理 `history_gap`；`:299` 对带未用令牌的未知数据集直接回 `continue`，没有排除 `history_gap=true`。概要 `:1007`、`:1013` 同样明确“不用对账”。`:314` 又允许先原子安装快照，再报到，安装与报到之间可以断线。

**失败路径：**【复现】`grant_history_gap` 使用未回滚的中枢和从未使用过的恢复授权：

1. 设备装好包含 257 条记录的快照，生成新数据集；首次 `sync/status` 发出前断网。
2. 设备继续本地使用，删除这 257 条记录。数据集本身完整，但最早一条删除墓碑被挤掉，因此报告 `complete=true`、`history_gap=true`。
3. 中枢仍保留原快照副本，授权没用过、对应版本也没变，命中新增分支，返回 `continue`，`acked_ver` 设为快照版本。
4. 增量从这个版本起发，`from_ver` 能接上，剩余 256 条墓碑却无法表达最早的删除。实验中设备已空，中枢仍有 1 条已被删掉的记录；改用完整清单的对照能移除它。

**影响与边界：**【推断】中枢保留错误的恢复副本，之后换设备或从中枢恢复时可把删除的记录带回，违反 `:1644` 的“超过 256 次删除……不复活”验收要求。只检查 `from_ver` 连续不能找回被挤掉的删除。如果设备保留 gap 并再次发 `sync/status`，此时已认识的数据集可能进入 `manifest`，所以本轮不声称永久损失或必然永远不同步；当前协议仍会先把不完整的增量历史当作可以接续，且没要求这个二次补救。

**建议：**把“恢复授权有效”和“还能发完整增量”分开。有效令牌且中枢基准未变时可以认可新数据集；只有快照水位之后的变化连续、没有 `history_gap` 才回 `continue`，否则走完整对账。对没有有效授权的未知数据集仍回 `wait`，不能为了处理 gap 又给任意未知数据集删除权。新增“安装后断线 → 本地删除超过 256 条 → 第一次携令牌报到”的契约用例。
