### 2. PQ-BN 跳相状态（AUD-011/F-8）

- 【复现】`python3 docs/audits/2026-11-03-codex-r8/experiments/pq_checks.py` 用当前真实内核比较逐相运行与跳步。普通及 ASan/UBSan 各 23 组，均编译 exit=0；判据检测到 11 组差异，探针 exit=1（行为不等价，非 sanitizer 异常）。输出见 [pq-results.json](experiments/pq-results.json)。
- ≤255 相在跨 4096、65536 和 uint32 时钟回绕的状态均相同；512、513 相本组也相同。`H=512, from=20, n=768` 时跳步造成 2624 个早已静止像素被认为停留不足 64 相，逐相参考为 0；受影响第 236 行所在 tile 在下一次白转灰规划时，`hot` 48 字节、`cold` 256 字节不同。故不能将任意跳步等价写成已验证。
- 【代码核查】`drivers/display/pqbn/pqbn_v4.c:503–512` 对长跳步只执行最后 512 相；模 1024 的年龄判定可能已经丢失早先钳位的作用。`ports/sim/hal/hal_display_sim.c:1092` 将调用限制为 255，因此此长跳步反例不应夸大成当前模拟器必现回归，定中。
- 【复现】返回行数还存在取整误差：684 行屏，`from=1,n=1` 实扫 2 行、返回 1；`from=510,n=255` 实扫 341 行、返回 340。归入下节 CPU 记账问题，不单独编号。
- 【复现】复用第七轮“20 相运行 + 255 相静止，重复三次”的时钟反例，当前内核配旧跳时钟算法为 30208/32768 像素停留等级错误（92.2%，exit=1）；配新维护调用为 0（exit=0）。此正反对照确认原 F-8 的当前模拟器状态缺陷已修，残留为接口长步长及 CPU 记账。命令和输出见 [clock-cycle-results.json](experiments/clock-cycle-results.json)。

### 3. PQ-BN 静止维护的 CPU 成本（AUD-011/F-8）

- 【代码核查】`hal_display_sim.c:1098–1099` 将 `pqbn_v4_skip` 的返回行数乘 `row_idle=43`；`pqbn_v4.c:471–492` 的维护会读取/修改每个静止像素的 PSRAM 状态，而 `pqbn_v4_exec_row:591–592` 的空行路径只是直接返回。两种工作量不同。
- 【复现（指令级模型，非实机）】`python3 docs/audits/2026-11-03-codex-r8/experiments/pq_cost.py` 使用本机 ESP RISC-V GCC、仓库现有 S31 编译参数、fitted/slow 配置及 1216×684 生产内存布局，直接编译当前内核；两个 ISS 运行均 exit=0。命令、输出与区段指令数见 [pq-cost-results.json](experiments/pq-cost-results.json)。

- 白屏 255 相维护执行 7,881,837 条目标指令；当前只记 0.0456875 ms（14,620 cycles）。这是用错成本类，并非主机运行速度或普通测试的小幅波动。fitted×1.3 与 slow 取大仍为约 58.1 ms。
- 【推断】正常阅读长静止后的首次刷新会低估这段 CPU 占用，影响刷新时延、并发可用 CPU 与电流账。按第一轮“明显缺陷或风险，近期会碰到”定高：当前可选 PQ-BN 路径直接受影响；本轮尚未证明这段漏账使整机可行性或预算通过结论翻转，也未证明必然音频欠载。定级不以“未做实机”作为排除严重模型缺陷的理由。
- 探针首编译出现一次宏名 `W/H` 与结构字段冲突，改为枚举常量后编译通过；该审计辅助程序错误保留在结果中，不计作产品问题。

### AUD9-001（中）：新跳相 API 在较长静止后不等价于逐相运行
