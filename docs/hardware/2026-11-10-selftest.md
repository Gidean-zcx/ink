# 2026-11-10 上机：真机自检（第一次用我们自己的驱动）

用户 2026-11-10 晚上连上设备，说“你自己玩吧，别给我看了，别搞挂了就行”，也没空配合按键和观察。全程无人值守，只做可复原的写入。原始日志、备份都在仓库外的私有目录，不进仓库。

## 做了什么

| 时间 | 动作 | 结果 |
| --- | --- | --- |
| 16:08 | 用户短按电源键唤醒（出厂固件闲置 180 秒会睡、USB 断开）；等屏幕空闲 5 秒后进下载模式 | 设备停在下载模式，不再睡眠 |
| 16:08 起 | 整片读两遍、比对，再和设备 verify-flash | 两遍一致，和设备一致。和 11-03 的备份按区域比：只有 NVS 变了（设备用了几天），引导程序、分区表、otadata（seq 1 选 ota_0）、出厂固件 ota_0、ota_1（空）、资源和字库都没变 |
| 之后 | `tools/hw-selftest/run.py`：屏幕空闲后写 ota_1（0x580000，自检固件 952 208 B）和选中 ota_1 的 otadata（0xd000），写后校验，复位 | 自检固件从 0x580000 启动，跑完 17 项 |
| 之后 | 写回出厂 otadata 和 ota_1 被覆盖的那段，整个 ota_1 和 otadata 与备份比对 | `RESTORE VERIFIED` |
| 之后 | 复位 | 出厂固件照常 `Loaded app from partition at offset 0x80000` |
| 之后 | 屏幕空闲后再进下载模式 | 保持连接，等下一轮 |

只写了 otadata 和 ota_1 两处，没有整片擦除，没碰引导程序、NVS、eFuse、4G 模组设置，没驱动屏幕。

## 自检结果（我们的 I2C HAL 和芯片驱动）

| 项目 | 结果 |
| --- | --- |
| 安全第一步 | 屏幕电源（TCA9555 P00～P02）本来就是关的，读回确认，没有写 |
| 系统 | ESP-IDF v6.1，芯片版本 0，双核，320 MHz（实测 320） |
| 内存 | 内部可用约 364 KB（最大块 258 KB），PSRAM 16 MB，1 MB 读写无错（写 69 MB/s、读 66 MB/s） |
| flash | JEDEC 852018，16 MB |
| 计时 | 100 万次 LCG 12.5 ms，内部 memcpy 464 MB/s，100 ms 延时实测 95 ms |
| GPIO | GPIO2（扩展芯片和加速度计中断线与）、GPIO5（触摸中断）空闲都是高 |
| I2C 扫描 | 0x19、0x20、0x38、0x51、0x55、0x6b 全部应答，没有缺的（0x3c 摄像头没时钟、0x68 屏幕电源芯片睡着，都在意料之中） |

| 加速度计 | 地址 0x19，WHO_AM_I 0x11；CTRL1 = 0x10（1 Hz、三个轴都没开），所以 xyz 读到 0，下一轮先开轴再读 |

| Wi-Fi | 扫描 2.5 秒，找到 9 个网络（只记数量） |

## 发现

- **S31 的 UART0 默认引脚就是 GPIO58/59，也就是 NT26 的 UART2**：控制台走 UART0 的固件会把日志送进模组。自检固件把控制台设成只走 USB；端口固件也要这样设（记进 backlog）。
- 加速度计出厂配置三个轴都没开，“拿起亮屏”在真机上要先开轴（accel-use 的驱动会写 CTRL1，上机时核对）。
- 4G 模组要先写帧协议层才能对话（端口后续批次）。
