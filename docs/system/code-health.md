## 防御性代码

| 指标（只算 `.c`） | 全部 26661 行 | 早期手写模块 2443 行 |
| --- | --- | --- |
| 守卫式提前返回占比 | 4.3% | 4.8% |

| 一行写多句占比 | 2.1% | 0.7% |

结论：**整体没有防御性代码泛滥。** 问题集中在三处：

1. **成员身份这一套铺得太开。** “代次”（generation）出现在 36 个文件、392 行，加上 `epoch`、`durable`、隔离、连接核对，约 680 行。根因只有一个：删掉一位家人后编号可以复用，所以到处都要核对“还是不是原来那个人”。这是复查逐轮逼出来的。
2. **`backup_service.c`。** 1110 行里守卫占 13.6%，180 行一行多句。
3. **写法太挤。** `backup_service.c`、`hub/pairing.c`、`ui/shell/navigation.c` 三个文件有 369 行一行多句，`navigation.c` 平均每行 67 个字符，所有系统页面都挤在这一个文件里。

## 建议

| 做什么 | 效果 | 优先级 |
| --- | --- | --- |
| 编号不复用，去掉代次：新家人用不重复的编号，核对只问“这个人还在不在” | 【估算】产品代码少 300～400 行，配套测试少 1000～2000 行，以后的服务不用再传代次，还顺带去掉 `durable` | 高 |
| 用格式化工具重排上面三个文件，备份按收集、上传、恢复拆开 | 行数不减反增，但能读 | 中 |
| `navigation.c` 按页面拆开 | 随应用框架一起做 | 随框架 |
| 全面重写 | 不需要 | 不做 |
