# 平台抽象与设备模拟器

版本：v0.2（2026-11-02）。状态：第一级模拟器 + 第二级指令级校准已实现；系统纵切（主页、书架、阅读器、中枢连接、AI 按键提问）全部在 CI 中按预算自动检查；按独立评审意见修正了模拟器的乐观之处（§5.2）。对应需求 R-034、R-035，想法 I-035、I-036。

> 一句话：系统代码只认 `platform/include/ink/` 里的接口（OSAL + HAL）。同一份系统代码可以跑在模拟的 Plus 上，将来也能跑在真机、RK3566 这类 Linux 设备和桌面上；模拟器按“宁可悲观”的参数复现 Plus 的 CPU、内存、刷新、存储和输入，在电脑上就能发现卡顿、内存不够和刷新冲突。

## 0. 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 有没有现成的 ESP32-S31 模拟器 | 没有。QEMU 只支持 esp32/c3/s3；ESP-IDF 的 linux 目标是单核协作式，没有时间与资源模型 | 2026-11-01 调研（[性能建模报告](../research/simulator/performance-modeling.md)） |
| 采用什么方式 | **两级**：第一级把系统代码编译成电脑程序，跑在“虚拟时间内核 + 按设备尺寸限定的内存池 + 外设模型”上；第二级用自写的 RISC-V 指令级模拟器跑热点代码，给第一级的 CPU 成本校准（已完成首轮，[报告](../research/simulator/iss-calibration.md)） | 本文 §2、§6 |
| 结果是否可信 | 时间按上限取、资源按下限取；同一场景重复运行结果逐位一致；每个参数注明来源（代码 / 数据手册 / 指令级测量 / 估算）；一次独立评审找出的 3 个高、8 个中、7 个低问题已全部处理（§5.2）。到货后按 SP-01 等实测校准，验收规则为“预测的 p95 时延与峰值内存不低于实测的 0.9 倍”（宁可高估） | [性能建模报告](../research/simulator/performance-modeling.md) |
| 换设备要不要重写 | 不用。系统与应用只依赖 OSAL/HAL 与设备档案；分辨率、DPI、屏幕类型（墨水屏/LCD）、核数、内存在档案里，界面用 dp 和物理尺寸。同一个系统已在 Plus、RK3566 类墨水屏平板、桌面 LCD 三个档案上跑通 | 本文 §1、`profiles/` |
| 模拟器已经发现了什么 | 内部 RAM 极紧、翻页时间构成、打开书时界面任务读 Flash 会让真机死机、按下反色让反馈慢一倍、滑动被当成点击、换屏被拆成两次刷新、Flash 写入与刷新冲突、PMIC 上电挡在每次响应前面、上游每次刷新都比对整块屏幕、4G 空闲恢复让提问多等等，均已修正或写入预算 | 本文 §5 |
| 现在的数字（悲观档） | 翻页稳定 0.85 s（SRS 建议 0.6 s，差距见 §5.3）；点书到首页稳定 1.45 s（SR-UX-03 ≤1.5 s）；首次可见变化 0.29 s；按住 AI 键到看到“正在听” 0.58 s（SR-UX-05 ≤0.3 s 要靠提示音）；松开到第一段回答 2.3 s；内部 + DMA RAM 最坏时余 48 KiB | CI 输出 `metrics.json` |

## 1. 分层与移植

```
apps/            主页、书架/阅读器……（只调用 system 与 ink/*.h）
system/          显示服务（刷新调度器）、输入服务、界面运行时（唯一 LVGL 任务）、
                 存储服务（Flash 守卫）、中文排版、字体、中枢连接、AI 服务……   ← 与平台无关
platform/include/ink/   osal.h  hal_display.h  hal_input.h  hal_storage.h  hal_net.h
                        hal_power.h  hal_device.h  hal_assets.h  probe.h  rotation.h
ports/sim        模拟器（本仓库已实现）
ports/esp32s31   FreeRTOS + 上游驱动（到货前搭骨架，到货后实测）
ports/posix      pthread + Linux（RK3566 等 SoC、桌面；待做）
profiles/*.json  设备档案：每个数字都在这里，系统运行时按档案自适应
```

| 接口 | 内容 | 设计要点 |
| --- | --- | --- |
| `osal.h` | 任务、队列、互斥量（优先级继承）、信号量、软件定时器、带能力标记的内存分配、时间、CPU 成本标注 | 语义取最受限的 FreeRTOS：固定优先级抢占、同优先级按节拍轮转、互斥量不移交所有权；延时与超时“至少 N”，结束在 now+N 之后的第一个节拍（FreeRTOS 端口须按微秒时钟算目标节拍）；栈放 PSRAM 的任务**不得调用任何 Flash 接口**（读也不行）。在它上面正确的代码在 Linux 上也正确 |
| `hal_display.h` | 8 位灰度、原生方向；按“为什么变”提交区域；完成回调给出排队、开始变化、稳定三个时刻 | 不暴露 EPDiy；LCD 端口忽略波形；`hal_display_hold_power()` 用于交互期保持高压电源；`hal_display_wake()` 在手指按下/按键时提前给 PMIC 上电，让上电与界面渲染并行 |
| `hal_input.h` | 原生坐标的触摸与逻辑按键（AI、电源、音量、HOME、上一页、下一页、返回） | 手势在可移植的输入服务里识别，阈值按毫米 |
| `hal_storage.h` | `/user`（掉电安全、写入昂贵）、`/content`、`/cache` 三个卷 | 设备上分别是内部 Flash 的 LittleFS、TF 卡 FAT；Linux 上是目录 |
| `hal_net.h` | 链路状态（无 / Wi-Fi / 4G、信号）与变化回调；到中枢的 WebSocket：异步打开、整条消息收发（文本/二进制）、关闭 | 设备上是 lwIP + mbedTLS + esp_websocket_client（4G 经 NT26 的 UART 以太网）；Linux 上是主机网络；系统只看到“消息通道 + 链路状态”，重连与协议在可移植的中枢连接服务里 |
| `hal_assets.h` | 只读资源（字体等）内存映射，不占堆 | 设备上是 Flash 分区，经 64 KiB 共享缓存读取；`hal_asset_access()` 是给模拟器的提示（设备上为空），用来计缓存缺失 |
| `probe.h` | 系统上报“对用户重要的”指标，如“操作到首次可见变化” | 模拟器里进入指标、轨迹和 CI 预算；设备上进日志 |

换到 RK3566 / Linux / 别的分辨率时需要做的事：实现一个 `ports/posix`（约千行：pthread 版 OSAL、Linux 帧缓冲/DRM 或 rockchip-ebc 的显示 HAL、evdev 输入），写一份设备档案。系统、应用、字体、排版、刷新调度和测试场景不变。

## 2. 第一级模拟器：模型与参数

所有参数在 `profiles/metalio-plus.json`（悲观档，CI 的门槛）里，来源见[性能建模报告](../research/simulator/performance-modeling.md)和[指令级校准报告](../research/simulator/iss-calibration.md)。另有 `metalio-plus-psram16.json`（PSRAM 16 MB + 预期 CPU 成本，即“很可能的情况”）和 `metalio-plus-upstream-display.json`（上游显示管线：127 行队列、64 KiB LUT、PMIC 上电期间暂停触摸；只用来比较时间）。启动时会列出档案没写、用了默认值的参数（Plus 档案现为 0 个）。

| 模型 | 做法 | 主要参数（Plus 悲观档） |
| --- | --- | --- |
| CPU 与调度（`sim/vtk`） | 每个系统任务是真实的线程，但同一时刻只放行一个（“接力棒”），由离散事件调度器按虚拟时间推进：2 核、固定优先级抢占、**同优先级按节拍轮转**、上下文切换与内核调用计费、空闲时间瞬间跳过。互斥量按 FreeRTOS：只给直接持有者继承优先级、持有任何互斥量期间不降回、不移交所有权。CPU 时间有两种算法：**标注模式**（默认，确定性）按代码里的成本标注计费，系统代码再加 I-cache 缺失系数；**实测模式**按主机 CPU 时间 × 换算系数 | 320 MHz（CoreMark 拟合 3.08/MHz）；内核调用 2 µs、切换 10 µs；节拍 100 Hz；长计算每 200 µs 可被抢占；I-cache 缺失 +15% |
| 指令级校准（`tools/iss`） | 自写 RV32IMAFC 指令级模拟器（顺序单发射流水线、分支预测、I/D 缓存、S31 内存映射），用 ESP-IDF v6.1 的 S31 编译选项交叉编译真实内核，测出每字节拷贝、每字形、每像素转换、JSON、解压、CRC 的周期数；按 CoreMark 与 P4/S3 的 PSRAM 实测拟合 | 悲观档取“×1.3 与慢角的较大值”，预期档取 ×1.3；文本排版、LVGL、堆管理仍是估计 |
| 内存（`sim/mem`） | 三个真实的 TLSF 堆：内部、DMA 预留、PSRAM。**内部堆由几个互不相连的区段组成**（最大块受最大区段限制），每段扣除设备分配器的控制开销；任务控制块、栈、队列、定时器都从内部 RAM 扣；只要内部 RAM 的分配可用 DMA 预留（ESP-IDF 语义），DMA 分配也可落到内部堆；按“标签”统计谁用了多少；内部与 DMA 的最大空闲块每次分配都记录 | 内部 3×32 KiB、DMA 预留 64 KiB、PSRAM 7.5 MiB（按 8 MB 片）；每段控制开销 1.5 KiB |
| DMA 用户 | LCD bounce 缓冲（显示驱动）、4G UART 以太网的收发环（模组上电期间）、TF 卡每次传输的中转缓冲；I2S 录放音环随音频管线加入 | 4.8 KiB / 12 KiB / 4 KiB |
| 墨水屏 | 上电（PMIC 约 140 ms，期间占用共享 I2C）→ **比对**（上游：对区域所在的整行做差分图，PSRAM 进出）→ 相数 × 帧时间（任何局部刷新都要扫全屏；整屏闪刷用完整 48 相表）→ **回写**（脏行拷回旧帧缓冲）→ 稳定。播放期间两个最高优先级送行任务（栈在 PSRAM）一直转到这一相最后一行入队，占用率按行队列深度推出；LCD 每 8 行一次补缓冲中断加在 0 核。**欠载**：Flash 操作冻结送行任务期间，LCD DMA 每 17 µs 消耗一行，队列见底即判定（发生时刻在停顿开始时记录，连续多次短停顿也会累计），并按上游代价恢复（清屏 69 帧 + 完整 GC16） | GC16 36 相（整屏 48）、GL16 37、DU 20，帧 16 ms（最短相 12 ms）；行队列 32 行 = 544 µs；送行任务各占 93%；LCD 中断 10%；驱动内部 RAM 50 KiB（LUT 16 KiB、两条行队列、bounce、状态） |
| 触摸、按键、I2C | 手指按下 20 ms 后控制器报中断 → 驱动任务经 100 kHz 共享总线读 9 字节 → 按 10 ms 轮询直到抬起。**按键按真实来源**：AI 键直连 GPIO（去抖 20 ms）；电源/音量在 IO 扩展芯片上（中断后读两次 I2C）；HOME/上一页/下一页是触摸控制器识别的盖板触摸键（和手指一样要检测、读总线、轮询）。PMIC 上电、波形开始/结束的 IO 扩展写入都占同一条总线。事件带物理发生时刻，测的是端到端时延 | 本系统端口用总线互斥，PMIC 只在事务期间占总线（约 10 ms）；上游档案在整个上电期间暂停触摸（140 ms） |
| 内部 Flash（`/user`） | LittleFS 跑在模拟 NOR 上：擦除 45/300 ms、编程 0.5/2.4 ms（典型/最坏，或“尾部”取样），**每次读、写、擦都关缓存，两个核上所有任务冻结**（两核计为忙）；擦除 ≥20 ms 后调用者让出一个节拍；**栈在 PSRAM 的任务碰 `/user` 直接判为死机**（同 ESP-IDF 断言）；LittleFS 缓冲放内部 RAM（端口决定），读进 PSRAM 时按 ESP-IDF 计内部中转缓冲；每次调用与 CRC 计 CPU；NOR 只能 1→0；可保存镜像跨次运行；`powercut` 撕裂进行中的写入 | 用户分区 1408 KiB；CI 另用“老化”镜像（写到 80% 后删三分之一）和最坏擦写时间跑阅读场景 |
| 缓存 | 内存映射的字体：64 KiB 两路 D-cache 行模型，缺失一次按 DIO 80 MHz 取 64 字节计约 3.6 µs；每次刷新把 PSRAM 帧缓冲流过同一缓存，模型随之清空 | 阅读场景约 2.5 万次缺失 |
| TF 卡（`/content`、`/cache`） | 主机目录 + 每次操作延迟 + 带宽 + 每写 4 MB 一次 250 ms 的忙等（卡内部整理）；每次传输占一块 DMA 中转缓冲 | 读 4 MB/s、写 1 MB/s、1.5 ms/次 |
| 电源 | 资源引用计数、各部件电流与电量估算 | 全部为估算，只用于方案比较 |
| 资源分区 | 字体等只读资源计入 6 MiB 资源分区 | — |
| 网络链路（`hal_net_sim.c`） | 往返时延按对数正态分布（由 p50/p99 推出）、带宽（4G 受 UART 上限）、丢包重传、4G 空闲后恢复（RRC 恢复额外时延 + 尾巴期耗电）、随机断网；连接 = DNS + TCP + TLS（握手 CPU 与内部/PSRAM 内存计费）+ WebSocket；链路断开后连接要等“死连接检测”才发现 | 4G：p50 80 ms / p99 400 ms、1.2 Mbit/s（UART 上限 1.6）、丢包 1%、空闲 10 s 后恢复多 300 ms、每小时断网 1–2 次各 2–5 s；TLS 内部 6 KiB + PSRAM 40 KiB、握手 9600 万周期（约 0.3 s）；死连接 5 s |
| 中枢（`sim_hub.c`） | 按规则文件应答 JSON-RPC：思考时长、分段流式推送、错误、不应答（测超时）；默认规则含 `hello`、`ping`、`ai.ask`（思考 1.4 s，4 段每 450 ms） | `--hub 规则.json` |

确定性：标注模式下同一场景重复运行，指标文件与截图逐位一致（CI 中对自检和阅读场景各有专门测试）。实测模式用于交叉核对，不进 CI 预算。

## 3. 怎么用

```bash
cmake -S . -B build && cmake --build build -j && ctest --test-dir build --output-on-failure
./build/ink-sim --profile profiles/metalio-plus.json --script tests/scenarios/reader_basic.script \
    --budget tests/scenarios/reader_basic.budget.json --assets build/assets --content build/test-content \
    --out out/ --trace --frames
```

- **场景脚本**：按虚拟时间写手指、按键、截图、电量、断电（`powercut`，或 `powercut write 2` 在之后第 2 次 Flash 写入中途断电）、切换网络（`net lte|wifi|none`）、断网（`outage 6s`）等动作；坐标可写 `116dp`、`50%`，同一脚本适用于所有屏幕。CI 场景用 `--no-random-outages` 关掉随机断网；`--flash-timing typ|max|tail` 选 Flash 擦写时间的取法。
- **输出**：`metrics.json`（每个任务的 CPU、栈、内存标签、刷新次数与波形、时延分布、Flash 停顿……）、`final.png` 与 `snap-*.png`（按竖屏方向、含残影）、`frames/`（每次刷新一张）、`trace.json`（用 https://ui.perfetto.dev 打开，可看到每个核上每个任务何时运行、每次刷新与 Flash 停顿）。
- **预算**：`*.budget.json` 写“这个场景必须满足什么”，例如翻页 p95 ≤ 1 s、内部 RAM 低水位、零欠载、零警告；超出则 CI 失败。条目还可写 SRS 目标（`target_max` + `srs`）：没达到时输出“SRS GAP”并计入 `srs_gaps`，不让 CI 失败——差距一直可见，等实机数据再定。
- **CI**：`.github/workflows/sim.yml` 在每次推送时构建、跑全部场景（含 ASan/UBSan），并保存报告与截图。CI 需要 `fonts-noto-cjk` 生成中文点阵字体。

当前 19 项测试：模拟器自检（4 个档案，最多 36 项检查，含“波形中途写 Flash 必须判为欠载”）、PSRAM 栈任务读 Flash 必须死机、两项确定性、主页与阅读器场景（悲观与预期两档）、AI 提问场景（4G，含一次断网）、阅读中途断电再开机、老化文件系统 + 最坏擦写时间、上游显示管线对照、可移植性冒烟（RK3566 类、桌面 LCD）、指令级模拟器自检。

## 4. 已实现的系统部分（第一条纵切）

| 部分 | 内容 |
| --- | --- |
| 显示服务 | 唯一持有屏幕；六种刷新意图（A2/FAST/UI/TEXT/FLASH_UI/FULL）；相交合并、只刷最新内容、反馈优先、每 6 次正文刷新清一次残影、交互期保持电源、Flash 守卫；上报“操作 → 首次变化 / 完全可见”时延 |
| 输入服务 | 原生坐标转逻辑坐标；按毫米判断滑动、长按；按键长按（与定时器共享的状态加锁，过期定时器不会误触发）；物理时间戳；手指按下/按键时预先给屏幕上电；页面代次丢弃过时输入 |
| 界面运行时 | 唯一 LVGL 任务（8 位灰度，PSRAM 条带缓冲，旋转写入原生帧缓冲）；刷新意图提示；活动栈；dp 单位；默认不做按下反色；“先反馈再打开” |
| 存储服务 | 唯一碰 `/user` 的任务（栈在内部 RAM）：读在这里替调用者执行（能读到尚未落盘的写入），写排队、原子（临时文件 + 改名）、同路径合并、等屏幕空闲且无人“暂缓写入”（音频播放时用，最长 30 s），并持 Flash 守卫期间不开始新的刷新 |
| 中文排版与字体 | 点阵字体工具（Noto Sans CJK → GB2312 全集 + 标点 + 拼音，24/32 px，2 bpp，约 3 MiB）；行首行尾禁则、英文单词不拆、标点悬挂、两端对齐、首行缩进、分页；LVGL 字体适配 |
| 阅读器 | 书架（`/content/books`）；预渲染下一页到第二块 PSRAM 缓冲；按键、滑动、点按左右区翻页；懒分页；阅读位置经存储服务保存；向 AI 提供“当前页内容” |
| 中枢连接 | JSON-RPC 2.0 over WebSocket（D-04）；按需连接（有请求或按下 AI 键时连，空闲 60 s 断开，D-24）；`hello` 握手；请求表与超时；通知按前缀订阅；断线退避 1→60 s 加抖动；错误分为远端错误 / 超时 / 离线 / 连接中断；上报连接与请求时延 |
| AI 服务 | 按住 AI 键：立即显示“正在听”（同时预连接中枢）；松开：附上当前页内容发 `ai.ask`，流式显示回答；离线、超时、中断各有明确提示；HOME/返回关闭。语音识别暂用固定文本代替（音频管线未做） |
| JSON | jsmn 解析（固定 128 个记号，不分配内存）+ 小写入器；字符串反转义含 `\u` 与代理对 |

## 5. 模拟器已经发现并处理的问题

### 5.1 系统问题

| 发现 | 数据 | 处理 |
| --- | --- | --- |
| **内部 RAM 是第一约束** | 悲观档 96 KiB 中，显示驱动 50 KiB，平台任务栈与控制块约 25 KiB；最初阅读场景只剩约 5 KiB | 界面与显示服务的栈改放 PSRAM（它们本来就要访问 PSRAM 帧缓冲，写 Flash 时反正会冻结）；LVGL 的所有分配放 PSRAM（默认策略下它的小块分配悄悄吃掉约 3 KiB 内部 RAM）；现在低水位约 7.4 KiB。仍需：DMA 预留从 64 KiB 按实际需求压到 ≤32 KiB（模拟中 DMA 池几乎未用）、平台任务栈按实测收紧、显示驱动守住 ≤50 KiB |
| **翻页时间构成** | 按键 → 去抖 20 ms → 界面重绘并旋转约 90 ms → 显示服务拷贝约 33 ms → PMIC 上电 140 ms → GL16 592 ms，合计约 0.9 s；交互期电源保持时约 0.75 s | 预算 p95 ≤ 1 s。进一步优化方向：正文直接画进原生帧缓冲（省去 LVGL 重绘，约 −90 ms）；按键一按下就预先给 PMIC 上电（与渲染并行，最多 −140 ms）；实测后调整帧时间与相数 |
| **按下反色让反馈慢一倍** | 没有快速 A2 波形时，“按下反色、松开恢复”要两次 DU（各约 320 ms），真正的结果晚一个波形才出现 | 默认不做按下反色，用动作结果本身作为反馈（一次 FAST 刷新）；需要时用 `ink_ui_style_button_pressable` |
| **滑动被当成点击，翻了两页** | LVGL 对任何没有滚动的松手都发“点击”；阅读器同时收到“滑动”和“点左区” | 输入服务把完成滑动的松手标记出来，界面运行时据此取消这次点击 |
| **换屏被拆成两次刷新** | 点按钮留下的 FAST 区域提示落在新屏幕上，先用 DU 刷一块黑白、再 GC16 全屏，可见时间到 1.3 s | 换屏时清空区域提示，整帧一次 FLASH_UI |
| **打开书的首次可见变化 415 ms** | 加载 250 KB 文本 + 排版首页都在首帧之前 | “先反馈再打开”：被点的控件立刻反色（一次 FAST，首次变化约 160 ms），之后再建新页面 |
| **Flash 读写与刷新冲突** | 写 `/user`（擦除 45–300 ms）会冻结 PSRAM 上的送行任务，行队列只能撑 0.5 ms，必然欠载（真机上是可见的花屏）；读 `/user` 也会短暂关缓存 | 存储服务等屏幕空闲并持 Flash 守卫；欠载模型按行队列可撑时长判定；预算要求零欠载 |
| **PMIC 上电挡在每次响应前面** | “按住 AI 键 → 看到正在听”627 ms = 去抖 20 + 界面绘制 119 + 拷贝 27 + **上电 140** + DU 320 | 输入服务在手指按下/抬起、按键按下/松开时调用 `hal_display_wake()`，上电与绘制并行：降到 487 ms；翻页（按键）稳定在约 0.75 s。代价：没有后续刷新的唤醒只多耗高压电源约 8 mA × 1 s |
| **内部 RAM 指标口径** | 只看 96 KiB 内部池时低水位只剩 1.3 KiB（AI 场景）；但 ESP-IDF 的 64 KiB DMA 预留池对“只要内部 RAM”的分配同样可用（普通 malloc 才不能用） | 预算改为两条：内部 + DMA 合计可用 ≥ 32 KiB（`mem.internal_total`）、DMA 池至少留一半给 I2S/SDMMC/Wi-Fi；主任务栈 8→4 KiB。单独的内部池数字仍在报告里 |
| **4G 空闲恢复让提问多等** | 4G 空闲 10 s 后第一次发包要先恢复（多约 0.3 s 加一个往返）；首次连接（DNS+TCP+TLS+WS+hello）约 1.0–1.6 s | 按下 AI 键就预连接（说话的 1–2 s 内连好）；松开到第一段文字可见约 2.0–2.2 s，其中中枢思考 1.4 s；断网时约 4.3 s 显示“连接中断”提示 |
| **10 ms 节拍** | 上游 `CONFIG_FREERTOS_HZ=100`：5 ms 的延时实际变成下一个节拍（最多 10 ms）；超时同样取整 | OSAL 规定“至少延时 N，按节拍向上取整”，模拟器照此执行；是否改 1000 Hz 留待实测功耗后决定 |

### 5.2 独立评审指出的模拟器乐观之处（2026-11-02，已全部处理）

| 评审发现 | 影响 | 处理 |
| --- | --- | --- |
| **H1 打开书时界面任务读 `/user`**，而界面任务的栈在 PSRAM | 真机上 Flash 驱动关缓存时栈不可达，ESP-IDF 断言 → 死机；模拟器原先不报 | 模拟器对“PSRAM 栈任务碰 `/user`”直接判死机（有专门的死亡测试）；`/user` 的读改由存储任务代办；`osal.h` 写明规则 |
| **H2 欠载会被漏判** | 一次 45 ms 擦除完全落在波形里也报“零欠载”；判据只看单次停顿是否超过 544 µs | 停顿开始即记录与波形的重叠；按行队列水位建模（冻结时每 17 µs 少一行，停顿之间按净补充速度回升）；送行任务跳过错过的相；欠载按上游代价恢复（约 1.9 s） |
| **H3 漏算上游每次刷新的工作** | 上游先对区域所在整行做差分图、刷完再回写；完整清屏用 48 相表 | 驱动任务里计比对与回写；整屏闪刷用 48 相。翻页 0.75 → 0.85 s，点书到首页 1.45 s |
| M1 送行任务占用率与行队列深度不符；漏了 LCD 补缓冲中断 | 页面预渲染等后台工作被高估 | 占用率按行队列推导（32 行时 93%），0 核再加 10% 中断负载；预渲染 p95 0.29 s（预算按墙钟改为 0.6 s） |
| M2 写 Flash 时“IRAM 安全任务”仍在跑；同优先级不轮转 | ESP-IDF 写 Flash 时两个核都停调度 | 所有任务冻结（删掉该任务标志），两核计为忙；同优先级按节拍轮转；自检必须证明两个任务都在跑、都被冻结 |
| M3 很多工作在标注模式里不计时 | LittleFS、CRC、缓存缺失、LVGL 对象 | 都已计费（见 §2）；文本排版与 LVGL 仍是估计，下一步用指令级模拟器测我们自己的代码 |
| M4 LittleFS 缓冲在 PSRAM；CI 只用刚格式化的文件系统 | ESP-IDF 对 PSRAM 缓冲每 32 字节关一次缓存、读要 16 KiB 内部中转 | 缓冲放内部 RAM（端口决定 `LITTLEFS_MALLOC_STRATEGY_INTERNAL`）；CI 增加老化镜像 + 最坏擦写时间 |
| M5 内部堆是一整块、DMA 池没人用 | “DMA 预留几乎没用”的结论站不住；预算被放松 | 内部堆分区段；加入真实 DMA 用户；预算改为内部+DMA ≥32 KiB、最大可用块 ≥8 KiB、DMA 预留 ≥16 KiB |
| M6 按键都当直连 GPIO；上游上电期间暂停触摸 | 盖板键、音量键要经共享总线 | 按真实来源建模（§2）；上游档案暂停触摸 140 ms（按键送达 p95 83 ms，本端口 21 ms） |
| M7 双核才会暴露的竞争 | 长按定时器与松手同时到达；显示忙计数可能卡在大于 0 | 输入服务加锁并核对按住时长；忙计数不再跨任务读改写 |
| M8 指标与 CI 缺口 | 换屏端到端没测；单一随机种子；警告不拦；断电没测 | 新增 `ui.open_to_stable_ms`；最坏擦写时间；警告进预算；断电再开机场景；阅读场景确定性 |
| L1–L7 | 延时语义、互斥量语义、Flash 时间算 CPU、长标题位置丢失、恢复后重复刷新、默认值偏乐观等 | 均已修正或写明（§1 `osal.h` 一行、§2） |

### 5.3 与 SRS 建议值的差距，以及端口可以拿回多少

悲观档下，SR-UX-02（翻页 ≤600 ms）和 SR-UX-05（按 AI 键到提示 ≤300 ms）达不到：GL16 37 相 × 16 ms 光波形就 592 ms；屏幕提示无论如何超过 300 ms，SR-UX-05/01a 要靠提示音（音频管线）。下表是在同一场景上逐项打开端口优化的结果（`--profile` 临时改参数跑出，非实测）：

| 方案 | 翻页稳定 p95 | 点书到首页 | 首次可见变化 p95 | 预渲染 p95 | AI 键→“正在听” |
|---|---|---|---|---|---|
| A 上游管线（悲观基线） | 854 ms | 1451 ms | 285 ms | 290 ms | 583 ms |
| B 只比对改动区域 | 851 ms | 1396 ms | 285 ms | 201 ms | 554 ms |
| C B + 送行任务阻塞等待（不空转） | 851 ms | 1347 ms | 285 ms | 126 ms | 554 ms |
| D C + 行准备用向量指令（8 µs/行） | 851 ms | 1299 ms | 285 ms | 48 ms | 554 ms |
| E D + 换屏用普通 GC16（36 相） | 851 ms | 1107 ms | 285 ms | 48 ms | 554 ms |
| F E + 实测若为 12 ms 帧 | 703 ms | 886 ms | 285 ms | 48 ms | 474 ms |

结论：翻页几乎只取决于波形本身（相数 × 帧时间），端口优化主要省下 CPU（让预渲染、录音、网络在刷新期间还有算力）和换屏时间。要到 600 ms，需要 SP-01 实测确认帧时间，并评估更短的正文波形；这是到货后第一批要做的测量。

## 6. 可信度与局限

能在电脑上验证的：任务划分与优先级是否会互相饿死、内存是否够用以及碎片、刷新调度是否正确、时延由哪些部分构成、Flash 写入时机是否安全、断电后数据是否完好、不同分辨率与屏幕类型下界面是否成立。

还不能或只能粗略验证的：

1. **CPU 成本部分已校准。** 拷贝、字形、转换、JSON、解压、CRC 来自指令级模拟器（CoreMark 只能拟合到 3.08/MHz，比数据手册低 10%，取悲观）；LVGL（每像素 25 周期 + 每对象成本）、文本排版、堆管理仍是估计；到货后用实测校准。
2. **缓存与总线只做了粗模型**：I-cache 用固定缺失系数，字体 D-cache 用行模型；两核同时访问 PSRAM 的相互影响（评审 L4）没建模，只体现在每字节成本里；中断开销只建了 LCD 补缓冲一项。
3. **栈用量**是主机上的悲观估计；权威数字要用 RISC-V 编译的 `-fstack-usage`。
4. **网络是统计模型**：时延分布、恢复、断网参数是估算，4G 模组的真实行为（注网、弱信号、UART 流控）要到货后用 SP 系列实测校准；**还没有音频模型**（正在做）。
5. **模拟器一次只跑一个任务**，看不到真正的数据竞争；竞争靠代码审查和加锁规则防，评审找到的两处已修。
6. **内部堆区段大小是猜的**（3×32 KiB）；`idf.py size` 与设备上的 `heap_caps_print_heap_info` 出来后替换。
7. **波形时间来自上游代码与悲观帧时间**；温度对相数的影响未建模（上游也没有温度补偿，见 RK-14）。
8. **电流全部是估算**，只能比较方案，不能承诺续航。

## 7. 平移到真机

1. `ports/esp32s31`：用 FreeRTOS 实现 `osal.h`（`xTaskCreateWithCaps` 支持 PSRAM 栈、`heap_caps_*`、`esp_timer`；延时按微秒时钟算目标节拍），用上游驱动实现各 HAL（EPDiy 改造版、FT6336U、TPS65185、LittleFS、SDMMC）。系统与应用代码不改。端口必须做到模拟器里已经假定的几件事：I2C 总线互斥（PMIC 上电不整段暂停触摸）、LittleFS 缓冲放内部 RAM；值得做的优化见 §5.3（只比对改动区域、送行任务阻塞等待、向量指令准备行）。另需评估 S31 的 Flash 自动挂起（`SPI_FLASH_AUTO_SUSPEND`，S31 硬件支持，取决于板上 Flash 型号）：若可用，擦写期间缓存不关，送行任务与音频都不会被冻结。
2. 到货第一周：读 `esp_psram_get_size()`、跑 SP-01（刷新时序，尤其每相帧时间）、`idf.py size` 与 `heap_caps_print_heap_info`（静态内存与内部堆区段）、Flash 擦写与停顿实测、查板上 Flash 型号是否支持自动挂起，把实测值写回档案。
3. 同一批场景在真机上跑（按键注入或人工操作），对比预测与实测：预测不得比实测乐观超过 10%，否则调整参数并在档案里记录来源变化。
