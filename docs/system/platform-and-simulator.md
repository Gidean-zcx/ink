# 平台抽象与设备模拟器

版本：v0.1（2026-11-02）。状态：已实现第一级模拟器和系统的第一条纵切（主页、书架、阅读器），全部在 CI 中按预算自动检查。对应需求 R-034、R-035，想法 I-035、I-036。

> 一句话：系统代码只认 `platform/include/ink/` 里的接口（OSAL + HAL）。同一份系统代码可以跑在模拟的 Plus 上，将来也能跑在真机、RK3566 这类 Linux 设备和桌面上；模拟器按“宁可悲观”的参数复现 Plus 的 CPU、内存、刷新、存储和输入，在电脑上就能发现卡顿、内存不够和刷新冲突。

## 0. 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 有没有现成的 ESP32-S31 模拟器 | 没有。QEMU 只支持 esp32/c3/s3；ESP-IDF 的 linux 目标是单核协作式，没有时间与资源模型 | 2026-11-01 调研（[性能建模报告](../research/simulator/performance-modeling.md)） |
| 采用什么方式 | **两级**：第一级把系统代码编译成电脑程序，跑在“虚拟时间内核 + 按设备尺寸限定的内存池 + 外设模型”上（已实现）；第二级用 RISC-V 指令级模拟器跑热点代码，给第一级的 CPU 成本校准（进行中） | 本文 §2、§6 |
| 结果是否可信 | 时间按上限取、资源按下限取；同一场景重复运行结果逐位一致；每个参数注明来源（代码 / 数据手册 / 估算）。到货后按 SP-01 等实测校准，验收规则为“预测的 p95 时延与峰值内存不低于实测的 0.9 倍”（宁可高估） | [性能建模报告](../research/simulator/performance-modeling.md) |
| 换设备要不要重写 | 不用。系统与应用只依赖 OSAL/HAL 与设备档案；分辨率、DPI、屏幕类型（墨水屏/LCD）、核数、内存在档案里，界面用 dp 和物理尺寸。同一个系统已在 Plus、RK3566 类墨水屏平板、桌面 LCD 三个档案上跑通 | 本文 §1、`profiles/` |
| 模拟器已经发现了什么 | 内部 RAM 极紧、翻页时间构成、按下反色让反馈慢一倍、滑动被当成点击导致翻两页、换屏被拆成两次刷新、Flash 写入与刷新冲突等，均已修正或写入预算 | 本文 §5 |

## 1. 分层与移植

```
apps/            主页、书架/阅读器……（只调用 system 与 ink/*.h）
system/          显示服务（刷新调度器）、输入服务、界面运行时（唯一 LVGL 任务）、
                 存储服务（Flash 守卫）、中文排版、字体……   ← 与平台无关
platform/include/ink/   osal.h  hal_display.h  hal_input.h  hal_storage.h
                        hal_power.h  hal_device.h  hal_assets.h  probe.h  rotation.h
ports/sim        模拟器（本仓库已实现）
ports/esp32s31   FreeRTOS + 上游驱动（到货前搭骨架，到货后实测）
ports/posix      pthread + Linux（RK3566 等 SoC、桌面；待做）
profiles/*.json  设备档案：每个数字都在这里，系统运行时按档案自适应
```

| 接口 | 内容 | 设计要点 |
| --- | --- | --- |
| `osal.h` | 任务、队列、互斥量（优先级继承）、信号量、软件定时器、带能力标记的内存分配、时间、CPU 成本标注 | 语义取最受限的 FreeRTOS：固定优先级抢占、延时与超时按系统节拍取整；在它上面正确的代码在 Linux 上也正确 |
| `hal_display.h` | 8 位灰度、原生方向；按“为什么变”提交区域；完成回调给出排队、开始变化、稳定三个时刻 | 不暴露 EPDiy；LCD 端口忽略波形；`hal_display_hold_power()` 用于交互期保持高压电源 |
| `hal_input.h` | 原生坐标的触摸与逻辑按键（AI、电源、音量、HOME、上一页、下一页、返回） | 手势在可移植的输入服务里识别，阈值按毫米 |
| `hal_storage.h` | `/user`（掉电安全、写入昂贵）、`/content`、`/cache` 三个卷 | 设备上分别是内部 Flash 的 LittleFS、TF 卡 FAT；Linux 上是目录 |
| `hal_assets.h` | 只读资源（字体等）内存映射，不占堆 | 设备上是 Flash 分区；写 Flash 时同样不可读 |
| `probe.h` | 系统上报“对用户重要的”指标，如“操作到首次可见变化” | 模拟器里进入指标、轨迹和 CI 预算；设备上进日志 |

换到 RK3566 / Linux / 别的分辨率时需要做的事：实现一个 `ports/posix`（约千行：pthread 版 OSAL、Linux 帧缓冲/DRM 或 rockchip-ebc 的显示 HAL、evdev 输入），写一份设备档案。系统、应用、字体、排版、刷新调度和测试场景不变。

## 2. 第一级模拟器：模型与参数

所有参数在 `profiles/metalio-plus.json`（悲观默认）里，来源见[性能建模报告](../research/simulator/performance-modeling.md)。另有 `metalio-plus-psram16.json`（PSRAM 16 MB 的预期情况）和 `metalio-plus-upstream-display.json`（上游显示驱动的内存占用）作对照。

| 模型 | 做法 | 主要参数（Plus 悲观档） |
| --- | --- | --- |
| CPU 与调度（`sim/vtk`） | 每个系统任务是真实的线程，但同一时刻只放行一个（“接力棒”），由离散事件调度器按虚拟时间推进：2 核、固定优先级抢占、上下文切换与内核调用计费、空闲时间瞬间跳过。CPU 时间有两种算法：**标注模式**（默认，确定性）按代码里的成本标注计费；**实测模式**按主机 CPU 时间 × 换算系数 | 320 MHz；内核调用 2 µs、切换 10 µs；节拍 100 Hz（延时按 10 ms 取整）；长计算每 200 µs 可被抢占 |
| 内存（`sim/mem`） | 三个真实的 TLSF 堆：内部、DMA、PSRAM，大小即设备上系统可用的预算；任务控制块、栈、队列、定时器都从内部 RAM 扣；按“标签”统计谁用了多少 | 内部 96 KiB、DMA 64 KiB、PSRAM 7.5 MiB（按 8 MB 片） |
| 墨水屏 | 上电（PMIC 约 140 ms，期间占用共享 I2C）→ 相数 × 帧时间（任何局部刷新都要扫全屏）→ 稳定；播放期间两个最高优先级送行任务占两个核各约 70%；画面状态与残影可截图；Flash 冻结超过行队列可撑住的时间即判定“欠载” | GC16 36 相、GL16 37 相、DU 20 相、帧 16 ms；驱动内部 RAM 50 KiB、PSRAM 1.6 MiB；行队列 32 行 = 544 µs |
| 触摸、按键、I2C | 手指按下 20 ms 后控制器报中断 → 驱动任务经 100 kHz 共享总线读 9 字节（约 1.2 ms，PMIC 上电、电量计轮询会占总线）→ 按 10 ms 轮询直到抬起；按键去抖 20 ms。事件带物理发生时刻，所以测出的是端到端时延 | 见档案 `input` |
| 内部 Flash（`/user`） | LittleFS 跑在模拟 NOR 上：擦除 45/300 ms、编程 0.5/2.4 ms（按“尾部”取样），**每次读写擦都关缓存**：所有非 IRAM 任务和用 PSRAM 的任务在两个核上冻结；NOR 只能 1→0；可保存镜像跨次运行；`powercut` 会撕裂进行中的写入，用来测掉电安全 | 用户分区 1408 KiB |
| TF 卡（`/content`、`/cache`） | 主机目录 + 每次操作延迟 + 带宽 + 每写 4 MB 一次 250 ms 的忙等（卡内部整理） | 读 4 MB/s、写 1 MB/s、1.5 ms/次 |
| 电源 | 资源引用计数、各部件电流与电量估算 | 全部为估算，只用于方案比较 |
| 资源分区 | 字体等只读资源计入 6 MiB 资源分区 | — |

确定性：标注模式下同一场景重复运行，指标文件与截图逐位一致（CI 中有专门测试）。实测模式用于交叉核对，不进 CI 预算。

## 3. 怎么用

```bash
cmake -S . -B build && cmake --build build -j && ctest --test-dir build --output-on-failure
./build/ink-sim --profile profiles/metalio-plus.json --script tests/scenarios/reader_basic.script \
    --budget tests/scenarios/reader_basic.budget.json --assets build/assets --content build/test-content \
    --out out/ --trace --frames
```

- **场景脚本**：按虚拟时间写手指、按键、截图、电量、断电等动作；坐标可写 `116dp`、`50%`，同一脚本适用于所有屏幕。
- **输出**：`metrics.json`（每个任务的 CPU、栈、内存标签、刷新次数与波形、时延分布、Flash 停顿……）、`final.png` 与 `snap-*.png`（按竖屏方向、含残影）、`frames/`（每次刷新一张）、`trace.json`（用 https://ui.perfetto.dev 打开，可看到每个核上每个任务何时运行、每次刷新与 Flash 停顿）。
- **预算**：`*.budget.json` 写“这个场景必须满足什么”，例如翻页 p95 ≤ 1 s、内部 RAM 低水位、零欠载；超出则 CI 失败。
- **CI**：`.github/workflows/sim.yml` 在每次推送时构建、跑全部场景（含 ASan/UBSan），并保存报告与截图。CI 需要 `fonts-noto-cjk` 生成中文点阵字体。

当前测试：模拟器自检（4 个档案，32 项检查）、确定性、主页场景（2 个 Plus 档案）、阅读器场景（2 个 Plus 档案）、可移植性冒烟（RK3566 类、桌面 LCD）。

## 5. 模拟器已经发现并处理的问题

| 发现 | 数据 | 处理 |
| --- | --- | --- |
| **内部 RAM 是第一约束** | 悲观档 96 KiB 中，显示驱动 50 KiB，平台任务栈与控制块约 25 KiB；最初阅读场景只剩约 5 KiB | 界面与显示服务的栈改放 PSRAM（它们本来就要访问 PSRAM 帧缓冲，写 Flash 时反正会冻结）；LVGL 的所有分配放 PSRAM（默认策略下它的小块分配悄悄吃掉约 3 KiB 内部 RAM）；现在低水位约 7.4 KiB。仍需：DMA 预留从 64 KiB 按实际需求压到 ≤32 KiB（模拟中 DMA 池几乎未用）、平台任务栈按实测收紧、显示驱动守住 ≤50 KiB |
| **翻页时间构成** | 按键 → 去抖 20 ms → 界面重绘并旋转约 90 ms → 显示服务拷贝约 33 ms → PMIC 上电 140 ms → GL16 592 ms，合计约 0.9 s；交互期电源保持时约 0.75 s | 预算 p95 ≤ 1 s。进一步优化方向：正文直接画进原生帧缓冲（省去 LVGL 重绘，约 −90 ms）；按键一按下就预先给 PMIC 上电（与渲染并行，最多 −140 ms）；实测后调整帧时间与相数 |
| **按下反色让反馈慢一倍** | 没有快速 A2 波形时，“按下反色、松开恢复”要两次 DU（各约 320 ms），真正的结果晚一个波形才出现 | 默认不做按下反色，用动作结果本身作为反馈（一次 FAST 刷新）；需要时用 `ink_ui_style_button_pressable` |
| **滑动被当成点击，翻了两页** | LVGL 对任何没有滚动的松手都发“点击”；阅读器同时收到“滑动”和“点左区” | 输入服务把完成滑动的松手标记出来，界面运行时据此取消这次点击 |
| **换屏被拆成两次刷新** | 点按钮留下的 FAST 区域提示落在新屏幕上，先用 DU 刷一块黑白、再 GC16 全屏，可见时间到 1.3 s | 换屏时清空区域提示，整帧一次 FLASH_UI |
| **打开书的首次可见变化 415 ms** | 加载 250 KB 文本 + 排版首页都在首帧之前 | “先反馈再打开”：被点的控件立刻反色（一次 FAST，首次变化约 160 ms），之后再建新页面 |
| **Flash 读写与刷新冲突** | 写 `/user`（擦除 45–300 ms）会冻结 PSRAM 上的送行任务，行队列只能撑 0.5 ms，必然欠载（真机上是可见的花屏）；读 `/user` 也会短暂关缓存 | 存储服务等屏幕空闲并持 Flash 守卫；欠载模型按行队列可撑时长判定；预算要求零欠载 |
| **10 ms 节拍** | 上游 `CONFIG_FREERTOS_HZ=100`：5 ms 的延时实际变成下一个节拍（最多 10 ms）；超时同样取整 | OSAL 规定“至少延时 N，按节拍向上取整”，模拟器照此执行；是否改 1000 Hz 留待实测功耗后决定 |

## 6. 可信度与局限

能在电脑上验证的：任务划分与优先级是否会互相饿死、内存是否够用以及碎片、刷新调度是否正确、时延由哪些部分构成、Flash 写入时机是否安全、断电后数据是否完好、不同分辨率与屏幕类型下界面是否成立。

还不能或只能粗略验证的：

1. **CPU 成本是估算。** 标注模式按每像素、每字形、每字节的周期数计费，LVGL 内部绘制按每像素 25 周期平摊。第二级（RISC-V 指令级模拟器 + 按官方 CoreMark 校准）正在做，结果出来后替换 `costs_cycles`；到货后再用实测校准。
2. **没有缓存与总线争用模型**：PSRAM 带宽、两核同时访问的相互影响只体现在固定的每字节成本里。
3. **栈用量**是主机上的悲观估计；权威数字要用 RISC-V 编译的 `-fstack-usage`。
4. **还没有网络、音频、4G 模型**：网络参数已写进档案，模型在做中枢连接时加入。
5. **波形时间来自上游代码与悲观帧时间**；温度对相数的影响未建模（上游也没有温度补偿，见 RK-14）。
6. **电流全部是估算**，只能比较方案，不能承诺续航。

## 7. 平移到真机

1. `ports/esp32s31`：用 FreeRTOS 实现 `osal.h`（`xTaskCreateWithCaps` 支持 PSRAM 栈、`heap_caps_*`、`esp_timer`），用上游驱动实现各 HAL（EPDiy 改造版、FT6336U、TPS65185、LittleFS、SDMMC）。系统与应用代码不改。
2. 到货第一周：读 `esp_psram_get_size()`、跑 SP-01（刷新时序）、`idf.py size`（静态内存）、Flash 擦写与停顿实测，把实测值写回档案。
3. 同一批场景在真机上跑（按键注入或人工操作），对比预测与实测：预测不得比实测乐观超过 10%，否则调整参数并在档案里记录来源变化。
