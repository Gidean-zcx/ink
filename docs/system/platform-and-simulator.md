# 平台抽象与设备模拟器

版本：v0.5（2026-11-02）。状态：第一级模拟器 + 第二级指令级校准已实现；系统纵切（主页、书架、阅读器、中枢连接、AI 按键与语音提问、动作注册表与 AI 工具调用、电源与待机）全部在 CI 中按预算自动检查；两次独立评审指出的模拟器乐观之处均已修正（§5.2、§5.3）。v0.3 的主要变化：墨水屏送行任务改为逐行建模并用指令级实测校准，结论是“送行算力是刷新管线的关键约束”（§5.4，决策 D-35）；Flash 读写一律不与刷新重叠（D-36）。v0.4：电源服务（活跃/空闲/锁屏、空闲降频、按片浅睡、唤醒键）与待机场景，模拟器为此加了主频、浅睡与按状态的电流统计；待机耗电估算见 §5.5（决策 D-37～D-39）。v0.5：用户另一会话研究的 PQ-BN 直驱刷新算法作为第二种显示驱动接入（逐像素异步、没有全局锁），在指令级模拟器上重测了它的算力，并与 EPDiy 方案跑同一批场景（§5.6，[集成报告](../research/eink-refresh-integration.md)，决策 D-40）。对应需求 R-034、R-035，想法 I-035、I-036。

> 一句话：系统代码只认 `platform/include/ink/` 里的接口（OSAL + HAL）。同一份系统代码可以跑在模拟的 Plus 上，将来也能跑在真机、RK3566 这类 Linux 设备和桌面上；模拟器按“宁可悲观”的参数复现 Plus 的 CPU、内存、刷新、存储和输入，在电脑上就能发现卡顿、内存不够和刷新冲突。

## 0. 结论

| 问题 | 结论 | 依据 |
| --- | --- | --- |

## 1. 分层与移植

```
apps/            主页、书架/阅读器……（只调用 system 与 ink/*.h）
system/          显示服务（刷新调度器）、输入服务、界面运行时（唯一 LVGL 任务）、
                 存储服务（Flash 守卫）、中文排版、字体、中枢连接、AI 服务……   ← 与平台无关
platform/include/ink/   osal.h  hal_display.h  hal_input.h  hal_storage.h  hal_net.h
                        hal_audio.h  hal_codec.h  hal_power.h  hal_device.h  hal_assets.h
                        probe.h  rotation.h
ports/sim        模拟器（本仓库已实现）
ports/esp32s31   FreeRTOS + 上游驱动（到货前搭骨架，到货后实测）
ports/posix      pthread + Linux（RK3566 等 SoC、桌面；待做）
profiles/*.json  设备档案：每个数字都在这里，系统运行时按档案自适应
```

| 接口 | 内容 | 设计要点 |
| --- | --- | --- |
| `osal.h` | 任务、队列、互斥量（优先级继承）、信号量、软件定时器、带能力标记的内存分配、时间、CPU 成本标注 | 语义取最受限的 FreeRTOS：固定优先级抢占、同优先级按节拍轮转、互斥量不移交所有权；延时与超时“至少 N”，结束在 now+N 之后的第一个节拍（FreeRTOS 端口须按微秒时钟算目标节拍）；栈放 PSRAM 的任务**不得调用任何 Flash 接口**（读也不行）。在它上面正确的代码在 Linux 上也正确 |
| `hal_display.h` | 8 位灰度、原生方向；按“为什么变”提交区域；完成回调给出排队、开始变化、稳定三个时刻 | 不暴露 EPDiy；LCD 端口忽略波形；`hal_display_hold_power()` 用于交互期保持高压电源；`hal_display_wake()` 在手指按下/按键时提前给 PMIC 上电，让上电与界面渲染并行 |
| `hal_input.h` | 原生坐标的触摸与逻辑按键（AI、电源、音量、HOME、上一页、下一页、返回） | 手势在可移植的输入服务里识别，阈值按毫米 |
| `hal_storage.h` | `/user`（掉电安全、写入昂贵）、`/content`、`/cache` 三个卷 | 设备上分别是内部 Flash 的 LittleFS、TF 卡 FAT；Linux 上是目录 |
| `hal_net.h` | 链路状态（无 / Wi-Fi / 4G、信号）与变化回调；到中枢的 WebSocket：异步打开、整条消息收发（文本/二进制）、关闭 | 设备上是 lwIP + mbedTLS + esp_websocket_client（4G 经 NT26 的 UART 以太网）；Linux 上是主机网络；系统只看到“消息通道 + 链路状态”，重连与协议在可移植的中枢连接服务里 |
| `hal_audio.h` | 固定格式 16 kHz 单声道 16 位：麦克风按块回调（带“丢了多少”）、扬声器写入/排空、“现在写入的样本多久后听到” | 设备上是 BH1098G 经 I2S（ESP 为从机）、NS4150 功放，电源与 4G 共用一路；Linux 上是 ALSA；硬件采样率不同由端口重采样 |
| `hal_codec.h` | Opus 编解码（60 ms 一帧） | 编解码器随平台：S31 用乐鑫带汇编优化的 esp_audio_codec，Linux 用 libopus |
| `hal_assets.h` | 只读资源（字体等）内存映射，不占堆 | 设备上是 Flash 分区，经 64 KiB 共享缓存读取；`hal_asset_access()` 是给模拟器的提示（设备上为空），用来计缓存缺失 |
| `probe.h` | 系统上报“对用户重要的”指标，如“操作到首次可见变化” | 模拟器里进入指标、轨迹和 CI 预算；设备上进日志 |

换到 RK3566 / Linux / 别的分辨率时需要做的事：实现一个 `ports/posix`（约千行：pthread 版 OSAL、Linux 帧缓冲/DRM 或 rockchip-ebc 的显示 HAL、evdev 输入），写一份设备档案。系统、应用、字体、排版、刷新调度和测试场景不变。

## 2. 第一级模拟器：模型与参数

所有参数在 `profiles/metalio-plus.json`（悲观档，CI 的门槛）里，来源见[性能建模报告](../research/simulator/performance-modeling.md)和[指令级校准报告](../research/simulator/iss-calibration.md)。另有 `metalio-plus-psram16.json`（预期 CPU 成本，即“很可能的情况”；PSRAM 已实测为 16 MB，两档都按 16 MB）和 `metalio-plus-upstream-display.json`（上游显示管线：127 行队列、64 KiB LUT、PMIC 上电期间暂停触摸；只用来比较时间）。启动时会列出档案没写、用了默认值的参数（Plus 档案现为 0 个）。2026-11-03 起，PSRAM 容量、内部堆的区段结构、DMA 预留、Flash 型号与擦写时间按[第 0 步实机记录](../hardware/2026-11-03-phase0.md)改写，见 §5.7。

| 模型 | 做法 | 主要参数（Plus 悲观档） |
| --- | --- | --- |
| CPU 与调度（`sim/vtk`） | 每个系统任务是真实的线程，但同一时刻只放行一个（“接力棒”），由离散事件调度器按虚拟时间推进：2 核、固定优先级抢占、**同优先级按节拍轮转**、上下文切换与内核调用计费、空闲时间瞬间跳过。互斥量按 FreeRTOS：只给直接持有者继承优先级、持有任何互斥量期间不降回、不移交所有权。Flash 停顿期间所有任务冻结：一段计算即使在停顿登记前就开始了，跑到停顿起点也停下、停顿结束后才继续（评审二 M-B）。CPU 时间有两种算法：**标注模式**（默认，确定性）按代码里的成本标注计费，系统代码再加 I-cache 缺失系数；档案缺某个成本类会报警告而不是悄悄记 0；**实测模式**按主机 CPU 时间 × 换算系数 | 320 MHz（CoreMark 拟合 3.08/MHz）；内核调用 2 µs、切换 10 µs；节拍 100 Hz；长计算每 200 µs 可被抢占；I-cache 缺失 +15% |
| 指令级校准（`tools/iss`） | 自写 RV32IMAFC 指令级模拟器（顺序单发射流水线、分支预测、I/D 缓存、S31 内存映射），用 ESP-IDF v6.1 的 S31 编译选项交叉编译真实内核，测出每字节拷贝、每字形、每像素转换、JSON、解压、CRC 的周期数；按 CoreMark 与 P4/S3 的 PSRAM 实测拟合 | 悲观档取“×1.3 与慢角的较大值”，预期档取 ×1.3；文本排版、LVGL、堆管理仍是估计 |
| 内存（`sim/mem`） | 三个真实的 TLSF 堆：内部、DMA 预留、PSRAM。**内部堆由几个互不相连的区段组成**（最大块受最大区段限制），每段扣除设备分配器的控制开销；任务控制块、栈、队列、定时器都从内部 RAM 扣；分配顺序按 IDF 6.1 的 S31 能力表：DMA 与内部分配先用普通内部 RAM、再用预留，普通分配最后也会落进预留；按“标签”统计谁用了多少；内部与 DMA 的最大空闲块每次分配都记录 | 内部 80 + 16 KiB：结构实测，即一大段加顶部 16 KiB 一段，总量 96 KiB 仍是悲观估计；DMA 预留 64 KiB（出厂固件实测配置）；PSRAM 15.5 MiB（实测 16 MB 片）；每段控制开销 1.5 KiB |
| DMA 用户 | LCD bounce 缓冲（显示驱动）、4G UART 以太网的收发环（模组上电期间）、TF 卡每次传输的中转缓冲；I2S 录放音环随音频管线加入 | 4.8 KiB / 12 KiB / 4 KiB |
| 墨水屏 | 上电（Plus 三档：板级驱动对 TCA9555/TPS65185 芯片模型走真实上电顺序，约 125～140 ms，见 §5.8；上游显示管线档仍按固定 140 ms 并暂停触摸）→ **比对**（上游：对区域所在的整行做差分图，PSRAM 进出）→ 逐相播放 → **回写**（脏行拷回旧帧缓冲）→ 稳定。**每一相逐行规划**：两个最高优先级送行任务（栈在 PSRAM）把行转换进各自的行队列——上游固定奇偶分行，本端口“谁空谁取”；每行成本分三种（整行转换、只转换区域内的列、区域外的空操作行）；LCD 补缓冲中断占 0 核一部分，使 0 核送行变慢；预填够若干行后开始扫描，之后中断每 17 µs 取一行（同时预取两块 8 行的 bounce 缓冲）；某一行没按时备好就是**欠载**，按上游中止该波形并恢复（清屏 69 帧 + 完整 GC16）。一相的长度 = 预填 + 688 行扫描 + 帧结束开销，不足 12 ms 补足。送行任务一直占着核，直到自己最后一行入队（上游在满队列上空转），或只在计算时占核（“阻塞”方式）。Flash 停顿按虚拟时间纳入规划（不论何时登记）：送行任务冻结；补缓冲中断若不是 IRAM 安全（上游配置）则同时被屏蔽，停顿超过一块 bounce 缓冲即花屏；整屏闪刷用 48 相表；每相都清空字体缓存模型 | 端口：每行 31.8 µs（指令级实测 28.9 µs × 1.1）、预填 64 行、每任务队列 48 行、只转换区域列、谁空谁取、中断 IRAM 安全、LUT 1 KiB；整屏一相 12.9 ms、预填 1.0 ms、最小余量 46 行。上游复现：每行 33.4 µs、奇偶分行、预填 192、队列 127、比对整屏、“清屏”= 69 帧 + 48 相；一相 15.1 ms、余量 129 行。GC16 36 相（整屏 48）、GL16 37、DU 20；LCD 中断 10% |
| 墨水屏：PQ-BN 直驱（可选驱动，`display.driver = "pqbn"`） | 研究内核（`drivers/epd/pqbn_v4.c`）每相真的运行：UI 的更新换成 4 bpp 目标并标记 32×4 的 tile，驱动在有像素在动时连续出相，新更新加入下一相（没有全局锁）。每相：两个扫描任务（沿用送行模型，满队列时阻塞）按每行成本送行，行成本 = 空闲带 r_idle，或 r_band + r_tile × 本相在推的 tile；规划器是单独的任务，成本 = p_base + p_px × 访问的像素 + …（两者都由 `tools/iss/bench` 在研究场景上实测拟合）。内核要求规划下一相时本相扫描已经走过那些 tile，所以默认规划排在每相扫描之后（内核原样）；`plan_during_scan` 让两者重叠，代表“规划跟在扫描后面逐带进行或 tile 状态双缓冲”的改造端口。相时钟在两次驱动之间按真实时间前进（上限 255 相）；面板模型按满摆推数、首推粘滞、像素间离散推动光学状态，截图即模型状态。区域内 tile 全部静止才算完成；GC16 = 黑→白→内容的闪刷；可在相边界暂停给 Flash 让路 | 研究的面板假设：满摆 7.6 推、粘滞 0.3 / 120 相、离散 ±4%（未实测）；悲观成本：每行 43 / 1836 + 216 周期 × tile，规划 26.7 万 + 248 周期 × 像素；预算 8000 像素/相、关自动运动、规划在扫描之后、两个扫描任务、预填 32 行、队列 2×24 行 |
| 触摸、按键、I2C | 手指按下 20 ms 后控制器报中断 → 驱动任务经 100 kHz 共享总线读 9 字节 → 按 10 ms 轮询直到抬起。**按键按真实来源**：AI 键直连 GPIO（去抖 20 ms）；电源/音量在 IO 扩展芯片上（中断后读两次 I2C）；HOME/上一页/下一页是触摸控制器识别的盖板触摸键（和手指一样要检测、读总线、轮询；每个键是控制器的一个触点，与手指共用 2 个触点，所以两个键可以同时按住）。PMIC 上电、波形开始/结束的 IO 扩展写入都占同一条总线。事件带物理发生时刻，测的是端到端时延。触摸控制器一段时间没被触摸就转入慢速“监视”扫描，第一下触摸（含盖板键）要多等最多一个监视周期；系统空闲时后台总线轮询（电量计等）放慢 | 本系统端口用总线互斥，PMIC 只在事务期间占总线（约 10 ms）；上游档案在整个上电期间暂停触摸（140 ms）。监视模式 10 s 后进入、最多多等 60 ms（估计，未对照数据手册）；后台轮询 500 ms，空闲时 2 s |
| 内部 Flash（`/user`） | LittleFS 跑在模拟 NOR 上，按 IDF 6.1 的调用方式计停顿：**一次 `esp_flash_write` 每 8 KiB 一个关缓存窗口**（LittleFS 从内部缓冲直写），窗口内 SPI1 每条命令最多 64 字节、每条编程命令计“首字节时间 + 按长度分摊的页时间”；读按 64 字节一条命令计；每次擦一个扇区一个窗口（IDF 只在多扇区擦除之间让出，LittleFS 每次只擦一个）。**每个窗口内两个核上所有任务冻结**；**栈在 PSRAM 的任务碰 `/user` 直接判为死机**（同 ESP-IDF 断言）；读进 PSRAM 时按 IDF 申请内部中转缓冲（取所需、16 KiB、最大空闲块三者最小，失败即报错）；波形播放期间发生的 Flash 操作单独计数（系统规则是零，见 D-36），并先计入 IDF 跨核 IPC 等最高优先级送行任务让出的时间；每次调用与 CRC 计 CPU；NOR 只能 1→0；可保存镜像跨次运行；`powercut` 撕裂进行中的写入 | 板上 Flash 型号未核实，取通用悲观值：擦除 45/400 ms、页编程 0.7/3 ms、编程命令首字节 30 µs、每条 SPI1 命令 1.5 µs、原始读 20 MB/s（实际约 13.6 MB/s）；用户分区 1408 KiB；CI 另用“老化”镜像和最坏擦写时间跑阅读场景 |
| 缓存 | 内存映射的字体：64 KiB 两路 D-cache 行模型，缺失一次按 DIO 80 MHz 取 64 字节计约 3.6 µs；比对和每一相的送行都把 PSRAM 帧缓冲流过同一缓存，模型随之清空 | 阅读场景约 2.5 万次缺失 |
| TF 卡（`/content`、`/cache`） | 主机目录 + 每次操作延迟 + 带宽 + 每写 4 MB 一次 250 ms 的忙等（卡内部整理）；每次传输占一块 DMA 中转缓冲 | 读 4 MB/s、写 1 MB/s、1.5 ms/次 |
| 电源与待机（`hal_power_sim.c`） | 资源引用计数、各部件电流与电量估算。**主频随系统状态**：活跃时全速，空闲与锁屏时降到空闲主频，有人持升频锁（刷新、音频编解码、TLS 握手）时全速；按周期计费的 CPU 工作在低主频下相应变慢，基础电流跟随主频。**待机 = 显式浅睡**（同上游，60 s 一片）：进入序列（PMIC 休眠、TF 卡停放、断电源）→ 其他任务全部冻结、各部件停止耗电（保持 4G 时换成模组寻呼电流）→ 只有已武装的唤醒源（电源键、AI 键、定时器、RTC、4G）能叫醒，过芯片唤醒延迟后执行恢复序列（按键唤醒还要重挂 TF 卡）；睡眠中的触摸和其他按键丢失；进入序列结束时再查一次显示与音频是否空闲、系统是否要取消。按系统状态分别统计平均电流（`power.avg_ma.locked` 即待机电流）和锁屏时间里的睡眠占比 | 全速 320 MHz 25 mA、空闲 160 MHz 20 mA；整板浅睡 1.5 mA，保持 4G 另加 5 mA（模组 3.3–4.1 mA + 同一路电源上的蓝牙音频芯片）；进入 200 ms、恢复 30 ms、芯片唤醒 2 ms、TF 卡重挂 100 ms；电池 1700 mAh（上游测试放出 1870.7 mAh × 0.9）。全部为估算，只用于方案比较 |
| 资源分区 | 字体等只读资源计入 6 MiB 资源分区 | — |
| 网络链路（`hal_net_sim.c`） | 往返时延按对数正态分布（由 p50/p99 推出）、带宽（4G 受 UART 上限）、丢包重传（**同一连接按 TCP 保序：重传的那条会挡住后面的消息**）、4G 空闲后恢复（RRC 恢复额外时延 + 尾巴期耗电）、随机断网；连接 = DNS + TCP + TLS（握手 CPU 与内部/PSRAM 内存计费）+ WebSocket；链路断开后连接要等“死连接检测”才发现 | 4G：p50 80 ms / p99 400 ms、1.2 Mbit/s（UART 上限 1.6）、丢包 1%、空闲 10 s 后恢复多 300 ms、每小时断网 1–2 次各 2–5 s；TLS 内部 6 KiB + PSRAM 40 KiB、握手 9600 万周期（约 0.3 s）；死连接 5 s |
| 音频（`hal_audio_sim.c`） | I2S DMA 环：麦克风每 15 ms 完成一个描述符，环 4 个（60 ms）；平台音频任务（栈在 PSRAM）取走并转成单声道，落后超过 4 个就覆盖最旧的（丢音，计数）；扬声器每 15 ms 播一个描述符，没人补的描述符播零（按 IDF 的 auto_clear 配置），**只有在声音中间断掉才算欠载**（计次数与断音时长），静音之后的空播只算“空闲”；功放经 IO 扩展打开再等稳定；录放各占一块 DMA 内存；扬声器实际播出的声音（含断音）写成 `speaker.wav` | 环 4×240 帧、每帧 8 字节（32 位立体声）、每方向 7.5 KiB DMA；功放启动 30 ms |
| 编解码（`hal_codec_sim.c`） | 替身 Opus：包长同真 Opus（24 kbps 时 180 字节，静音包很小），带音量与音高摘要，解码成可听的音调；每帧 CPU 与状态内存按档案计 | 编码 240 万周期/帧（约占一核 12%），解码 45 万；状态 30/27 KiB 放 PSRAM（估计，待指令级或实测） |
| 中枢（`sim_hub.c`） | 按规则文件应答 JSON-RPC：思考时长、分段流式推送、错误、不应答（测超时）；默认规则含 `hello`、`ping`、`ai.ask`、**语音轮 `ai.listen`**（收麦克风帧，收到结束通知后：0.3 s 给识别文字、思考 1.4 s 后发文字与 TTS 音频帧（比实时快 2 倍发送）、带轮次号的 `ai.tts.end`、结果）；规则可按轮次（`turns`）向设备发 `tools/call`（可故意用旧的页面代次测“过时”），并用回执里的 `say` 作为回答 | `--hub 规则.json` |

确定性：标注模式下同一场景重复运行，指标文件与截图逐位一致（CI 中对自检和阅读场景各有专门测试）。实测模式用于交叉核对，不进 CI 预算。

## 3. 怎么用

```bash
cmake -S . -B build && cmake --build build -j && ctest --test-dir build --output-on-failure
./build/ink-sim --profile profiles/metalio-plus.json --script tests/scenarios/reader_basic.script \
    --budget tests/scenarios/reader_basic.budget.json --assets build/assets --content build/test-content \
    --out out/ --trace --frames
```

- **场景脚本**：按虚拟时间写手指、按键、截图、电量、断电（`powercut`，或 `powercut write 2` 在之后第 2 次 Flash 写入中途断电）、切换网络（`net lte|wifi|none`）、断网（`outage 6s`）、换 SIM 卡（`sim external|internal none|data|sms|voice`）、设备朝向（`orient portrait|upside_down|landscape_left|landscape_right|face_up|face_down`）、晃动（`shake`）、时钟掉电（`rtc lost`）、周围的网络（`wifi on|off [rssi]`、`cell on|off [rsrp]`）、来短信（`sms-in 号码 内容`）、来电（`call-in 号码`）、对方接听或挂断（`remote answer|hangup`）等动作；坐标可写 `116dp`、`50%`，同一脚本适用于所有屏幕。CI 场景用 `--no-random-outages` 关掉随机断网；`--flash-timing typ|max|tail` 选 Flash 擦写时间的取法。
- **输出**：`metrics.json`（每个任务的 CPU、栈、内存标签、刷新次数与波形、时延分布、Flash 停顿……）、`final.png` 与 `snap-*.png`（按竖屏方向、含残影）、`frames/`（每次刷新一张）、`trace.json`（用 https://ui.perfetto.dev 打开，可看到每个核上每个任务何时运行、每次刷新与 Flash 停顿）。
- **预算**：`*.budget.json` 写“这个场景必须满足什么”，例如翻页 p95 ≤ 1 s、内部 RAM 低水位、零欠载、零警告；超出则 CI 失败。条目还可写 SRS 目标（`target_max` + `srs`）：没达到时输出“SRS GAP”并计入 `srs_gaps`，不让 CI 失败——差距一直可见，等实机数据再定。
- **CI**：`.github/workflows/sim.yml` 在每次推送时构建、跑全部场景（含 ASan/UBSan），并保存报告与截图。CI 需要 `fonts-noto-cjk` 生成中文点阵字体。

当前 38 项测试：模拟器自检（4 个档案，最多 36 项检查，含“波形中途写 Flash 必须判为欠载”）、PSRAM 栈任务读 Flash 必须死机、两项确定性、主页与阅读器场景（悲观与预期两档）、AI 提问场景（4G，含一次断网）、AI 工具调用场景、待机场景（锁屏后马上解锁、锁屏浅睡 5 分钟、睡眠中的触摸与盖板键不得漏进应用、电源键与 AI 键唤醒、10 分钟自动锁屏）、阅读中途断电再开机、老化文件系统 + 最坏擦写时间、上游显示管线对照、可移植性冒烟（RK3566 类、桌面 LCD）、PQ-BN 直驱档案上的阅读场景（翻页门槛单独设为 1.1 s，目标值仍是现方案的 722 ms）与 AI 场景（与 EPDiy 方案同一套预算）及其可移植性冒烟、PQ-BN 在相边界暂停给 Flash 写入让路的场景、两个盖板键同时按住（下一页未松开就按主页，HOME 不得被推迟）、指令级模拟器自检；2026-11 审计复核又加了四个场景：连续阅读不停顿时也要落盘（`reader_continuous`）、每秒 5 次连续翻页时每次都要翻到且等待有上限（`reader_rapid`）、关闭 AI 面板后迟到的回答语音不得播放（`ai_dismiss`）、打不开的书上翻页不得崩溃（`reader_empty`）。见[审计记录](../audits/README.md)。屏幕电源链路又加了两项（§5.8）：VCOM 与面板不符必须报警，2% 的 I2C 传输超时时驱动必须靠重试恢复。另有整块板的接线自检（`selftest-board-wiring`：马达、P12 共享复位与 P14 共享电源对 4G 模组和触摸芯片的影响、时钟闹钟从待机中唤醒芯片、加速度计的重力与运动中断、共用 GPIO2 时按键照常、最后关机脉冲断电），4G 模组自检（`selftest-sim-slots`：自研 NT26 驱动对着模组模型在线切卡、拔掉在用的卡、切到空卡槽再切回、模组软复位后自行重新注册）和桌面模拟器的无界面测试（`gui-smoke`）：在窗口里用鼠标点开书架、打开一本书、点“下页”盖板键，检查系统收到触摸和翻页。2026-11-03 Codex 审计（[记录](../audits/README.md)）之后又加了三项：屏电源上电失败时刷新必须失败、面板不变（`scenario-home-panel-power-dead`）；按住 AI 键时关闭面板，录音必须当场停止（`ai_dismiss_held`）；系统服务检查（`systest-services`：大文件替换小文件后不得读到旧缓存）。接线自检同时加了浅睡：睡眠中各部件的状态（扩展芯片方向、P05/P14、屏电源脚、加速度计、前光）、外设忙时拒绝、电源键短按与按住进睡眠的唤醒、P16 被拉低时不用它唤醒。

### 3.1 桌面模拟器（R-042，D-43 暂定 A）

`ink-sim-gui` 把同一套模拟放进窗口，像 Android Studio 的模拟器那样用：

```bash
./build/ink-sim-gui                      # 默认：预期档、构建出的字体和样书、持久的 Flash 与 SD
./build/ink-sim-gui --profile profiles/metalio-plus.json --speed 2   # 换档案、两倍速
```

- **左边是设备**：屏幕按墨水屏的样子显示（含残影；系统开前光时按冷暖比例染色），刷新完成才变，和真机一样有延迟。鼠标左键就是手指，按住拖动是滑动。屏幕下方三个盖板键在官方的触摸坐标 X=100/200/300 上（HOME、返回/上页、下页）；右侧是电源键、音量+、音量−，左侧是 AI 键（BOOT）。键在外壳上的位置是示意，官方没有公开外壳图。顶部指示灯显示“刷新中”“待机”“充电”“振动”“前光”。
- **快捷键**：空格 = AI 键（按住说话），P = 电源键（按住 3 秒即长按），`=`/`-` = 音量，H = 主页，←/→ = 上页/下页；按住 Shift 悬停屏幕可看触摸坐标。
- **右边是硬件控制**：暂停/继续与 0.25×～10× 倍速（暂停时整台设备冻结，虚拟时间不走）；喇叭声音放到电脑上；麦克风可选电脑麦克风；摄像头画面来自电脑摄像头（可切测试图案），并显示设备最近拍的一张；短信与电话的“外面的人”（发短信给设备、打电话给设备、对方接听或挂断）；网络只设周围的信号（有没有 Wi-Fi、4G 覆盖与强弱），用哪条由系统决定；电量与 USB 充电（电量计读数、充电电流）；设备朝向和“晃一下”（加速度计），时钟芯片的时间；网络在 4G、Wi-Fi、无网络之间切换，或断网 5 秒；4G 的两张卡（外置卡槽、内置卡）各插什么卡（没有、只有流量、加短信、加通话），以及模组的状态（卡槽设置、在用的卡、是否注册）；窗口只模拟硬件，切卡由系统经 AT 命令完成（R-043、R-044）；麦克风听到的声音（说话、安静、噪声）；“拔掉电池”掉电（正在写的 Flash 会写坏一半）；CPU 两个核的占用（按档案折算到 S31）、内部 RAM 与 PSRAM 余量。
- **下边是日志**：系统日志和模拟器的提示、警告都在这里，可筛选；终端里同样有一份。
- **数据**：Flash 镜像和 SD 卡目录默认在 `build/gui-data/`，重启后书签、设置都还在；截图和 `metrics.json` 在 `build/gui-data/out/`。“重启设备”和崩溃、掉电后的“重新开机”都是重新启动整个程序，等于给设备重新上电。
- **调试**：系统代码和窗口在同一个进程里，可以用 `lldb ./build/ink-sim-gui`（Linux 用 gdb）或 VS Code、Xcode 下断点、单步、看变量；macOS 第一次调试时系统会要求授权开发者工具。设备死机（panic）时窗口不退出，保留最后的画面、原因和日志。

**结构**：窗口跑在主线程（macOS 要求），模拟在另一个线程里运行原来的 `sim_main()`，固定为实时模式、没有默认结束时间。两边只通过 [ports/sim/sim_gui.h](../../ports/sim/sim_gui.h) 交互：

- 窗口的动作（触摸、按键、电池、网络……）作为外部事件注入（`vtk_inject_external`），在模拟里以中断上下文执行，和场景脚本走同一套接口，所以时序模型（触摸控制器、IO 扩展器、I2C 总线）一样生效；
- 画面和状态由窗口每 33 ms 请求一次，模拟在事件里把可见图像（屏幕值加残影，按竖屏方向）和统计数据交给窗口；画面没变就不拷贝；
- 内核新增 `vtk_set_realtime_speed` 和 `vtk_set_paused`，可从任何线程改速度或冻结，虚拟时间从当前位置接着走；不开实时模式的运行（全部场景测试）不受影响，确定性测试仍逐位一致。

依赖：SDL2（系统装了就用，Debian/Ubuntu 是 `libsdl2-dev`，macOS 可 `brew install sdl2`；没装时 CMake 自动下载 release-2.32.10 编译）和 Dear ImGui v1.91.9b（自动下载）。不想编窗口程序时加 `-DINK_GUI=OFF`。窗口的中文字体用构建时配置的 Noto Sans CJK，找不到再用系统的冬青黑体、华文黑体。

**和官方硬件的一致性**（R-043）：逐项对照见[模拟器与官方硬件的对照](../research/simulator/hardware-parity.md)。2026-11-03 第三轮后 21 项都一致（估计与假设见对照表）。总线上除摄像头外每颗芯片都有寄存器级模型，系统经本项目的驱动访问它们（D-41 A）：

- `drivers/board/metalio_board`：IO 扩展芯片的唯一实例与锁，屏电源、按键、马达、功放、共享复位与电源、关机脉冲都经它；`drivers/board/metalio_touch`：触摸坐标与盖板键；
- `drivers/ft6336u`、`drivers/bq27220`、`drivers/cx25601n`、`drivers/pcf8563`、`drivers/sc7a20h`、`drivers/nt26`；
- 新的 HAL：`hal_power_shutdown`、`hal_rtc_*`、`hal_accel_*`、`hal_camera_*`、`hal_uart_*`（蓝牙音频芯片）、`hal_modem_at` / `hal_modem_at_payload` / `hal_modem_urc`（4G 的 AT、短信、电话）、`hal_net_use`（系统选网）；`hal_power_battery` 在 Plus 上经电量计和充电芯片读；

### 5.1 系统问题

| 发现 | 数据 | 处理 |

| **内部 RAM 是第一约束** | 悲观档 96 KiB 中，显示驱动 50 KiB，平台任务栈与控制块约 25 KiB；最初阅读场景只剩约 5 KiB | 界面与显示服务的栈改放 PSRAM（它们本来就要访问 PSRAM 帧缓冲，写 Flash 时反正会冻结）；LVGL 的所有分配放 PSRAM（默认策略下它的小块分配悄悄吃掉约 3 KiB 内部 RAM）；现在低水位约 7.4 KiB。仍需：DMA 预留从 64 KiB 按实际需求压到 ≤32 KiB（模拟中 DMA 池几乎未用）、平台任务栈按实测收紧、显示驱动守住 ≤50 KiB |
| **翻页时间构成** | 按键 → 去抖 20 ms → 界面重绘并旋转约 90 ms → 显示服务拷贝约 33 ms → PMIC 上电 140 ms → GL16 592 ms，合计约 0.9 s；交互期电源保持时约 0.75 s | 预算 p95 ≤ 1 s。进一步优化方向：正文直接画进原生帧缓冲（省去 LVGL 重绘，约 −90 ms）；按键一按下就预先给 PMIC 上电（与渲染并行，最多 −140 ms）；实测后调整帧时间与相数 |
| **按下反色让反馈慢一倍** | 没有快速 A2 波形时，“按下反色、松开恢复”要两次 DU（各约 320 ms），真正的结果晚一个波形才出现 | 默认不做按下反色，用动作结果本身作为反馈（一次 FAST 刷新）；需要时用 `ink_ui_style_button_pressable` |
| **滑动被当成点击，翻了两页** | LVGL 对任何没有滚动的松手都发“点击”；阅读器同时收到“滑动”和“点左区” | 输入服务把完成滑动的松手标记出来，界面运行时据此取消这次点击 |
| **换屏被拆成两次刷新** | 点按钮留下的 FAST 区域提示落在新屏幕上，先用 DU 刷一块黑白、再 GC16 全屏，可见时间到 1.3 s | 换屏时清空区域提示，整帧一次 FLASH_UI |
| **打开书的首次可见变化 415 ms** | 加载 250 KB 文本 + 排版首页都在首帧之前 | “先反馈再打开”：被点的控件立刻反色（一次 FAST，首次变化约 160 ms），之后再建新页面 |
| **Flash 读写与刷新冲突** | 写 `/user`（扇区擦除典型 50 ms、最长 240 ms，PY25Q128HA 手册）会冻结 PSRAM 上的送行任务，行队列只能撑 0.5 ms，必然欠载（真机上是可见的花屏）；读 `/user` 也会短暂关缓存 | 存储服务等屏幕空闲并持 Flash 守卫；欠载模型按行队列可撑时长判定；预算要求零欠载 |

| **内部 RAM 指标口径** | 只看 96 KiB 内部池时低水位只剩 1.3 KiB（AI 场景）；但 ESP-IDF 的 64 KiB DMA 预留池对“只要内部 RAM”的分配同样可用（普通 malloc 才不能用） | 预算改为两条：内部 + DMA 合计可用 ≥ 32 KiB（`mem.internal_total`）、DMA 池至少留一半给 I2S/SDMMC/Wi-Fi；主任务栈 8→4 KiB。单独的内部池数字仍在报告里 |
| **语音一轮的时间与资源（悲观档，4G）** | 按键到听见提示音 61 ms；松开到看到识别出的问题 1.4–1.6 s、第一段文字 2.1–2.8 s、听到第一个字 2.4–3.1 s（中枢思考按 1.4 s 计）；刷新期间送行任务占满两核，编码落后，上传完成最多在松开后 0.63 s；麦克风零丢音、扬声器零欠载；回答播放期间翻页的阅读位置保存等了 6–11 s | 满足 SR-UX-01a/05（靠提示音）与 06b；06a（≤3 s）余量不大。代价：DMA 预留里录放各占 7.5 KiB，内部 + DMA 最坏时余量降到约 32 KiB，把 WebSocket 与 4G 串口网卡两个任务的栈移到 PSRAM（端口决定，它们不碰 Flash）后回到 40 KiB |
| **4G 空闲恢复让提问多等** | 4G 空闲 10 s 后第一次发包要先恢复（多约 0.3 s 加一个往返）；首次连接（DNS+TCP+TLS+WS+hello）约 1.0–1.6 s | 按下 AI 键就预连接（说话的 1–2 s 内连好）；松开到第一段文字可见约 2.0–2.2 s，其中中枢思考 1.4 s；断网时约 4.3 s 显示“连接中断”提示 |

| **10 ms 节拍** | 上游 `CONFIG_FREERTOS_HZ=100`：5 ms 的延时实际变成下一个节拍（最多 10 ms）；超时同样取整 | OSAL 规定“至少延时 N，按节拍向上取整”，模拟器照此执行；是否改 1000 Hz 留待实测功耗后决定 |
| **静音里的“欠载”是假象，真问题是编码挡住了补扬声器** | 按 AI 键后的提示音播完、等 TTS 时，刷新期间编码器占着音频任务，扬声器环流干，每轮报 18–19 次欠载；但当时要播的本来就是静音 | 模型改成 IDF 的 auto_clear 语义（只有声音中间断掉才算欠载）；服务不再用 CPU 喂静音、每编一帧补一次扬声器、提示音缩到能一次写进 DMA 环（60 ms）；两个 AI 场景欠载为 0 |
| **网络模型会让消息乱序** | 每条消息的往返时延独立随机、重传只推迟那一条，晚到的 TTS 帧会落在“TTS 结束”之后 | 同一连接按 TCP 保序（重传挡住后续消息）；设备端 `ai.tts.end` 带轮次号，旧一轮的结束不再把新一轮的回答静音（原先是真缺陷） |
| **Flash 读也会撞上刷新** | 原先只有写入等屏幕空闲；读 `/user`（如打开书时读阅读位置）照样关缓存，在上游配置下补缓冲中断被屏蔽，跨核 IPC 还要等送行任务让出（模拟中一次等了 7 ms）| 规则改为“任何 Flash 操作都不与波形重叠”（D-36）：读也持守卫；为避免点书多等一次刷新（约 0.23 s），加了小文件读缓存与书架预取，点书时的读改为零等待 |
| **锁屏标记还没画上去，芯片就睡了** | 第一次跑待机场景：锁屏后 0.1 ms 就进入浅睡，界面任务还没画标记就被冻结，截图里没有标记，唤醒后才画出来；电量统计显示刷新电流在整段睡眠里一直“开着”——那是一次被冻结在半途的刷新 | 睡前必须“安静”：界面没有未处理的消息和未渲染的刷新、显示服务没有排队或正在播的刷新、存储服务没有排队的写入，才睡。显示服务的忙计数改为“发送前加一、处理完再减”，消息出队到登记之间不会读成 0；HAL 在进入序列结束时再查一次。现在锁屏到入睡约 1.05 s（标记的 FAST 刷新 + 安静检查） |
| **刚锁屏就解锁，设备“死”一分钟** | 浅睡的进入序列约 200 ms（PMIC 休眠等）；这期间按电源键，输入服务解锁了，芯片却照样睡下去，要等下一次定时唤醒（60 s）才恢复 | 睡眠配置加取消回调：进入序列结束、真正睡之前问电源服务“还要睡吗”（原子读锁屏状态，不阻塞；真机在挂起调度器后调用）。场景里专门在进入序列中按一次电源键：0.71 s 解锁可见 |
| **等 AI 回答时降频** | 按 AI 键 5 s 后没有输入就进入空闲，回答文字的解析和绘制跑在 160 MHz | 有用户在等的网络传输（持“网络”需求）期间保持活跃全速，同上游“设备不空闲时不进 AppIdle”；音频不算（编解码自己持升频锁） |
| **锁屏标记显示成方框** | 界面字体（Montserrat）只有拉丁字母 | 标记改用中文点阵字体（同主页按钮的做法） |

### 5.2 第一次独立评审指出的模拟器乐观之处（2026-11-02，已全部处理）

| 评审发现 | 影响 | 处理 |
| --- | --- | --- |

“首次变化 p95”一列 2026-11-03 按审计复核重跑：A、B、E～H 都是 336 ms，原表的 282 ms 是早期版本的数字，其余各列与重跑一致（[审计记录](../audits/README.md) AUD-019）。

读法：

1. **送行任务的速度决定能不能用。** 两个任务合计的出行速度必须不低于扫描速度（17 µs 一行），差额只能靠预填补。上游靠 192 行预填和两条 127 行队列（约 77 KiB 内部 RAM）在拟合成本下留出 129 行余量；本端口把队列压到 48 行（约 29 KiB）省下内部 RAM，代价是必须让送行更快：谁空谁取（两核负载均衡）、只转换区域内的列、优化查表代码（四张预移位小表、掩码并入同一遍，指令级实测 −13%）。
2. **余量不宽。** 每行成本超过约 34 µs，本端口设计就会花屏（C、D）；上游设计在慢角也花屏（A′）。退路有两个：预填 128（G，+10 KiB 内部 RAM，翻页 +45 ms）或降像素时钟到 20 µs 一行（H，翻页 +80 ms）。到货后第一件事是读上游自带的 `EpdTiming` 日志（每相周期、扫描时间）并测每行准备时间，再定档。S31 的向量扩展（XespV）能否用于查表要查清：指令级模拟器不建模它，若可用，余量会大得多。
3. **刷新期间的 CPU。** 空转的送行任务占核到本相最后一行入队，刷新期间别的任务只在每相末尾有约 1–2 ms 可用；改成阻塞（E）后预渲染从 216 ms 降到 40 ms、点书快 90 ms。音频在 B 下仍零丢音、零欠载（每相末尾的窗口够补 60 ms 的环）。
4. **翻页与 SRS。** 一相按“预填 + 扫描 + 开销、不足 12 ms 补足”推出后，翻页稳定 p95 0.72 s（原先按 16 ms 帧估为 0.85 s），离 SR-UX-02 的 0.6 s 仍差约 0.12 s：GL16 的 37 相本身就要约 0.48 s。到 0.6 s 需要更少相数的正文波形或实测更短的相，这仍是到货后第一批测量。

### 5.5 待机与续航估算（悲观档，全部为估算）

电流全是估计值（档案 `power` 一节写明了来源与假设），这里的数字只用来比较方案、找出大头，到货后由 SP-14（整机电流）、SP-10（可接听待机）实测替换。

| 状态 | 平均电流 | 构成 |
| --- | --- | --- |
| 活跃（正在操作） | 约 48 mA | 全速主控、刷新、4G 驻网 |
| 空闲（在读一页） | 28 mA（不降频 33 mA） | 主控 20 mA + 4G 驻网 8 mA |
| 锁屏待机，4G 保持在线（可接听） | 约 6.6 mA（长时间待机）；待机场景平均 7.2 mA（含三次锁屏/解锁过程） | 整板浅睡 1.5 + 4G 那一路 5 + 每分钟醒一次约 0.1 |
| 锁屏待机，4G 断开（上游做法） | 约 1.6 mA；场景平均 2.3 mA | 浅睡 1.5 + 每分钟醒一次 |

按电池 1700 mAh 推算：只待机，保持 4G 约 10.7 天，断开约 44 天；按 SR-NF-01 的一天（读 1 小时约 30 mAh + 听 1 小时约 60–70 mAh，后者未建场景 + 其余 22 小时待机），保持 4G 约 7 天，断开约 13 天。结论：

1. **可接听待机占一天耗电的六成**，最大的杠杆是 4G 模组的寻呼周期：厂商资料里长寻呼周期的空闲电流只有 0.17–0.27 mA（短周期 3.3–4.1 mA），若能用上，保持在线的待机可降到约 2–3 mA；同一路电源上的蓝牙音频芯片待机电流也要实测。这决定 D-37 的取舍，SP-10 实测优先。
2. 每分钟一次的定时唤醒只占约 0.1 mA，60 s 一片可以保留；空闲降频每小时阅读省约 5 mAh（D-39）。
3. 锁屏前忘记锁屏（等自动锁屏）的代价：每次约 (28 − 6.6) mA × 锁屏时间，10 分钟约 3.5 mAh（D-38）。

### 5.6 PQ-BN 直驱刷新算法：集成与复核

**在 macOS 上跑测试**（2026-11-03 起全部通过）：Apple clang 17、arm64 上 32 项全过，`-Werror` 与 ASan/UBSan 构建也全过；三次并行运行，各任务的栈估计逐位一致。模型输出与改动前逐位一致（34 份指标、395 张截图），只有栈估计不同。

原来失败，是因为任务栈估计的口径（[D-42](../decisions/README.md)）：

- **原口径**：扫描任务的整条主机栈，减去一个空探针任务的用量。两者都包含内核在任务线程上做的事（pthread 等待、事件回调、跟踪钩子、线程退出）和模拟器自己的记账，深度随主机的 libc 和调度时机变化：
  - macOS 上探针每次运行差 164 字节，所有估计跟着变，确定性测试因此随机失败；
  - `main` 的 6～7.9 KiB 主要来自开机时模拟器把 `--content` 复制到模拟 SD 卡，于是超过 4 KiB，触发“零警告”预算；开 `--trace` 时探针约 2.8 KiB，估计还随跟踪开关变；
  - Linux 上探针是第一个退出的线程，glibc 的 `pthread_exit` 要回卷并加载 `libgcc_s`，探针用了 9016 字节（CI 诊断实测），所有估计都减去它，18 个系统任务里 11 个被压到下限 256 字节，所以 Linux 上几乎不报警；
  - ASan 构建下，任务里再建任务时，macOS 上 ASan 的 `pthread_create` 拦截器用光了任务的 64 KiB 主机栈，4 个自检中止。
- **现口径**：每个任务的主机栈分成两段。内核在下面一段运行；模拟器在任务上下文里做的主机工作（指标、跟踪、警告、日志、截图与帧图、显示更新记账、主机文件与目录、资源文件读取、模拟器对象的主机堆）经 `vtk_host_call` 也到那一段。任务开始时先清掉主机线程启动留下的痕迹（glibc 留下约 1.9 KiB）。估计只扫上面一段、从任务入口量起，已退出的任务取退出前的值，再减去探针的用量（约 0.2 KiB）、加 256 字节的 RTOS 帧。Linux 上链接时立即绑定符号（`-z now`），动态链接器不会在任务栈上运行。

两种主机上的新估计（各场景取最大，字节；括号内为配置的栈）：

| 任务 | Linux（GCC、x86-64） | macOS（clang、arm64） | 原口径 Linux / macOS |
| --- | --- | --- | --- |
| 存储（3584） | 3384 | 3168 | 2224 / 3312 |
| 中枢连接（4096） | 3336 | 3392 | 432 / 2192 |
| `main`（4096） | 3112 | 2560 | 3344 / 7924 |
| 显示服务（3072） | 2296 | 2016 | 288 / 2096 |
| 界面（10240） | 5383 | 5616 | 4256 / 5504 |
| 墨水屏驱动（4096） | 1720 | 1648 | 1488 / 3040 |
| `i2c_bg`（2048） | 792 | 928 | 256 / 1776 |

“原口径 Linux”一列来自 CI 诊断（[run 41585010018](https://github.com/Gidean-zcx/ink/actions/runs/41585010018)），只含直接运行模拟器的测试，不含断电、老化镜像、确定性三项和之后新增的 6 项；其余三列是全部 32 项，Linux 新口径来自 [run 41589992162](https://github.com/Gidean-zcx/ink/actions/runs/41589992162)。存储和中枢连接两个任务离配置的栈最近。估计在主机上偏悲观（RV32 的栈帧更小），要不要加栈，以 S31 编译的 `-fstack-usage` 为准。没有真实代码的驱动不计在内，例如 SD 卡在模拟器里是主机文件，FatFS 的栈没有算。

### 5.8 芯片模型：屏幕电源链路（D-41 方案 A 第一步，2026-11-03）

**目的**：让真机上要跑的驱动代码先在模拟器里跑，靠芯片模型而不是固定时间来模拟。这样上电顺序错误、VCOM 设错、总线故障后的恢复，都能在电脑上发现；其中前两类在真机上可能伤面板。

**结构**：

| 层 | 文件 | 真机 | 模拟器 |
| --- | --- | --- | --- |
| I2C 主机接口 | `platform/include/ink/hal_i2c.h` | ESP-IDF `i2c_master`（端口层，待写） | `ports/sim/hal_i2c_sim.c`：每次传输按位时占用共享总线，交给该地址上的芯片模型；没有模型就 NACK |
| 芯片驱动 | `drivers/tca9555/`、`drivers/tps65185/` | 同一份代码 | 同一份代码 |
| 板级上电顺序 | `drivers/board/metalio_epd_power.c` | 同一份代码 | 同一份代码 |
| 芯片 | 实物 | — | `ports/sim/dev_epd_power.c`：TCA9555（0x20）与 TPS65185（0x68）的寄存器级模型，TCA9555 的 P00～P02 接 TPS65185 的 VCOM_CTRL、PWRUP、WAKEUP，P07 读它的 PWR_GOOD |

档案里 `display.pmic = "tps65185"` 的三个 Plus 档案（悲观、预期、PQ-BN）走这条路径，`power_up_us` 与 `touch_pause_during_power_us` 不再使用。上游显示管线档写 `"none"`，仍是固定时间，用来比较上游行为。

**驱动的依据**：

- 按 TI 数据手册的寄存器表独立编写；
- 上电和断电的顺序、寄存器值、等待时间沿用上游板级代码（CloudZao/Metalio-E-INK4-Plus @690a023 的 `epd_board_metalio_eink4_plus.c`），让真机收到和出厂固件相同的序列；
- 没有拷贝代码：上游的 `tps65185.c` 来自 LGPL 的 EPDiy；
- 有一处改动：重试 3 次仍失败时，上游会重启芯片，这里改为把错误交给调用方，由系统进入安全模式；
- 板上 VCOM 取 1200 mV，来自上游 `config.h`，出厂固件启动日志也印证了这个值。

**模型检查**（任何一条触发都会成为模拟器警告，CI 失败）：

- VCOM 驱动值与面板要求（档案 `panel_vcom_mv`，即面板标签上的值）不符；
- 波形开始时高压或 VCOM 没有就绪；
- 断电时 XOE 拉低不足 12 µs 就关了高压（面板规格 6.1）；
- 高压还开着就拉低了 WAKEUP。

**故障注入**：`--i2c-faults RATE[:DEVICE]` 让这一比例的 hal_i2c 传输超时，并按 50 ms 超时占住总线；加 `:pmic` 之类只对一个器件。每个器件用自己的随机序列，别的芯片多了或少了传输，不会改变这个器件在哪次出错（2026-11-03 起；CI 的故障场景用 `0.08:pmic`）。第 0 步在实机上见过一次这种情况：IO 扩展芯片写超时，接着屏幕电源上电重试。

**结果**：

| 项 | 数值 |
| --- | --- |
| 上电时间 | 由驱动自己的等待（两段 50 ms、轮询、一个节拍）和模型时序决定：p50 124.7 ms，最长 139.5 ms。原先固定为 140 ms |
| 阅读场景 | 9 次上电全部一次成功，没有顺序违规，VCOM 一直是 1200 mV |
| 2% 故障下 | 出现 1 次超时，引起 1 次重试，那次上电用了 380 ms；没有失败，没有无电扫描 |
| 对时延的影响 | 各场景在 ±1 ms 以内；AI 键提示音快了 9 ms，因为上电时不再人为占住总线 10 ms，只占真实的寄存器读写时间 |

**新增测试**：

- `selftest-panel-vcom-mismatch`：面板标签写 1.50 V，板上驱动 1.20 V，必须报警；
- `scenario-reader_basic-panel-power-faults`：2% 超时下必须靠重试恢复，且没有任何警告。

| REVID | 0x65，占位，实机还没读过 |
| TCA9555 地址 | 0x20，上游默认值 |
| TCA9555 引脚作输入时 | 按下拉处理 |

UPSEQ1 的选通延时编码（3/6/9/12 ms）按数据手册。

**真机上还要做的**：

## 6. 可信度与局限

能在电脑上验证的：任务划分与优先级是否会互相饿死、内存是否够用以及碎片、刷新调度是否正确、时延由哪些部分构成、Flash 写入时机是否安全、断电后数据是否完好、不同分辨率与屏幕类型下界面是否成立。

还不能或只能粗略验证的：

1. **CPU 成本部分已校准。** 拷贝、字形、转换、JSON、解压、CRC 来自指令级模拟器（CoreMark 只能拟合到 3.08/MHz，比数据手册低 10%，取悲观）；LVGL（每像素 25 周期 + 每对象成本）、文本排版、堆管理仍是估计；到货后用实测校准。
2. **缓存与总线只做了粗模型**：I-cache 用固定缺失系数，字体 D-cache 用行模型；两核同时访问 PSRAM 的相互影响（评审 L4）没建模，只体现在每字节成本里——两个送行任务同时从 PSRAM 读帧，真实的每行成本可能高于指令级的单核数字，这正是 §5.4 余量要留的原因；中断开销只建了 LCD 补缓冲一项；跨核 IPC 等待按悲观方式计（等待期间两核都冻结）。
3. **栈用量**是主机上的悲观估计：只量任务自己的代码及它直接调用的主机 libc，不含线程启动、内核和模拟器的记账（D-42，§5.7）；没有真实代码的驱动（如 FatFS）不计。权威数字要用 RISC-V 编译的 `-fstack-usage`。
4. **网络是统计模型**：时延分布、恢复、断网参数是估算，4G 模组的真实行为（注网、弱信号、UART 流控）要到货后用 SP 系列实测校准。**音频**：I2S 时序按上游配置，Opus 每帧 CPU 是估计；回声消除、唤醒词、真实语音识别不在模拟器里（识别在中枢，用替身文字）。
5. **模拟器一次只跑一个任务**，看不到真正的数据竞争；竞争靠代码审查和加锁规则防，评审找到的两处已修。
6. **内部堆总量仍是估计**：区段结构已按出厂固件的 `heap_init` 改为 80 + 16 KiB（[第 0 步](../hardware/2026-11-03-phase0.md)），总量 96 KiB 要等本项目固件的 `idf.py size` 来替换。出厂固件静态占用 226.7 KiB，留下约 201 + 16 KiB，只能作参考。
7. **波形时间按逐行规划推出**（预填 + 扫描 + 帧结束开销，不足 12 ms 补足），送行成本来自指令级测量并与上游的经验吻合；帧结束开销 150 µs、LCD 中断占 0 核 10% 是估计；温度对相数与相长的影响未建模（上游也没有温度补偿，见 RK-14）。
8. **电流全部是估算**，只能比较方案，不能承诺续航。S31 的数据手册没有公开功耗数字（2026-11-02 查询），空闲主频的省电按 S3 类芯片的比例估计；4G 模组按厂商资料。

## 7. 平移到真机

1. `ports/esp32s31`：用 FreeRTOS 实现 `osal.h`（`xTaskCreateWithCaps` 支持 PSRAM 栈、`heap_caps_*`、`esp_timer`；延时按微秒时钟算目标节拍），用上游驱动实现各 HAL（EPDiy 改造版、FT6336U、TPS65185、LittleFS、SDMMC）。系统与应用代码不改。端口必须做到模拟器里已经假定的几件事：
   - I2C 总线互斥（PMIC 上电不整段暂停触摸）、LittleFS 缓冲放内部 RAM；
   - **送行管线按 D-35**：谁空谁取、只转换区域内的列、优化查表（四张预移位 256 字节表，掩码并入同一遍）、预填 64 行、每任务队列 48 行；
   - **LCD 补缓冲中断 IRAM 安全**：开 `CONFIG_LCD_RGB_ISR_IRAM_SAFE` 与 GDMA 的 IRAM 安全选项，EPDiy 的取行回调与行队列放内部 RAM（代码进 IRAM 约占几 KiB 内部 RAM，待 `idf.py size` 核实）；
   - **Flash 操作不与波形重叠**（D-36）：只经存储服务，读写都持 Flash 守卫；
   - 值得做的优化见 §5.4（送行任务满队列时阻塞，由中断按低水位唤醒；只比对改动区域）。

   - **电源**：`hal_power_sleep` 用 `esp_light_sleep_start` 按片睡；挂起调度器后再查一次刷新、音频与取消回调，再睡；唤醒键电平先锁存再恢复按键方向（上游做法）；定时唤醒不重挂 TF 卡、不恢复电源轨；升频锁用 `esp_pm_lock_create(ESP_PM_CPU_FREQ_MAX)`，需开 `CONFIG_PM_ENABLE` 并保持自动浅睡关闭（同上游）；降频时 LCD、I2S、UART 的时钟不得随 CPU 主频变化（驱动持 APB 锁或用独立时钟源），否则波形与音频出错——列入到货验证；保持 4G 待机要用模组的睡眠握手（MRDY/SRDY）让模组在寻呼间隙睡眠，电流由 SP-10 实测。

   - **PQ-BN 直驱（D-40 选用时）**：内核即 `drivers/epd/pqbn_v4.c`；执行器（`pqbn_v4_exec_row`）放 IRAM（`PQBN_HOT` = `IRAM_ATTR`），两个扫描任务谁空谁取、满队列时阻塞，预填 32 行；规划器单独一个任务，跟在扫描后面逐带规划下一相（规划某一带用该带下一次被扫描的相号），或把执行器读取的 tile 状态做双缓冲；相时钟跨过空闲时段前进（上限 255 相），并补做被跳过相号的时间戳维护（审计 F-8）；每像素状态、帧缓冲与规划器的表放 PSRAM，执行表与 tile 状态放内部 RAM；实现 `hal_display_pause()`：Flash 操作前在相边界停住、像素保持；面板响应按 SP-13 标定后重建表。

   另需评估 S31 的 Flash 自动挂起（`SPI_FLASH_AUTO_SUSPEND`，S31 硬件支持，取决于板上 Flash 型号）：若可用，擦写期间缓存不关，送行任务与音频都不会被冻结。板上是 Puya PY25Q128HA：芯片支持挂起（75h/7Ah，延迟 ≤ 30 µs），但 IDF v6.1 的通用驱动只对 XMC、FM 开启（[第 0 步](../hardware/2026-11-03-phase0.md)），要用就得自写芯片驱动并实测。还要评估 XespV 向量扩展能否用于行准备。
2. 到货第一周（第 0 步已完成：PSRAM 16 MB、`heap_init` 区段、Flash 型号、出厂固件的 `EpdTiming`，见[记录](../hardware/2026-11-03-phase0.md)）：读 `esp_psram_get_size()`、跑 SP-01（刷新时序：上游 `EpdTiming` 日志给出每相周期与扫描时间；另测每行准备时间，分上游 C 与优化版）、`idf.py size` 与 `heap_caps_print_heap_info`（静态内存与内部堆区段）、Flash 擦写与停顿实测、查板上 Flash 型号是否支持自动挂起，把实测值写回档案，并按 §5.4 选定预填与行时间。
3. 同一批场景在真机上跑（按键注入或人工操作），对比预测与实测：预测不得比实测乐观超过 10%，否则调整参数并在档案里记录来源变化。
