# 第二期简报：限定 Plus，明确通信依据与数据恢复方向

日期：2026-10-26。阶段：想法整理与可行性探索；本期未开始全系统设计或固件开发。

## 这轮已经明确与仍待考虑的事项

- **已明确**：只考虑 CloudZao E-Ink4 Plus。通信可以依据原理图、模组规格与接线判断可开发性，不要求已有完整第三方 app。
- **用户仍在考虑**：服务器备份同步、整机还是按 app 备份、是否需要账户。
- **助手建议**：系统统一管理数据，允许整机用户数据恢复与单 app 恢复；先建立成员和设备的归属关系，完整注册账户系统后定。

## 通信：有开发依据，最后一段音频链路仍需确认

**总体判断：有条件可行。** 上一轮把通信重点放在 Claw4 不够充分；Plus 自己的板级代码已经接入 NT26，并定义控制引脚及共享电源。修正来自对同一提交更深入的核查，不是用户需要放宽硬件约束。[Plus 板类](https://github.com/CloudZao/Metalio-E-INK4-Plus/blob/ad8edf4150a688737c0d7c00cae4413079b262ef/main/boards/metalio-e-ink4-plus/metalio_e_ink4_plus_board.cc#L54)

| 关注点 | 现在的判断 | 决定因素 |
| --- | --- | --- |
| 4G 联网 | 有板级初始化和驱动路径 | 实物装配、模组固件、SIM 及网络；尚未实测。 |
| 短信 | 有条件可开发 | NT26 子型号/固件的短信能力，收发协议、编码和通知。 |
| 电话呼叫控制 | 有条件可开发 | VoLTE/IMS、运营商业务和模组接口。 |
| 真正双向通话 | 证据尚不完整 | NT26 与现有音频器件之间的接线、时钟和路由。已有 AI 麦克风/扬声器不能单独证明蜂窝音频畅通。 |
| 锁屏/待机接收 | 需要专门设计 | 保持模组可接收、通知主控，以及共享供电带来的续航代价。 |

利尔达官方提供短信和拨打/接听/挂断的 API，但属于模组内部 SDK；其型号表也把语音能力与特定子型号/底包对应。由此可以支持“值得在既定硬件上开发”的判断，尚不能说所有 NT26 都只差一个电话界面。[产品能力表](https://opendocs.lierda.com/docs/CAT.1_Doc_Protal/zh_CN/index.html)、[API 说明](https://opendocs.lierda.com/docs/CAT.1_Doc_Protal/zh_CN/software/api-overview.html)

目前没有取得对应 Plus 版本的整机原理图，因此没有声称完成了电路审查。后续优先补齐模组完整型号、固件功能和音频接线这三个事实；不必因此暂停其他产品原型讨论。

## 找到的第三方线索：布丁 Pudding

沿无名科技论坛和固件入口，找到 [CloudZao Burner](https://burner.cloudzao.com/)中的“布丁”，作者 paouke，v0.1.0 测试版。简介列有电话、短信和蜂窝网络，但同时写明短信发送仍在诊断。

它适配的是 **普通 E-Ink4 / ESP32-S3**，不是已确认的 Plus 固件。它能作为功能探索的线索；本轮没有拿到该条目对应源码，也没有验证短信接收、双向通话或 Plus 移植。不能因其存在就承诺可直接复用，也不能因为它尚有问题而否定硬件可开发性。[目录来源摘录](/home/workspace/reader/docs/research/sources/2026-10-26-cloudzao-firmware-catalog.json)

Plus 分类另有 RickyOS、kiikoread、CrossLink 等；本轮检查的 13 个条目说明未证明完整短信/通话。有些固件限定 Plus 的板卡/面板版本，后续仍需精确对应。详细检索范围和固定代码入口见 [通信调研](/home/workspace/reader/docs/research/eink4-plus-cellular.md)。

## 备份：整机和按 app 可以同时成立

建议由系统负责备份，数据内部按成员、共享资源与 app 分类。用户可以选“恢复整台设备的数据”，也可以选“只恢复单词 app”，两者使用同一套备份基础。

| 需要恢复的东西 | 建议如何对待 |
| --- | --- |
| 书籍、题库、保存的故事与录音 | 由共享内容服务管理；卸载一个 app 不应自动删掉其他 app 仍在用的内容。 |
| 学习记录、批注、备忘录、故事断点、游戏存档 | 作为重点个人数据，保存成员归属和版本，允许按 app 恢复。 |
| 系统设置与 app 清单 | 支持重建使用环境；兼容的 app 程序是否也归档后定。 |
| API 密钥、服务器凭据 | 单独决定加密与恢复方式，避免刷机同时抹掉唯一恢复凭据。 |
| 缓存与可重新生成的索引 | 可不备份或低优先级，减少存储和上传。 |

建议讨论的三个默认体验：

1. 更新固件优先保留数据，并处理格式迁移；必要时可从备份恢复。OTA 回滚程序不自动回滚数据。
2. 卸载 app 与清除其个人数据分开，重新安装后可恢复；保留多久、是否自动保留仍待定。
3. 同步之外保留历史版本，避免误删在设备与服务器间传播后无处找回。

整片 Flash 镜像可以辅助工程救援，但不会涵盖独立 TF 卡，不适合作为唯一用户备份。离线新产生且尚未备份的数据也无法保证全擦后找回；界面应让人看到最近可恢复的时间点。[数据保护调研与官方依据](/home/workspace/reader/docs/research/data-backup-sync.md)

## 账户：先解决“是谁的数据、刷机后怎么取回”

现在不必决定做手机号/邮箱注册。少量家庭设备可以先考虑“家庭空间 + 本人/子女档案 + 设备配对 + 独立保管的恢复凭据”。这是建议，不是定案。

成员档案负责区分学习和故事进度；服务器授权负责限制访问；恢复凭据负责在设备清空后重新取得数据。这三件事需要解决，但不一定都表现为用户每天登录一个账户。若未来扩大到多个家庭，再评估完整账户体系。

## 对关键架构的影响

本轮只新增两项应保留的系统能力：

- **数据持久化与恢复**：app 说明哪些数据重要、属于谁、是什么版本；系统统一安排备份和恢复，并保持共享内容关系。
- **通信与音频协调**：蜂窝服务维护短信/电话状态，电话界面和 AI 调用共同能力；切换 Wi-Fi、听故事、语音唤醒与来电要能协调。

下一步仍是收集想法、完善场景与确定边界。服务器、自研账户、存储技术、app 运行时、驱动开发方案均未定；基本方向经用户认可后才进入完整系统设计。
