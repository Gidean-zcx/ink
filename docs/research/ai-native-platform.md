# AI 原生系统、动态应用与语音：能力边界

查阅日期：2026-10-26。关联 G-001、G-002、R-005～R-009、R-012～R-021、H-004～H-006。硬件现已限定 E-Ink4 Plus。下文是关键架构研究与待讨论建议，不是正式系统设计、接口规范或技术栈定案。

后续具体交互依据见 [按设计问题查竞品](/home/workspace/reader/docs/research/interaction-library/comparison.md)：从播放/浏览位置、隐藏入口、暂缓/删除、规则过滤等实际文档语义反推 AI 需要理解的数据与动作。该映射是本项目分析，不证明竞品已经开放相应 AI API，也未提前定义本系统接口。

## 判断与成立条件

**有条件可行**：在 E-Ink4 Plus 上，让可配置 API 大模型统一理解目标、发现 app 能力、组织任务，由设备端应用和服务执行。条件是控制模型上下文、内存、后台负载和数据规模，明确远端与本地各自承担的工作。

**有依据可行**：能力发现、结构化工具调用、渐进式加载、MCU 本地唤醒和 ELF 加载分别已有上游机制。它们还不是本项目上经过验证的完整系统。

**信息不足**：任一特定板卡能同时承担高刷游戏、连续语音、联网任务及动态 app；是否直接连接模型 API，还是经家庭服务中转；能否达到用户期望续航。

## 最新目标：完整的系统级 AI 能力

用户进一步明确 G-002：系统/app 的一切行为与数据都能由 AI 操作或获取，任何场景和页面的数据均可提供给 AI。这已是明确目标；原先少量工具和几个场景的例子不足以表达覆盖范围。

**有条件可行**：对本系统控制开发或接入约定的应用，可以将全面可观察、可操作作为基本接入要求。任意外来程序自动具备语义接口、模型可靠理解一切媒体和持续高频调用，则尚无依据保证。需要逐类适配和资源验证，不能把这些未验证部分默认视为已经完成。

以下是将该目标展开成可检查的产品表现；具体实现与验收方法仍待认可：

- 用户在任意 app 内都能唤醒 AI，并把当前内容作为必要上下文，例如“解释这道题”“把这个单词加入复习”。
- app 同时提供给人使用的界面，以及供 AI 获取的内容、状态、行为记录和可调用动作；两者操作相同的数据与状态。
- 一次指令可以跨 app：收集学习资料、生成或导入练习、加入学习安排、随后朗读。
- 安装新 app 后 AI 能发现其能力；更新、卸载后能力目录同步变化。
- AI 的“已完成”以执行回执为依据；下载中、等待网络、失败和取消有真实状态。

建议让模型负责理解与规划，本地服务负责状态保存和执行规则。书架、闹钟、播放断点、学习记录等不依赖一段聊天文本作为唯一记录。这样更换模型或清空对话后仍能继续使用。

## 全场景覆盖需要讨论哪些能力

覆盖目标来自用户；下表的表示和管理方式是助手建议，没有选择 SDK、数据库或通信协议。

| 能力 | AI 需要取得或执行的内容 | 例子 |
| --- | --- | --- |
| 页面上下文 | 当前 app／页面、正文、选择位置、输入中内容、弹窗、控件状态、可执行操作。 | “这个词”“刚才那道题”“把这里改一下”有确定对象；下拉面板和设置页也覆盖。 |
| 业务数据 | 书籍、新闻、题库、笔记、提醒、音频等对象及关联资料，包含当前未显示的数据。 | 找到上周阅读过但不在当前列表里的文章，读取来源与笔记。 |
| 行为和进度 | 用户与 AI 做过的操作、作答和提示、阅读/播放位置、导入与修改结果。 | 知道哪些内容看过、哪里做错、故事停在哪里；观察和模型推测分别保存。 |
| 操作与修改 | 所有面向用户的系统/app 功能，并支持跨 app 的查询、新建、修改、删除、导入、导出等适用操作。 | 修改笔记、调整学习安排、控制音频、设置提醒，在同一任务中连贯执行。 |
| 任务状态 | 排队、执行、部分成功、失败、取消、完成及其实际结果。 | “资料导入好了”对应可打开的内容；重复尝试不意外重复建立任务。 |
| 生命周期 | 安装、更新、卸载、恢复后的能力与数据变化。 | 新装 app 能被发现；恢复的旧记录还能关联内容，失效动作不会继续被调用。 |

页面语义和业务数据都需要覆盖。只看当前像素不能直接取得未显示的全文、来源关系和后台状态；只读数据库也不能准确知道用户指的是哪一段、正在编辑什么。建议把两者通过稳定内容定位关联起来。

对于图片、图表、手写、游戏画面或自绘页面，需要暴露对应媒体对象、可用说明与输入操作；适用时增加结构信息或截图。取得画面与理解其中全部含义的能力要分别验证。模拟器内部的游戏语义尤其需要额外适配，不能由“系统能截图”直接推定。

## 完整可访问与渐进式披露怎样同时成立

建议平台维护完整的能力与数据入口，每次任务再逐级读取：**全局目录 → 当前场景概要 → 相关对象及动作 → 所需全文／媒体／历史 → 执行后的新状态**。数据范围完整，单次模型上下文按任务组织，具体分层与索引待验证。

例如用户正在看一篇新闻，说“帮我补上这方面基础知识”：先取得当前文章和所指段落，再读取来源、相关学习记录，发现资料与学习 app 的能力，完成导入后返回入口。用户无需先切到聊天 app 或重述整篇文章。

这也提出四个尚未定案的关键问题：

- **数据位置与读取范围**：本地保存哪些索引和对象，哪些处理放在家庭服务器或云端；家庭成员、模型供应商与单次任务的可用范围怎样表达。
- **当前与历史**：当前页面可读、业务记录可查和过去每个瞬时画面永久可还原是不同存储要求。用户尚未要求全程录屏，保留粒度与期限需结合恢复需求、空间与耗电讨论。
- **状态变化**：模型响应期间页面或数据可能已变，应依据对象定位及状态版本判断动作是否仍适用，再返回实际结果。
- **数据可信性**：新闻、书籍和第三方资料是任务数据；其中的文字不能自行成为系统命令。模型生成的总结、掌握推测和原始行为事实也需区分。

[MCP Resources 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/resources)提供资源列举、读取和可选变更订阅，[Tools 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)提供动作发现和调用。这些是可参考的机制；它们不会自动生成本系统全部页面语义、行为记录和应用覆盖，当前也未决定采用 MCP。

## 后续原型应如何检查 G-002

建议建立逐 app 的“页面—数据—动作—状态”覆盖表，列出尚不可读或不可操作的位置，而不是用工具数量代替完整性。供讨论的检查场景包括：

1. 在新闻正文、书中选段、练习题和音频播放页分别指代“这里”，AI 找到正确对象并能展开相关资料。
2. 对同一操作，手动入口与 AI 入口得到相同的业务结果；新安装 app 的新页面与动作也加入覆盖。
3. 连续任务跨新闻、资料库、练习、笔记，途中失败或取消后能读取真实进度并继续。
4. 用户切换页面、修改数据或中断播放后，AI 不依据过期状态误操作。
5. 备份恢复后仍能找回内容、历史与断点；已发生的外部动作不因恢复任务而自动重放。

覆盖检查属于未来原型验证，本轮未编写接口、实现事件系统或开展实机测试。模型是否始终在线也需讨论；已有业务数据与本地应用应如何在 API 不可用时运行，仍属于平台方案的一部分。

## 概念职责划分

| 层次 | 应承担的职责 | 本阶段边界 |
| --- | --- | --- |
| 板卡适配 | 屏、触摸、键、音频、存储、网络、电源，以及有对应硬件时的蜂窝模组 | 研究并剥离可复用驱动依赖，不继承上游产品架构。 |
| 本地系统服务 | 显示调度、输入、音频会话、文件/内容、时间与提醒、任务状态、设备电源 | 用户动作和 AI 动作共用服务；需要实测资源预算。 |
| 数据保护（新增候选） | 成员与 app 数据归属、共享内容、备份/同步、恢复及数据版本 | 用户仍在考虑服务器与账户；建议统一提供服务，未选存储或同步技术。 |
| 应用运行与安装 | 应用生命周期、资源包、版本、可调用动作、安装/更新/卸载 | 具体运行时与隔离强度未定；系统 OTA 与 app 安装分开。 |
| AI 协调 | API 配置、上下文、能力检索、计划、执行回执、跨 app 任务 | 提供稳定系统入口，不能由模型自行绕过设备规则。 |
| 产品界面与应用 | 现代系统外壳，以及学习、读听、备忘录、新闻等 app | 优先设计用户任务和状态，不预先拆成大量独立程序。 |

权限、资源限制和执行结果检查应由可信系统代码落实；仅给模型一段“请遵守”的文字不能替代。对普通续播、翻页不必反复确认；发送短信、替换大量内容等行为的授权方式应按具体影响讨论。这些是平台建议，尚未成为用户确认的细则。

## 渐进式披露：可以怎样工作

建议形成五个阶段，而不是启动时把所有 app 的全文说明塞给模型：

1. **发现**：只给简短应用目录和检索入口，例如“书库、练习、音频、提醒”。
2. **选相关能力**：用户说“继续故事”，只找内容与播放相关能力。
3. **加载动作详情**：再取得所需动作的参数、返回信息、适用条件和权限。
4. **调用与确认状态**：执行后返回内容标识、真实播放位置、结果或错误。
5. **按需展开**：大型题库、书籍和日志只返回摘要或标识，需要时再取具体片段。

安装/升级/卸载须更新目录和版本，避免 AI 调用已经失效的动作。资料正文是数据，不能因为网页或书籍内含指令就改变系统权限。

**外部依据**：[MCP Tools 2025-11-25 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)定义能力列举、参数描述、调用和目录变更通知；[Anthropic 的渐进披露说明](https://www.anthropic.com/research/code-execution-with-mcp)讨论按需查找工具及加载不同详细程度的定义。

**本项目推断**：可借鉴这种描述方式；MCU 内部未必需要完整 MCP 服务栈，协议转换也可以放在远端。MCP 不会自动提供应用安装、进程隔离、权限执行或任务恢复；本轮没有指定采用任何模型厂商或协议版本。

## 动态 app：需要区分的四类机制

| 机制 | 能解决什么 | 不能混同的能力 |
| --- | --- | --- |
| 固件内置模块 | 高效率基础服务、固定原生功能 | 增加功能若仍需整机刷写，就不满足动态 app 安装目标。 |
| 内容包/声明式页面 | 动态更新课程、题库、故事、资源与受控界面 | 只是安装数据时，不等于安装新程序逻辑。 |
| 脚本或字节码 app | 运行时加载逻辑，调用受控系统服务；可研究 Lua/Wasm 等候选 | 运行时开销、暂停/终止、UI 绑定和目标芯片适配需验证，尚未选型。 |
| 原生可加载模块 | 用编译后的机器代码提供计算密集功能 | 架构/ABI 绑定、重定位、内存及故障影响更复杂；不能把加载器当成隔离系统。 |

**上游依据**：乐鑫的 [ELF 示例](https://github.com/espressif/esp-iot-solution/blob/master/examples/elf_loader/elf_embed_example/README.md)演示加载执行 ELF，其当前支持列表包括 S3、S31、P4。示例本身嵌入在主项目中，因此它证明的是加载执行机制，不能据此宣称已经实现可独立下载安装的应用生态。

**建议**：先用同一个小功能比较动态机制是否能在不刷整机的情况下安装、调用系统服务、注册 AI 能力、退出和卸载，再确定运行时。高耗时计算、屏驱动和音频底层是否应保持原生服务需由性能数据决定。当前不选择 Lua、Wasm、ELF 中任何一种作为已定架构。

“AI 操作所有 app”现在已加强为 G-002：每个系统/app 功能、页面和数据都纳入接入范围，不能只选择少量方便的动作。逐项实现方式仍需验证；第三方应用必须有可适配接口。现有 MCU 平台上的可安装应用不自动等于兼容 Android APK 或桌面程序。

## 语音链路与运行位置

| 环节 | 候选运行位置 | 条件/限制 |
| --- | --- | --- |
| 按键或唤醒词、活动检测 | 设备本地 | 按键需要现有 GPIO/电源逻辑支持；唤醒词需音频采集持续工作，不能假定整机断电仍可唤醒。 |
| 语音识别 | 远端通用识别；可研究本地少量固定命令 | 本地唤醒不等于本地识别任意自然语言，儿童发音、环境声要验证。 |
| 大模型理解与规划 | 可配置 API；服务可在云端或家庭服务器 | 直接 API 与中转方案待比较，模型工具调用能力也需匹配。 |
| 应用动作 | 本地 app/服务；必要时调用远端检索或转换 | 读写本地文件、设置提醒、控制播放等动作要能确认真实结果。 |
| 语音输出 | 本地播放；TTS 可远端生成后流式/缓存播放 | 音频格式、首音延迟、缓存容量、费用和断网恢复待确定。 |

乐鑫 [ESP-SR README](https://github.com/espressif/esp-sr/blob/master/README.md)与 [WakeNet 文档](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/wake_word_engine/README.html)提供本地唤醒/音频前端依据。S31 的支持状态应以所用版本核对；CloudZao Plus 的现有依赖清单尚不能证明该功能已在此板开启，见 [代码抽查](/home/workspace/reader/docs/research/cloudzao.md)。

候选体验包括按住说话、唤醒词后对话、朗读中打断。必须区分麦克风正在采集、正在等待远端、正在播放三种状态。是否可全双工、远场唤醒，取决于回声消除和实际音频链路。来电、提醒、故事和 AI 回复需要统一音频优先级，不能各自抢占扬声器。

## 内容准备与导入

“我想学分数”应得到可继续学习的内容，而非只得到一段回答。建议任务路径：明确少量必要条件 → 检索已有资料 → 获取可访问内容 → 转换与校验 → 导入学习 app → 返回数量和入口 → 保存学习进度。

需要区分三个执行地点：

- **设备端**：交互、已转换资料的阅读/练习、音频播放、进度和索引；复杂格式是否能直接解析需单独核查。
- **电脑/家庭服务器预处理**：可选的 PDF/OCR、版式转换、批量资料整理、题库格式转换；用户是否接受依赖尚未确认。
- **云服务**：候选的搜索、模型推理、语音识别与合成；仅配置一个模型 API 不保证这些服务全部可用。

| 内容 | 导入要保存/说明的信息（建议） | 成功条件与例外 |
| --- | --- | --- |
| 书籍 | 书名、作者、版本、来源、可用文件及格式 | 找到符合用户访问权限的可用版本后入库；只有购买/借阅入口时如实返回，不宣称本地已有书。 |
| 学习资料 | 主题、来源、适用水平、正文/媒体与必要出处 | 可在 app 打开；搜索结果列表不等于已导入内容。 |
| 题库 | 题干、选项、答案、解析、标签、来源/版本 | 区分原题与 AI 生成练习；校验格式与明显冲突，支持错误反馈，不能承诺生成答案绝对正确。 |
| 新闻 | 出处、发布时间、抓取时间、原文链接与摘要 | “最新”需实时获取；离线缓存显示时间，不能让模型知识替代新闻源。 |

下载、转换、入库是可失败的多步任务。建议用稳定标识和可恢复状态避免重试时重复导入；正在下载时允许取消。首版支持格式、最大规模和来源范围尚未决定。

## “继续上次的故事”意味着什么

至少分清三类内容：固定音频、书籍的 TTS 朗读、AI 生成故事。固定音频需要内容/章节与时间位置；书籍朗读需要可定位的文字段落；生成故事还需要保存已生成版本和段落，避免每次恢复重新生成一段不同的故事。

用户后续补充儿童为 5–6 岁、可独立阅读、偏好听书。对应候选场景是“刚才那句话是什么意思”：系统向 AI 提供正在播放的内容及可定位片段，回答后恢复播放。读听切换还需文字位置与音频位置对应；如果只有独立录音，能否逐句定位必须另行核查。此处为原型建议，尚未实现。

建议以成员档案归属进度，在停止、切换及合理间隔持久化，并允许纠正“上次”指的是哪个内容。家庭共用设备时不能仅靠声音就假定说话人。存储、重启、异常断电及内容版本变化下的恢复方法留待后续设计。

用户后续提出刷机、升级与卸载重装后的数据保护。建议将已保存故事、版本与断点一起纳入系统备份范围；聊天记忆、app 程序和用户数据分开管理。恢复 AI 任务状态时避免重新执行已经完成的外部动作。详见 [备份与账户讨论](/home/workspace/reader/docs/research/data-backup-sync.md)；这些是候选方向，不提前确定服务器或账户体系。

## 需要先验证的架构问题

1. 在 Plus 的实际空闲 RAM/PSRAM、音频与网络负载下，哪种动态运行方式可成立。
2. 模型能否只按需取得少量能力描述，可靠完成跨应用任务并返回真实结果。
3. 无网、API 超时或切换供应商后，哪些本地应用和已有内容仍可使用。
4. 全局 AI 入口、音频会话、故事断点与来电等状态能否协调。

这些是未来有限验证的议题；本轮没有安装运行时、运行模型基准或实施应用平台。
