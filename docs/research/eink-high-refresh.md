# 墨水屏高刷与现代交互：第一轮核查

查阅日期：2026-10-26。关联 I-005、I-006、I-009；硬件现已限定为 E-Ink4 Plus，普通 E-Ink4 仅保留为历史技术比较。本文包含作者说明、公开代码结构核查、带假设的估算和助手建议；没有本项目实机结果。

## 当前判断

**有依据可行**：墨水屏在特定驱动方式下，可以以 60Hz 节奏接收和处理新图像，也有 MCU 上的 Game Boy 演示。

**有条件可行**：借鉴这种原理研究 CloudZao 的并行墨水屏，做局部动态区域、低延迟手势反馈和限定游戏平台。

**信息不足**：E-Ink4 Plus 能否在全分辨率、指定灰阶、长期运行、语音并发条件下达到 60fps，且无可见残影。暂不能承诺，目标也未被删除。

## 与用户视频线索接近的项目

用户描述：在 B 站看过很流畅的墨水屏 Game Boy 模拟器，宣称 60fps；没有视频链接。本次找到 Wenting Zhang 的 PaperBoyS3，属于匹配线索，不认定就是同一视频。

作者于 2026-06-29 发布的 [PaperBoyS3 技术说明](https://www.hackster.io/wenting-zhang/60fps-eink-gameboy-emulator-on-m5papers3-57e4e5)描述：

- 目标为 M5PaperS3，采用原始行列/并行屏接口；它不是本项目允许替换采用的板卡。
- 以逐像素状态追踪，让新图像可在之前像素仍在变化时继续提交，驱动节奏为 60Hz；像素物理响应时间没有因此变成 16.7ms。
- GB 画面为 160×144；用抖动与缩放处理四级灰度，核心处理区约 480×144，避免按整块屏幕处理。
- 实际模拟器依赖动态跳帧，文中给出的游戏渲染范围为 30–60fps；并非所有游戏恒定 60fps。

上述是作者说明，未由本项目复现。作者的 [GitLab 项目](https://gitlab.com/zephray/paperboy)可作为后续移植入口；本轮未完成其源码、许可和依赖审计。没有从说明中取得“在目标 CloudZao 面板上普遍无残影”的证据。

另有 [Modos Glider](https://github.com/Modos-Labs/Glider)和 [Caster](https://github.com/Modos-Labs/Caster)提供低延迟电子纸控制器的资料。Caster 是 FPGA 控制器设计；可研究原理，不能当成一段可原样塞入现有 MCU 的驱动，也不能在当前硬件约束下直接增配 FPGA。

## “60fps”需要分别记录的量

| 层次 | 实际含义 | 不能据此推定 |
| --- | --- | --- |
| 游戏模拟速度 | 仿真的时间是否跟上原机器 | 每一帧都被绘制或显示 |
| app 渲染帧率 | 软件生成多少新画面 | 显示控制器接受了全部画面 |
| 控制器/面板扫描节奏 | 多久提交/驱动一次像素 | 像素每次都已完全变到目标灰阶 |
| 光学响应与残影 | 人眼看到的变化、拖影和对比度 | 可从视频标题或帧率计数器直接得出 |

“无残影”目前只是体验目标。后续应在文字滚动、黑白反转、移动图形和静止恢复等固定画面上定义观察条件与阈值。不能用“看起来流畅”代替残影、清晰度和刷新闪烁的独立评估。

## 数量级估算，不是跑分

计算日期：2026-10-26。MB/s 采用十进制；KiB 采用 1024 字节。

1. **E-Ink4 的当前传输上限**：假设每帧上传完整 800×480、每像素 1bit，60 帧需 800×480÷8×60 = 2.88 MB/s。10 MHz 单数据线 SPI 的理想上限仅为 1.25 MB/s；单帧裸数据需 38.4ms，还未计命令、旧帧、等待和光学变化。结论仅针对完整帧上传；局部/稀疏更新不遵循这一整帧数据量，不能据此否定所有局部高刷。
2. **Plus 的像素状态开销**：假设仿照逐像素 4bit 状态，覆盖完整 1216×684，则单个状态缓冲约 406.1 KiB；60Hz 时每像素状态各读写一次，仅此项约 49.9 MB/s。还没有包括输入帧、DMA 输出、缓存未命中和计算。
3. **工作量不可按演示直接类推**：1216×684 的像素量约为 480×144 的 12 倍。这仅是处理像素数比较，不是 S31 相对 S3 的速度预测。现有公开材料不足以得出最终刷新率。

这些估算说明应先限定动态区域和工作负载；不等于已证明 Plus 达不到目标，也不支持盲目提高屏驱动电压或时钟。

## 可讨论的刷新策略

以下是助手建议，不是已确认设计或已完成算法：

| 使用内容 | 候选策略 | 需观察的代价 |
| --- | --- | --- |
| 长时间阅读、题干静止 | 清晰文字模式；局部更新答案、选中态 | 清晰度、局部变化积累的残影 |
| 下拉状态栏、短手势 | 优先及时反馈；操作结束后恢复清晰状态 | 跟手性、停下后的收敛时间和闪烁 |
| 游戏/动态学习局部区域 | 指定活动区域与有限灰阶；研究异步逐像素更新 | 算力、内存、对比度、音频竞争、功耗 |
| 清理残影 | 根据画面历史和实测选择适当清理时机 | 清理频率与用户干扰 |

商业参考 [BOOX BSR](https://shop.boox.com/en-ca/blogs/news/boox-super-refresh-bsr-technology)也区分清晰、均衡、快速和极速模式，官方明确快速模式可能有残影、极速模式牺牲细节。这支持“分场景取舍”的思路，不证明其专有算法可移植。

## 后续最小验证建议

在板卡与范围被确认后，再开展有限验证，不在本轮直接开发驱动：

1. 锁定面板与板卡版本、时序资料、波形来源、屏电源限制和驱动许可。
2. 从静态文字和小块黑白运动开始，分别记录软件输出、面板接受节奏、输入到可见变化延迟；用高速拍摄或光学测量辅助观察。
3. 对比不同活动面积、灰阶、背景与温度下的残影、对比度、清理间隔及功耗，再考虑扩展到整屏。
4. 加入音频播放、唤醒监听、联网和存储写入，核查争用。游戏单独跑通不能代表整个系统并发可用。
5. 保存测试条件及原始结果，再决定目标应覆盖哪些 app 和显示模式。

目前没有屏幕寿命、续航、音频并发或稳定 60fps 的实测数据。
