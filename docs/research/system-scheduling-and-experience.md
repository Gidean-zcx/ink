# 有限算力下的系统调度与端到端体验

查阅与记录日期：2026-10-31。目标为 CloudZao E-Ink4 Plus，关联 R-008、R-010、R-029、I-030。本文为基于固定源码与官方文档的设计建议，不是技术栈定案或已实现的系统。没有编译、刷机、实机并发、光学时延或功耗测试。

## 结论与适用条件

**有条件可行**：沿用 ESP-IDF / FreeRTOS 的基础调度，在其上设计系统服务、资源准入和业务流程状态；通过有限并发、明确预算及可恢复任务提高体验。是否能在特定屏幕模式下同时满足音频、显示与联网的时限，必须用实际装配验证。任务分层本身不产生额外算力。

用户本轮明确：硬件算力有限，高效底层调度、多任务系统，以及实现流程中感受到的体验，都需要重视。CPU 优先级、内存容量、DMA 与外设访问、屏幕物理刷新、任务状态应联合评价。

## 2. 建议分三层调度

| 层次 | 负责什么 | 采用的机制 |
| --- | --- | --- |
| RTOS 与驱动层 | 任务抢占、核亲和、中断、定时器、DMA 供数 | 优先复用 ESP-IDF 已有能力，审计关键任务的执行时间、临界区及阻塞。 |
| 系统服务与资源层 | 决定一个工作能否开始、用多少内存／带宽、何时让出资源 | 音频、UI、刷新、存储、网络等服务；有界队列、资源预算、并发上限与背压。 |
| 应用与业务流程层 | 当前用户在做什么、哪个结果最重要、何时取消或恢复 | 前台场景与可恢复任务状态；输入、内容、任务完成及持久化状态相互关联。 |

[ESP-IDF 官方说明](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s31/api-reference/system/freertos_idf.html)支持固定优先级、抢占、时间片及核亲和；双核选择还受亲和性约束。应用层的“任务预算”是附加策略，不等于原生调度器自动提供 CPU 配额。

### 少量长期服务，应用提交有界工作

建议默认只有一个前台交互场景；后台仅维持明确获准的音频、下载、备份等工作。一个安装的 app 不必拥有永久线程、独立网络循环和独立刷新计时器。页面隐藏后保存必要状态并释放可重建资源，后台能力通过系统服务表达。

CPU 密集工作拆成有界步骤，按页、块或记录推进，步骤间检查取消与压力。不要让“一个工作线程”串行执行不可打断的长解析，从而阻塞前台依赖。脚本／原生模块的运行方式仍需单独评估；FreeRTOS task 本身不等同于已完成进程隔离。

网络等待、屏幕等待、磁盘等待让任务阻塞在事件上，不忙轮询。UI 回调只更新状态、提交命令，不在回调中下载、整本排版或等待物理全刷。

## 3. 优先保障哪些工作

以下是工作类别，不是建议直接写入固件的优先级数值。

| 类别 | 例子 | 调度策略 |
| --- | --- | --- |
| 有截止约束的驱动工作 | 音频 DMA／缓冲补给、刷新期间的行数据供应、必要协议处理 | 明确截止时间及峰值负载，预留资源；中断只做必要动作，后续计算交给合适任务。 |
| 交互控制 | 按键／触摸、停止播放、返回／取消、已接入的来电事件 | 短路径响应，独立于慢计算和云请求；读取／执行控制后再安排可见反馈。 |
| 当前任务的必要计算与 IO | 下一页、当前搜索、用户正在等待的内容、AI 当前回复 | 提升其依赖链优先级；缓存未命中的读取不能一直排在后台备份后。 |
| 后台维护 | 大文件备份、预取、离线索引、历史日志 | 限速、分块、可暂停；设置老化或最低服务份额，避免永久饥饿。重要新进度落盘可单列较高时限。 |

音频和显示若同时需要超过硬件可承受的服务率，仅调高优先级无法保证二者。应测定可并发的刷新模式与负载组合，必要时减少其他计算、降低刷新频率或在安全边界串行执行。

绑核应基于驱动中断、SDK 任务、向量运算能力及实测阻塞决定。先记录两核分别被谁占用，不预设“网络一核，UI 一核”就能解决所有争用。

## 4. 工作开始前做资源准入

一个耗资源工作建议声明：

- 所属场景／用户、工作类别、截止或等待目标。
- 预计峰值内部内存、外部内存、栈、DMA 需求。
- 单次计算步长、网络连接与 IO 预算。
- 可取消位置、恢复检查点、结果所对应的数据版本。

系统先确认资源可用再启动。音频开始时预留缓冲和关键内部内存；批量解析、图片转换及新的 TLS 连接不能无限并发。后台队列满时延迟或合并工作，不能一边无限接收、一边无限申请内存。

合并过期视觉状态与保留业务动作分开：旧进度显示可丢弃，用户保存、答题、短信发送等动作不能被简单当作旧帧删除。页面切换或搜索词改变后，用场景代次／请求标识拒绝迟到结果，避免旧回复覆盖新页面。

共享资源设置统一访问边界、锁顺序与最大持锁时间。需要时采用支持优先级继承的同步机制；高优先级线程等待低优先级线程的长 IO，不会因调高自身优先级自动恢复。持资源锁时避免等待网络和 UI 回调。

## 5. 内存、总线和 Flash 都要进入设计

按 684×1216、紧密打包估算，不计 stride／对齐及元数据：

- 1 bpp 单帧：103968 字节，约 101.5 KiB。
- 4 bpp 单帧：415872 字节，约 406.1 KiB。
- 三份 4 bpp 帧：约 1.19 MiB；具体固件可能另有前后帧、差分、UI 绘制和行缓冲，应逐项盘点，不能据此认定实际只有三份。

建议将关键控制结构、必须使用的内部 DMA 缓冲及不能受缓存关闭影响的执行路径单列预算；大内容、普通帧和可重建缓存优先评估外部内存。哪些 DMA 可访问 PSRAM、对齐与同步要求必须按外设驱动核对，不能概括成“所有 DMA 都不能用 PSRAM”。

[ESP32-S31 官方外部内存说明](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s31/api-guides/external-ram.html)记录缓存关闭时的外部内存限制，也说明启用 PSRAM XiP 会改变 Flash 操作条件并增加 PSRAM 总线负载。应对照实际 SDK／配置核验，不能直接套用其他 ESP32 型号结论，也不把“挪进 PSRAM”当作零成本优化。

上游 [Flash 闸门](https://github.com/CloudZao/Metalio-E-INK4-Plus/blob/ad8edf4150a688737c0d7c00cae4413079b262ef/main/display/epd_flash_guard.h#L5)明确协调完整波形与 OTA 写入。建议新系统盘点 NVS、OTA、用户记录、日志及字体／资源更新路径，分别判断实际冲突；SD 写入和片上 Flash 擦写不是同一种操作。交互路径先更新内存中的控制状态，持久化按数据耐久性目标安排；不能为省延迟把未落盘的数据宣称为可恢复。

完整波形通常只能在驱动确认安全的边界取消；暂停大文件上传可在块边界完成。系统应界定最大不可抢占窗口，紧急工作不能靠强杀持锁任务处理。ESP-IDF 官方同样提示跨核删除运行中任务可能留下锁或资源。

## 6. 把体验拆成可观察的时间与状态

至少区分：

1. 硬件事件发生／被采样。
2. 系统接受输入并更新逻辑状态。
3. 用户得到可感知反馈。
4. 目标内容稳定可读或音频开始／停止。
5. 业务真正完成，以及必要数据已经可靠保存。

优化应覆盖整条链路。减少软件等待能缩短前半段；屏幕物理波形的时长需由驱动、面板及模式解决。若刷新前后有输入暂停窗口，要测其长度与事件保留情况。上游 [触摸代码](https://github.com/CloudZao/Metalio-E-INK4-Plus/blob/ad8edf4150a688737c0d7c00cae4413079b262ef/main/boards/metalio-e-ink4-plus/display/metalio_touch.c#L331)保留已采样边沿，并在屏电源切换附近暂停 feed；这不证明每一个未采样短按都不会丢失。

建议保留稳定页面，等待时显示真实阶段；具备硬件并获用户允许时可使用震动／声音作即时反馈。分页、滚动或反馈形式需做任务对照，不预先禁止连续滚动。AI 文本按可读片段和最长等待阈值更新，避免每 token 触发整页重新排版；用户回看旧内容时不强制跳到末尾。

UI 对象建议由单一执行上下文管理，其他服务投递状态变化。[LVGL 9.2 官方线程说明](https://docs.lvgl.io/9.2/porting/os.html)要求串行化并发调用；这是通用参考，上游项目依赖为 9.5.0，具体锁及适配 API 仍应按该版本核对。

## 7. 例子：听故事，同时备份，临时唤起 AI

以下是候选流程，暂停／降低原音量等具体产品策略仍待选择。

| 时刻 | 系统动作 | 用户可感知结果 |
| --- | --- | --- |
| 正常听故事 | 音频保留缓冲；备份低优先级按块上传，限制内存与 IO。 | 播放连续，备份进度不持续抢刷屏。 |
| 用户按 AI 键 | 记录当前内容位置，按策略协调原音频；输入控制直接进入系统服务，备份在块边界让出资源。 | 知道设备已接受输入，阅读位置和故事进度保留。 |
| 等待识别／云响应 | 音频与网络按预算执行，UI 不同步等待；后台重计算暂缓。 | 页面稳定，可以返回或取消。 |
| AI 开始回答 | 按片段显示，按需播放；只为当前场景提交有效结果。 | 先得到可用答案，再逐步完整。 |
| 用户取消或返回 | 标记取消，停止后续可取消工作；迟到结果不覆盖新场景。已有外部副作用单独确认真实状态。 | 回到原内容，取消状态明确。 |
| 本轮结束 | 保存必要新状态，释放工作内存；恢复后台最低服务份额与适合的功耗状态。 | 能继续原来的读听，后台最终完成。 |

## 8. 第一轮原型应验证什么

先测资源和争用，再确定优先级数值、并发上限、缓冲大小与体验指标。可以逐步构造四组负载：

1. 阅读翻页与输入，无后台负载；建立硬件和软件基线。
2. 同时音频播放、下一页准备与局部／完整刷新；定位 DMA／CPU／内存带宽冲突。
3. 加入备份、Flash 安全写入和断网重试；观察最长阻塞、恢复与后台饥饿。
4. 加入 AI 流式回复、取消／页面切换及内存压力；检查迟到结果、分配失败和状态持久化。

记录两核任务执行／等待、临界区和资源闸门时长、内部／外部 heap 的最小余量和最大连续块、栈高水位、音频欠载、显示欠载、任务排队和取消耗时。输入到逻辑响应、首次可见、稳定可读、真正完成分别统计 p50／p95／p99，不只报平均 CPU 或绘制 FPS。

追踪本身采用有界内存缓冲，避开关键波形中的同步大量日志。测试应包含冷启动、冷热缓存和长时间运行；无动作时采用事件等待及合适的功耗策略，不靠不断轮询维持活跃。

目前未设定通用的“100 ms／60 fps 即合格”门槛；R-011 继续保留。阈值应在实际屏幕和并发基线上选择，不能用网页演示或空载平均值代替实机验收。
