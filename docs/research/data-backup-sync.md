# 用户数据、备份同步与账户：方向讨论

资料查阅日期：2026-10-26；需求状态更新：2026-10-30。硬件限定 E-Ink4 Plus。关联 I-012、I-027、R-022、R-023。用户现已确认账户系统、服务器备份与恢复的能力方向；本文的存储协议、账户形式及实现方案仍是待讨论建议，本次未复验外部资料或实机能力。

后续竞品依据：[Anki F-M020-03](/home/workspace/reader/docs/research/interaction-library/cases/M-020-anki.md)拆解同步方向、备份与媒体恢复，[Kobo F-M002-02/03](/home/workspace/reader/docs/research/interaction-library/cases/M-002-kobo.md)记录内容来源与笔记删除/导出的关系。它们供取舍参考；账户系统方向已由 R-022 确认，备份粒度与具体账户形式仍未定。

## 用户表达与当前判断

2026-10-26 用户关心刷机、固件更新、卸载重装 app 时的数据遗失，提出服务器备份候选。2026-10-30 用户进一步确认需要账户系统与服务器备份，理由是初期可能不稳定，后续可能有朋友使用，形成 R-022、R-023。整机／按 app 恢复、同步频率、部署与具体账户形式仍待定。

**有条件可行**：系统统一保存用户数据，向服务器备份，在刷机或重装后恢复。条件包括可恢复的数据格式、内容与进度的一致性、服务器访问凭据，以及独立于被刷设备的恢复入口。目前没有本项目的备份或恢复测试。

**建议**：系统管理备份，内部按“共享数据 + 各 app 数据”组织，对外同时提供整机用户数据恢复和单 app 恢复。两种恢复范围可以共用一套备份，不需要现在二选一。服务器位置、自动化程度和账户形式仍待确定；是否建设账户与服务器备份已不再是待定项。

## 先分清四件事

| 能力 | 解决的问题 | 仍需补上的部分 |
| --- | --- | --- |
| 更新时保留本地数据 | 正常升级不主动清除设置和内容 | 无法应对全擦、存储损坏、错误迁移或丢失设备。 |
| 备份 | 留下一份可恢复的历史状态 | 要验证备份完整，并实际能恢复；仅复制完成不够。 |
| 同步 | 让设备和服务器、或多台设备的当前状态接近 | 误删也可能传播；需要历史版本才能找回。 |
| 原始 Flash 镜像 | 为同版本工程救援保存底层字节 | 不包含独立 TF 卡；跨固件版本和单 app 恢复不方便。 |

外部例子：Syncthing 的文件版本管理默认关闭，且主要归档从其他设备收到的替换/删除，不覆盖所有本地改动。这说明“开了同步”不能直接等同于“所有误操作均可恢复”。这里只借鉴行为，不建议在 MCU 上直接运行 Syncthing。[官方说明](https://docs.syncthing.net/users/versioning.html)

## 整机与按 app：比较的是哪些层次

| 方案 | 合适用途 | 对本项目的判断 |
| --- | --- | --- |
| 整片 Flash 原样备份 | 固定板卡、固件和分区布局下的工程回退 | 可作为辅助，**当前约束下不建议**作为唯一用户备份。TF 卡和服务端数据不在其中。 |
| 每个 app 各自实现备份 | 少数独立应用的导入导出 | 容易漏掉共享书库、系统设置、AI 任务和跨应用关系；也让每个 app 重复开发。 |
| 系统统一逻辑备份，按 app 和共享资源组织 | 一键恢复全部，或只恢复书库/练习等指定部分 | **建议研究**。app 描述自己的持久数据和格式版本；系统统一安排上传、版本、校验与恢复。 |

“整机用户数据恢复”建议表达为恢复成员、设置、应用清单和选定数据，不默认覆盖当前可用固件。app 程序本身是否归档、能否重新获取兼容版本，需要单独决定；只有安装清单不保证未来仍能下载到旧 app。

快照与选择性恢复并不冲突，restic 的官方恢复工具就允许从同一快照恢复指定文件或目录；这里只参考产品能力，不选定其作为设备端技术栈。[官方恢复说明](https://restic.readthedocs.io/en/stable/050_restore.html)

## 数据应如何分类：建议稿

| 类别 | 本项目例子 | 备份建议与恢复边界 |
| --- | --- | --- |
| 难以重建的个人记录 | 备忘录、学习进度、错题、阅读批注、故事断点、游戏存档 | 优先保存；按成员归属，记录数据格式版本。 |
| 共享内容 | 书籍、题库、录音、已生成故事、需要保留的音频 | 保存内容本身及版本，或明确可重新获取的来源；进度引用的内容必须可恢复。 |
| 系统与应用配置 | 成员档案、提醒、音量、AI 配置、已安装 app 清单 | 区分可迁移设置和绑定某台设备的设置；恢复提醒不自动补执行所有过期任务。 |
| AI 持久状态 | 用户确认的偏好、跨应用任务状态、内容来源 | 与聊天记录区分；恢复旧任务不能重复发送短信、重复导入或重复执行其他外部动作。 |
| 凭据与密钥 | 模型 API 密钥、服务器凭据、设备身份 | 单独确定加密、迁移和恢复规则；不能默认明文进入普通导出包。 |
| 可再生成内容 | 缩略图、检索索引、临时下载、部分 TTS 缓存 | 可排除或低优先级；先区分临时缓存和用户要求保留的故事/音频。 |

共享书库不应只属于阅读 app 的安装目录。卸载阅读 app 后，听书 app 或 AI 仍可能引用同一本书。相同原则适用于题库、素材和家庭共享资源；具体目录、数据库和接口尚未设计。

## app 的安装、卸载和升级

建议把“卸载程序”和“删除个人数据”作为不同操作：

- 普通卸载可以保留一份明确可见、可管理的 app 数据档案，重新安装兼容版本时恢复。
- 用户主动清除数据时，明确区分设备副本、同步副本和历史备份；不能让旧设备上线后又悄悄恢复已删除内容。
- app 更新前后要识别数据版本。旧程序未必能读取新格式；固件回滚成功也不代表用户数据已回滚。
- 跨应用恢复要包含必要的共享内容和索引关系。先恢复可用内容再关联进度，缺少依赖时给出真实状态。

这是为解决用户担忧提出的候选行为，不是已经确认的默认卸载政策或数据保留期限。

## 账户：能力方向已确认，注册与恢复形式待定

需要分开讨论三个概念：

1. **成员档案**：区分本人和子女的书签、词汇和故事进度，可以先在本地使用。
2. **服务器身份与授权**：确定设备能访问哪一份家庭数据。即使不做手机号/邮箱注册，服务器仍需凭据或配对机制。
3. **刷机后的恢复资格**：新系统如何重新找到并解密原来的备份。唯一凭据若只存在被擦除设备中，服务器上有数据也可能无法恢复。

| 候选方式 | 适合的规模 | 需要接受的代价 |
| --- | --- | --- |
| 家庭空间 + 设备配对 + 独立保管的恢复凭据 | 本人和子女、少量设备 | 家长负责保存恢复资料；配对、丢失设备和撤销权限仍要设计。 |
| 自建服务器已有身份体系 | 已有家庭服务器或 NAS | 复用服务器访问管理，但成员档案、数据版本和设备恢复仍要单独处理。 |
| 完整账户系统 | 将来开放更多家庭或需要远程自助管理 | 注册、登录、找回、成员管理等持续维护工作更大。 |

**当前要求与实现建议**：账户系统能力方向已确认，需考虑未来朋友使用。建议明确账户、家庭空间、成员与设备的数据归属及恢复关系；手机号／邮箱、配对或复用已有身份体系等具体方式待比较。若采用加密备份，恢复密钥必须有设备以外的保管方法。具体凭据形式未定，也未要求儿童各自注册账户。

## 对 Plus 资源和使用体验的影响

以下为助手建议，未做流量或功耗实测：

- 小体积的重要进度可优先同步；书籍、音频等大文件按块处理，避免先在内存中组装整个备份。
- 根据充电状态、网络和用户选择安排大文件上传；4G 下是否允许自动传大量内容应可控制。
- UI 显示最近一次可恢复备份的时间、尚未上传的数据和失败原因；离线未备份的新记录依然可能在损坏或全擦后丢失。
- 创建一致的备份时，要协调应用正在写入的数据与共享内容；不能在任意时刻逐文件复制后就宣称形成同一时间点快照。

## 后续有限验证

账户与服务器备份方向现已获认可，按底层系统优先级先明确资源预算与恢复目标。可先用一个备忘录、一份学习记录和一个故事断点验证：正常升级、全擦后恢复、app 卸载重装、网络中断续传，以及备份过程中继续修改。还应检查缺失内容、格式版本不兼容、误删恢复、旧设备重新上线和凭据不在原机时的恢复。

“成功”的核心是恢复后能继续使用相同内容和正确进度，并如实说明缺失部分；不是仅验证服务器存在一个压缩包。保留期限、自动同步频率、服务器由谁提供、首版是否多设备同步，均保持待讨论。
