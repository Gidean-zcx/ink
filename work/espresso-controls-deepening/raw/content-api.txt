Overview
The Economist Content API provides authenticated access to Economist articles, sections, and tags for Economist Pro clients. This document is for developers integrating with the API.
Base URL:
https://api.economist.com/eco/content/all/b2b-content-api
Versioning is done via route prefixing (e.g., /v1/... ) to ensure backward compatibility.
Authentication
The B2B Content API uses API keys to authenticate requests. You can get your API key by contacting The Economist Pro Operations Team (economistpro@economist.com).
Your API keys carry many privileges, so be sure to keep them secure! Do not share your secret API keys in publicly accessible areas such as GitHub, client-side code, and so forth.
All API requests must be made over HTTPS. Calls made over plain HTTP will fail. API requests without authentication will also fail.
Endpoint
You can authenticate by sending a POST request to the following login endpoint.
POST /v1/auth/login
Request
Define the client_id and client_secret in the request body to obtain a JWT token.
{
"client_id": "your-client-id",
"client_secret": "your-client-secret"
}
Response
The response will include a JWT token that you can use for subsequent requests.
{
"metadata": {
"request_id": "7779ee23b8451d335128f04901b13506"
},
"data": {
"access_token": "<JWT-TOKEN>",
"expires_in": 86400,
"token_type": "Bearer"
}
}
When it expires, the token will no longer be valid, and you will need to authenticate again to obtain a new token.
The expires_in field indicates the number of seconds until the token expires (in this case, 86400 seconds or 24 hours).
Usage
Add the token to the Authorization header of all subsequent requests:
Authorization: Bearer YOUR_ACCESS_TOKEN
Metadata
The metadata object provides additional contextual information about the API response. It includes details such as filtering parameter and a unique request identifier useful for debugging and support.
Notes
Not all endpoints include all fields. For example, /v1/sectionsand /v1/tags typically only return request_id.
request_id should always be included when contacting support.
Example Metadata Format
{
"metadata": {
"start": "2025-05-21",
"end": "2025-06-20",
"filters": {
"sections": ["leaders", "britain", "the-world-this-week"],
"tags": ["artificial-intelligence"]
},
"request_id": "7779ee23b8451d335128f04901b13506"
}
}
Attributes
start (string) :The start date of the data range used in the request, formatted asYYYY-MM-DD.end (string) :The end date of the data range used in the request, formatted asYYYY-MM-DD.filters (object) :An object containing any filters applied to the request. This may include:filters.sections (array | string) :An array of section slugs that were filtered in the request.filters.tags (array | string) :An array of tag slugs that were filtered in the request.request_id (string) :Each API request returns a unique request_id in the response metadata. This ID can be used for debugging and support purposes. If you encounter an error, please provide this ID when contacting support.
Pagination Response
The Economist Content API uses cursor-based pagination for endpoints that return collections of data, such as /v1/articles and /v1/tags. This method provides clear, bidirectional navigation and consistent handling of large result sets, especially as the dataset changes over time.
Notes
You can page forward and backward through results using cursor tokens, after_cursor and before_cursor.
The response includes:
has_next_page and has_previous_page (booleans)
next_cursor and previous_cursor (opaque strings)
Cursors are opaque and must not be manipulated
Always check has_next_page and has_previous_page to determine if further requests are needed
Request Parameter
after_cursor (string) optional:The cursor token to start returning results after. If not provided, results start from the beginning.before_cursor (string) optional:The cursor token to start returning results before. If not provided, results end at the last item.
Response
{
"data": [ ... ],
"metadata": { ... },
"pagination": {
"has_next_page": true,
"has_previous_page": true,
"next_cursor": "a16fa874-0002-4507-bbc0-d1ac9f3ae14a",
"previous_cursor": "c56d46f4-f603-4a37-af4f-50a10a6a528c"
}
}
Attributes
pagination (object) :An object containing pagination information:pagination.has_next_page (boolean) :Indicates if there are more results available after the current page.pagination.has_previous_page (boolean) :Indicates if there are results available before the current page.pagination.next_cursor (string) :An opaque string token to use for fetching the next page of results. If there are no more results, this will be null.pagination.previous_cursor (string) :An opaque string token to use for fetching the previous page of results.
Rate Limiting
The Economist Content API enforces a global rate limit of 10 requests per second (RPS) per client. Clients should implement retry logic with exponential backoff to avoid service disruption.
Entitlements
The Economist Content API enforces entitlement-based access control. This means that each authenticated client can only access the content (e.g., sections, articles) they have been explicitly authorized to view, based on a contractual agreement with The Economist.
Entitlements are evaluated at runtime and apply to:
Section-level access for /v1/articles
Section visibility in /v1/sections
The World in Brief visibility in /v1/the-world-in-brief
How Entitlements Work
When a client authenticates using /v1/auth/login, their access rights are internally resolved and applied to every subsequent request.
All responses from content endpoints are automatically filtered to include only data the client is entitled to.
If a client tries to access or filter by an unauthorized section, the API will reject the request with a 403 Forbidden error.
Unauthorized Access Example
If a client includes a section they are not entitled to, the API returns:
403 Forbidden
{
"errors": [
{
"error": "unauthorized",
"error_description": "You are not authorized to access one or more requested sections"
}
],
"metadata": {
"request_id": "7779ee23b8451d335128f04901b13506"
}
}
Example
Section Filtering Within Entitlements
Suppose a client is entitled to the following sections:
leaders
britain
the-world-this-week
They may request
All articles from their accessible sections:
GET /v1/articles
Articles only from the leaders section:
GET /v1/articles?sections=leaders
Articles from leaders and britain:
GET /v1/articles?sections=leaders,britain
But this request will fail if they include a section like business that they are not entitled to:
GET /v1/articles?sections=leaders,business
→ 403 Forbidden
Images
The B2B Content API can include image components in article responses for clients with image entitlements. Image components provide access to charts, tables, maps, and infographics that accompany articles.
Image Entitlements
Not all clients are entitled to images. Image access depends on your specific agreement with The Economist. If you do not have image entitlements, image components will not appear in API responses.
Signed Image URLs
All image URLs provided by the API are signed with cryptographic signatures. This means:
URLs cannot be modified—any changes to the URL will invalidate the signature
URLs have a fixed expiry time—they will stop working after 30 days. Treat these URLs as short-lived and do not persist or rely on them beyond their validity window. When rendering or otherwise using an image, you should obtain or refresh the URL from the API (for example, on page load or on a cache miss), and re-fetch a new URL if an existing one fails or returns an expired/forbidden response.
URLs are client-specific—each URL is tied to your client identifier, allowing The Economist to assess usage and ensure proper access control
Image Types
Clients with image entitlements will receive the following image types:
CHART — Data visualizations and charts
TABLE — Tabular data visualizations
MAP — Geographic maps
INFOGRAPHIC — Infographic images
Best Practices
When integrating images into your application, we recommend the following approach:
Server-side rendering: Access image URLs when rendering pages on the server side, so the URLs are not exposed in client-side code. This is the preferred approach.
Direct embedding: If server-side rendering is not possible, you can embed the URLs directly in your HTML as image elements.
URL expiration: Be aware that image URLs expire. Implement a mechanism to refresh URLs periodically by re-fetching the article content from the API.
Self-hosting: While it is possible to download and self-host images depending on your CMS workflow, we prefer that clients use the provided URLs directly to ensure proper usage tracking and access control.

Filtering with sections or tags
You cannot filter by both sections and tags in the same request. Attempting to use both filters will result in a 400 Bad Request error.
We recommend filtering by sections as they are historically populated for all articles, providing more comprehensive and reliable results. Tags may not be available for all historical content.
Where tags are present on older articles, they were generated automatically and may use a different naming convention from editorial tags on recent content (for example cs-poland versus poland). See Tags for guidance on normalizing historic tag slugs in your application.
Sections or tags can be provided as a comma-separated list of slugs, e.g. ?tags=britain,world. If no filters are applied, all articles will be returned.
Filtering with date ranges
Always specify both start_date and end_date parameters explicitly when filtering articles by publication date. This ensures predictable, unambiguous results.
For example, to get the last 3 months of articles, calculate both dates explicitly. For instance, if today is October 31st 2025 use start_date=2025-07-31 and end_date=2025-10-31 to retrieve all articles from July 31st 2025 to October 31st 2025.

/v1/sections
GET /v1/sections
Retrieves all content sections that the authenticated client is entitled to access. A section typically represents a high-level editorial category (e.g., “leaders”, “britain”, “business”). These sections can be used to filter content when querying articles via /v1/articles.
This endpoint requires authentication and reflects the access entitlements associated with the client’s credentials.
Notes:
The slug is used as a query parameter when filtering articles (e.g., ?sections=leaders)
The name is a human-readable label suitable for UI display

/v1/tags
GET /v1/tags
Retrieves all tags available in the system. Tags represent topical classifications that can be used to refine article queries (e.g., “Artificial intelligence”, “Politics”, “Finance”). These tags are used with the /v1/articles endpoint to filter results.
This endpoint supports pagination and requires a valid Bearer token.
Notes
slug values are used in query strings for /v1/articles (e.g., ?tags=technology)
name provides a display-friendly version of the tag on editorial content; on older generated tags it often mirrors the slug (e.g. cs-poland)
Historical articles may return generated tags with a cs- prefix on the slug (e.g. cs-poland), while newer editorial tags use slugs without that prefix (e.g. poland) and a human-readable name. To compare or merge tags across eras in your application, remove the cs- prefix from generated slugs. Use slugs as returned when calling the API.

/v1/the-world-in-brief
GET /v1/the-world-in-brief
Retrieves the latest The World in Brief for today's date.
The World in Brief is The Economist's news service. It allows readers to catch up quickly on the global stories that matter, with updates appearing throughout the day.
The content is made up of several short paragraphs ("Gobbets") with the latest from around the world, and longer, but still bitesize, articles ("Chunks") covering what is happening today.
Time zone based delivery
The World in Brief is delivered based on the time zone configured during onboarding. The API determines "today's date"        using your configured local time zone.
When you make a request, the API:
Determines the current date in your configured time zone
Attempts to retrieve The World in Brief for that date
If today's edition is not yet available, automatically falls back to the previous day's edition
This means clients in different time zones will receive the edition corresponding to their local date. For example, a client in New York requesting at 11 PM EST on January 1st will receive January 1st's edition, while a client in Tokyo requesting at 1 AM JST on January 2nd will receive January 2nd's edition.
